# Issue #264 — Feed cache design (database-agent + security-agent design pass)

**Status:** design — no code written. Resolves the five open decisions from
`issues/264-rss-feed-cache-regeneration.md` §0/§Technical Requirements before implementation.

**Location note:** placed in `plans/` (not `docs/decisions/`) because it is an issue-scoped design
plan, matching the issue's own §0 reference `plans/264-*-design.md`. `docs/decisions/NNN-*.md` is the
sequentially-numbered ADR set for cross-cutting architecture decisions; a single-table feed cache is
not one. No new ADR is warranted — this reuses the patterns already recorded in ADR-009
(proto→schema codegen) and ADR-017 (GDPR writing-assistant data model).

---

## Decision 1 — Proto codegen vs hand migration

**Recommendation: proto codegen path.** Same as every other persisted `op.*`/`cache.*` table in the
repo except the two pgvector tables (which use `skip_ecto: true` only because proto cannot express a
`vector(1024)` column — not our case).

**Precedent confirmed by inspection** — `isbn_resolver_cache` / `title_search_cache` are proto-generated:
- `proto/persisted.exs:85-147` — both entries define `proto_file: "stacks/infra/v1/book_cache.proto"`,
  `proto_message: "IsbnResolverCacheEntry"` / `"TitleSearchCacheEntry"`, and generate an Ecto schema
  (`lib/stacks/gen/books/isbn_resolver_cache_entry.ex`, header line 1 = "Generated by mix proto.sync —
  DO NOT EDIT MANUALLY") and a migration
  (`priv/repo/migrations/20260422072905_create_isbn_resolver_cache.exs`, same generated header).
- Both carry `dbt_grant: false` + `skip_dbt: true` (persisted.exs:98-99, 128-129) — the exact
  warehouse-exclusion pattern this cache needs.
- The proto message itself (`proto/stacks/infra/v1/book_cache.proto`) documents that these `infra/v1/`
  messages are "persistence plumbing only … NOT A WIRE CONTRACT" — the correct home for a feed cache.

A hand-written migration would fail `mix proto.sync --check` in CI (drift) and would not produce the
Ecto schema. **Rejected.**

### Exact proto message — new file `proto/stacks/infra/v1/feed_cache.proto`

```proto
syntax = "proto3";
package stacks.infra.v1;

// FeedCacheEntry — persisted Atom XML for one platform-visible bookshelf's feed.
// NOT A WIRE CONTRACT. Persistence plumbing only (mirrors book_cache.proto):
// RegenerateFeedJob upserts a row on placement change; FeedController reads it.
// One row per bookshelf (bookshelf_id unique). Derived/regenerable — never
// exported to dbt (skip_dbt). Field numbers are forever — never reuse a number.
message FeedCacheEntry {
  // FK → op.bookshelves.id. Unique natural key — one cache row per bookshelf.
  string bookshelf_id = 1 [json_name = "bookshelf_id"];

  // Rendered Atom 1.0 XML for the feed (Feeds.build_atom_xml output).
  string atom_xml = 2 [json_name = "atom_xml"];

  // ETag = lowercase hex MD5 of atom_xml (Feeds.compute_etag). Stored alongside
  // the XML so a cache hit serves the identical etag a fresh render would.
  string etag = 3 [json_name = "etag"];
}
```

`created_at` / `updated_at` come from `timestamps: :standard` in the manifest — do not add them as
proto fields (matches every other manifest entry).

### Exact `proto/persisted.exs` manifest entry (add under the "Book lookup caches" block)

```elixir
%{
  proto_file: "stacks/infra/v1/feed_cache.proto",
  proto_message: "FeedCacheEntry",
  table_name: "feed_cache",
  schema_prefix: "op",
  ecto_module: Stacks.Feeds.FeedCacheEntry,
  ecto_path: "lib/stacks/gen/feeds/feed_cache_entry.ex",
  dbt_path: "stg_feed_cache.sql",   # required key; never emitted because skip_dbt: true
  timestamps: :standard,
  migration_exists: false,          # flip to true after the first `mix proto.sync` generates it
  dbt_grant: false,                 # no GRANT SELECT to stacks_dbt — cache out of warehouse
  skip_dbt: true,                   # no stg_ model / schema.yml block — GDPR warehouse guard
  indexes: [
    %{name: "feed_cache_bookshelf_id_index", columns: [:bookshelf_id], unique: true}
  ],
  field_overrides: %{
    bookshelf_id: %{
      belongs_to: Stacks.Shelving.Bookshelf,
      references_table: :bookshelves,
      on_delete: :delete_all,
      null: false
    },
    atom_xml: %{null: false},
    etag: %{null: false}
  }
}
```

The `belongs_to` + `references_table:` + `on_delete: :delete_all` shape is the confirmed non-`users`
FK pattern (precedent: `blog_assistant_sessions` FK → `users`, persisted.exs:1019-1024, which generates
`references(:users, type: :binary_id, prefix: "op", on_delete: :delete_all)` in
`20260713181718_create_blog_assistant_sessions.exs:23`; and `post_comments` FK → `blog_posts`,
persisted.exs:567-572). Substituting `:bookshelves` yields the CASCADE FK we need.

**Generation flow:** `just run mix proto.sync` → generates `lib/stacks/gen/feeds/feed_cache_entry.ex`
(`@schema_prefix "op"`, `schema "feed_cache"`) + a `create table(:feed_cache, prefix: "op", …)`
migration with the FK, the unique index (built `concurrently`), and — because `dbt_grant: false` — **no**
GRANT block. Then flip `migration_exists: true` and re-run `mix proto.sync --check` (green). Follow with
`just run just verify` (test-dbt / fresh-DB gate).

## Decision 2 — Schema

| Column | Type (migration) | Notes |
|--------|------------------|-------|
| `id` | `binary_id` PK | proto-gen default |
| `bookshelf_id` | `binary_id`, `references(:bookshelves, …, on_delete: :delete_all)`, **`null: false`**, **unique** | one cache row per bookshelf |
| `atom_xml` | `:text`, `null: false` | proto `string` → `:text` (precedent: `isbn`→`:text`, migration line 22) |
| `etag` | `:text`, `null: false` | stored pure-MD5 etag |
| `created_at`, `updated_at` | `:utc_datetime_usec` | `timestamps: :standard` |

- **Prefix: `op`** (recommended, not `cache`). Unlike the ISBN/title caches (no user linkage — pure
  external-lookup memoisation), this cache holds a user's shelf content and is subject to erasure. `op`
  keeps it in the user-operational mental model alongside `bookshelves`/`placements`. (Prefix does not
  affect erasure mechanics — that runs off the Ecto schema regardless — but `op` is the honest
  classification for user-linked data.)
- **`ON DELETE CASCADE`** on `bookshelf_id` (`on_delete: :delete_all`) — belt-and-suspenders for erasure
  (see Decision 4); also cleans the row if a bookshelf is deleted for any non-erasure reason.
- **Unique index on `bookshelf_id`** — enforces one row per bookshelf and is the conflict target for the
  worker's upsert (`on_conflict` needs a unique constraint to target).
- **`skip_dbt: true` + `dbt_grant: false`** — no `stg_feed_cache` model, no `wh` exposure. This is the
  GDPR warehouse-leak guard: derived feed XML (which embeds user-authored titles in `<summary>`) must
  not land in the warehouse. Do **not** add a staging model.

## Decision 3 — Read / write / invalidation flow

Introduce a thin `Stacks.Feeds` cache API so the worker and controller share one path
(`get_cached/2`, `put_cache/3` or a combined `regenerate/2`); keep the controller thin.

**Write (`RegenerateFeedJob.perform/1`):** on `{:ok, xml, etag}` from `generate_atom/2`, resolve
`bookshelf_id` (the job already resolves the bookshelf via `Feeds.generate_atom` → `Shelving.get_bookshelf`;
thread the id through or add a lookup) and **upsert**:

```elixir
Repo.insert(
  %FeedCacheEntry{bookshelf_id: bookshelf_id, atom_xml: xml, etag: etag},
  on_conflict: {:replace, [:atom_xml, :etag, :updated_at]},
  conflict_target: :bookshelf_id
)
```

- `{:error, :not_public}` → `:ok` (skip, no row) — unchanged.
- `{:error, :not_found}` → `{:cancel, …}` (no row) — unchanged.
- **Idempotent:** two runs of unchanged data leave one row with the same `etag` (MD5 of identical XML is
  identical).

**Read (`FeedController.show`):** look up cache by `(user_id, bookshelf_name)` → `bookshelf_id` → row.
- **Hit:** serve stored `atom_xml` + `etag`; preserve `If-None-Match` → `304`, `Content-Type:
  application/atom+xml`, `Cache-Control: public, max-age=300` (current behaviour,
  `feed_controller.ex:24-36`).
- **Miss:** call `generate_atom/2`, fill the cache (synchronous `put_cache/3`, so the very next request
  is a hit — enqueuing instead would leave a race window), serve the fresh result.
- Preserve `404` (not found) / `403` (not platform-visible) exactly (`feed_controller.ex:38-47`). On a
  miss these come straight from `generate_atom/2`'s error tuples — no cache row is written for them.

**ETag correctness across a cache-fill (confirmed):** `Feeds.compute_etag/1` is a pure lowercase-hex
MD5 of the XML (`feeds.ex:47-50`), a pure function of content. The stored etag is therefore byte-identical
to the etag a fresh `generate_atom/2` would produce for the same data. So `304` holds whether the client's
`If-None-Match` is compared against a stored etag (hit) or a freshly computed one (miss-fill) — **no false
`200`s and no false `304`s**. Store the etag alongside the XML; never recompute it divergently.

**Invalidation (already wired — verify, don't rebuild):** `placement.created/moved/removed` →
`Stacks.Feeds.Handlers.PlacementHandler` (registered `stacks/events/registry.ex:47,51,55`) → enqueues
`RegenerateFeedJob`, which now **rewrites** the row. Confirm the `placement.moved` dual-shelf case
re-enqueues/regenerates **both** the source and destination bookshelves' cache rows.

## Decision 4 — GDPR erasure (critical)

**gdpr-review verdict: CONCERNS → resolved in-scope.** The table is personal data (user-linked via
`bookshelf_id → bookshelves → users`; the XML `<summary>`/`<title>` embed user-authored book titles).
Erasure MUST remove it; export is n/a.

**The schema-guard blind spot is real and confirmed.** `GDPR.Deletion.delete_user_data/1`
(`deletion.ex`) reaches user data through explicit, hand-written Multi steps — it does **not** rely on
FK cascade discovery. Its steps key off `user_id` (bookshelves, comments, event_log, sessions) or off
the derived `bookshelf_ids` list (history, placements). A new `op.*` table whose only user path is
`bookshelf_id → op.bookshelves` is invisible to the `deletion_test.exs` schema-guard, which (per the
issue, `deletion_test.exs:388-455`) only audits `op.*` FKs whose target is `op.users`. **Erasure cannot
rely on the guard or on `Repo.delete(user)` cascade** (the user delete cascades to bookshelves, and the
CASCADE FK would then reach feed_cache — but that is the belt, not the braces; the explicit step is the
authoritative guarantee and is what the regression test pins).

### Concrete erasure plan (all inside the existing single `Ecto.Multi` transaction)

1. **Alias** `Stacks.Feeds.FeedCacheEntry` in `deletion.ex` (add to the `alias` block ~line 31).
2. **Multi step `:delete_feed_cache`, ordered BEFORE `:delete_bookshelves`** (order it right after
   `:delete_placements`, ~deletion.ex:127; `bookshelf_ids` is already in scope from the `:bookshelf_ids`
   step at line 111). Scope by the user's bookshelves:
   ```elixir
   |> Multi.run(:delete_feed_cache, fn repo, %{bookshelf_ids: bookshelf_ids} ->
     {count, _} =
       repo.delete_all(from fc in FeedCacheEntry, where: fc.bookshelf_id in ^bookshelf_ids)
     {:ok, count}
   end)
   ```
   (Ordering before `:delete_bookshelves` makes the explicit delete authoritative and independent of FK
   cascade timing; the CASCADE FK is redundant safety.)
3. **`preview_user_data/1`** (deletion.ex:52-68): add
   `feed_cache: count(from fc in FeedCacheEntry, where: fc.bookshelf_id in ^bookshelf_ids)` so the
   operator dry-run (`Stacks.Release.gdpr_erase_user/1`) reports it. Uses the same scope as the erasure
   step — cannot drift.
4. **`ON DELETE CASCADE`** on the FK (Decision 2) — second line of defence: even if the explicit step
   were ever removed, deleting the bookshelf row removes the cache row.
5. **Regression test** (`gdpr/deletion_test.exs`): seed a platform bookshelf + a cached feed row (via the
   worker or a direct insert); `delete_user_data/1`; assert `Repo.aggregate(from(fc in FeedCacheEntry,
   where: fc.bookshelf_id in ^ids), :count) == 0` and that `preview_user_data/1` reported the count > 0
   beforehand.

**Export = n/a, justified.** The cache is derived/regenerable; the underlying source data (placements +
bookshelves) is already in `export_user_data/2` (issue cites `export.ex:82-84`; inspection confirms
`export.ex` exports operational data and has no feed concept — correct, nothing to add). Do not add
feed_cache to export.

**Warehouse leak = none.** `skip_dbt: true` keeps it out of `wh`/staging; it is never written to
`event_log` or `audit`.

**Optional P2 (future-proofing):** extend the `deletion_test.exs` schema-guard to also flag `op.*` tables
carrying a `bookshelf_id` FK that lacks CASCADE (closing the class of blind spot, not just this
instance). In-scope only if cheap; otherwise spin out — it is not required for #264 correctness (the
dedicated regression test covers this table).

## Decision 5 — Staleness model

**Recommendation: no TTL.** Event-driven invalidation is authoritative and complete:

- Every mutation that changes a feed's content is a placement event (`created`/`moved`/`removed`), and
  each is already wired to re-enqueue `RegenerateFeedJob`, which upserts the row. There is no path that
  changes feed content without emitting a placement event, so there is no source of silent staleness for
  a TTL to catch.
- **Cold cache** is covered by the on-miss cache-fill (Decision 3): the first read after a deploy / cache
  eviction generates fresh and fills the row.
- The **HTTP** `Cache-Control: public, max-age=300` is a *client/CDN* freshness hint, unchanged and
  independent of the server-side store; it is not a server TTL and does not gate correctness (the pure-MD5
  ETag lets a revalidation `304` even after max-age lapses).

Adding a TTL would only introduce needless regeneration and a window where a valid cached row is treated
as stale. **Rejected.** (Contrast the ISBN/title caches, which *do* carry `expires_at` — those memoise
*external* upstream results that can change without any local event; a feed is a pure function of local
placement state we already observe. Different problem, different model.)

If a belt-and-suspenders safety net is ever wanted, prefer a low-frequency reconciliation sweep that
re-renders and compares etags (rewriting only on mismatch) over a blunt TTL — but this is **not** needed
for #264 and should not be built now.

## Open questions for a human call

1. **Schema prefix `op` vs `cache`.** Recommended `op` (user-operational, erasable). The only argument
   for `cache` is co-locating with the other two L2 caches. If the platform owner prefers all caches under
   the `cache` schema for operational tidiness, that is viable — erasure still works (it runs off the Ecto
   schema, and the explicit `:delete_feed_cache` step is prefix-agnostic) — but it slightly muddies the
   "`cache.*` = non-personal external memoisation" convention the current two tables establish.
   **Default to `op` unless the owner objects.**
2. **Miss-fill: synchronous write vs enqueue.** Recommended synchronous `put_cache/3` in the controller so
   the next request is a guaranteed hit (the point of #119 §12's hit-rate). If the owner wants the public
   feed route to stay strictly read-only (no writes on a GET), the fallback is to serve fresh + enqueue
   `RegenerateFeedJob` and accept that the *immediately* following request may still miss. Recommend
   synchronous; flag for confirmation.

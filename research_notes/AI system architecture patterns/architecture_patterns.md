## Key Question 1: What does Huyen say about cascades / routing between cheap and expensive models — when to route, how to decide, how to measure the router?

### Takeaway
Huyen's public, citable guidance is about **routing** (an intent classifier that decides *before* generation) rather than **cascading** (run cheap, escalate on a confidence check); she recommends small specialised classifiers because they are cheap enough to run several of them, and she places the router *fourth* in the build order, after guardrails. The cascade-with-scorer pattern that actually fits a book-identification pipeline is better sourced to FrugalGPT and AutoMix, which supply the missing piece Huyen's post does not cover: how to decide escalation and how to handle a noisy confidence signal.

### Cited Findings

**Huyen's own public writing on routing**
- "An application can use different models to respond to different types of queries… Instead of routing all queries to an expensive model, you can route simpler queries to cheaper models." — [Chip Huyen, "Building A Generative AI Platform", huyenchip.com, July 2024](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- A router "typically consists of an **intent classifier** that predicts what the user is trying to do." Predicted intents map to destinations — a static page, a human operator, or a model tuned for that case. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- An intent classifier can flag out-of-scope queries so the system declines with a stock response "**without wasting an API call**." — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- Specialised classifiers "are typically much smaller and faster than general-purpose models," so **several can run without adding much latency or cost**. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- A **next-action predictor** is a distinct component that decides the next step, explicitly including **asking the user for clarification**. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Scorers** are grouped with model APIs because they "are typically AI models, too," and "models used for scoring are typically smaller and faster than models used for generation." — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Build order** Huyen gives (explicitly "common, though you don't need to follow the exact same order"): (1) enhance context → (2) add guardrails → (3) add model router and gateway → (4) add cache → (5) add complex logic and write actions. Also: "A component can be skipped if your system works well without it," and "**Evaluation is necessary at every step of the development process.**" — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Gateway fallback is separate from routing:** "When the primary API is unavailable, the gateway can route requests to alternative models," or retry after a wait. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`

**Huyen on caching, including the semantic-cache warning that bears directly on an embedding tier**
- **Prompt cache**: a 1,000-token system prompt over 1M daily calls saves "approximately 1 billion repetitive input tokens a day," but "this isn't entirely free" — cache size can be large and costly to engineer. Gemini's cached input tokens got "a 75% discount compared to regular input tokens," with storage billed separately at $1.00 per 1M tokens per hour at time of writing. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Exact cache**: reuse results for identical requests; needs an eviction policy (LRU/LFU/FIFO); "How long to cache a query depends on how likely this query is to be called again"; most appealing for multi-step or time-consuming actions. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Semantic cache** (embedding-similarity lookup above a threshold) — Huyen is openly sceptical: "semantic cache's value is more dubious because many of its components are prone to failure." Costs are a vector DB plus a vector search on every query; "**Setting the right similarity threshold can also be tricky**"; a wrong match returns an **incorrect cached answer**. It "might still be worth it if the cache hit rate is high," and should be evaluated first for efficiency, cost, and risk. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- She separately lists **semantic caching** as an example of "starting too complex." — [Chip Huyen, "Common pitfalls when building generative AI applications", huyenchip.com, Jan 2025](https://huyenchip.com/2025/01/16/ai-engineering-pitfalls) `[primary]`

**Cascades proper (not Huyen) — the cheap-first-then-escalate pattern**
- **FrugalGPT** (Chen, Zaharia, Zou, Stanford) is "an instantiation of LLM cascade that learns which combinations of LLMs to use for different queries"; it reports matching GPT-4's performance with **up to 98% cost reduction**, or +4% accuracy at the same cost. The escalation decision is made by **fine-tuned DistilBERT scorers** trained to score correct outputs high and incorrect ones low; an output is accepted when its score exceeds a **threshold**. — [FrugalGPT, arXiv:2305.05176](https://arxiv.org/pdf/2305.05176) `[preprint]`; summarised in [DeepLearning.AI, The Batch](https://www.deeplearning.ai/the-batch/frugalgpt-a-method-to-cut-ai-costs-and-maintain-quality) and [FastML paper review](https://fastml.com/paper-review-frugalgpt)
- The 98% figure is a benchmark result on specific datasets, described by secondary review as holding "on some benchmarks" — not a general guarantee. — [FastML](https://fastml.com/paper-review-frugalgpt) `[secondary]`
- **AutoMix** (Madaan et al.) makes the small model **self-verify** its own answer, "yielding a noisy verification score," and then adds a **meta-verifier** that decides whether to trust that verification before routing: its output is "a binary signal, where 1 means the verifier's output can be trusted." Crucially, "Our method employs a **non-LLM setup for meta-verification** to avoid escalating the self-correction problems seen with LLMs." Later versions frame routing as a POMDP over states **Simple / Complex / Unsolvable**. Reported: ">50% computational cost reduction for comparable performance"; v1 abstract reports "up to 89%" gain in incremental benefit per cost on five context-grounded reasoning datasets with LLaMA2-13B/70B. — [AutoMix, arXiv:2310.12963](https://arxiv.org/abs/2310.12963) `[preprint]`; [code](https://github.com/automix-llm/automix)
- **Cascade vs router, cost and latency structure:** a classifier router picks a model *before* generation and adds its latency to every request; a cascade runs the cheap model first and accepts the cost of multiple sequential calls on escalation. Savings scale with how *rarely* it escalates — a cascade that escalates most traffic pays the cheap model's cost **on top of** the expensive one. — [tianpan.co, "LLM Routing and Model Cascades"](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades) `[practitioner-blog — unverified, treat as framing not evidence]`
- Same source argues cascades can **worsen p95 tail latency even as mean cost falls**, because the hard queries always pay cheap-tier rejection + strong-tier latency. — [tianpan.co, "The Cascade Router Reliability Trap"](https://tianpan.co/blog/2026-04-23-cascade-router-reliability-trap-bimodal-latency) `[practitioner-blog]`

**Measuring the router itself**
- The literature's framing for "when can a cheap stage be trusted to stop" is **selective prediction**: *selective risk* = loss on answered questions ÷ *coverage* (fraction answered). If confidence is well calibrated, a threshold rule is Bayes-optimal — answer only when P(correct) exceeds 1 − (abstention cost). — [UniCR, arXiv:2509.01455](https://arxiv.org/html/2509.01455v2) `[preprint]`
- The evaluation metrics proposed for such systems are **AURC (Area Under the Risk–Coverage Curve)** and **TCE (Target Calibration Error)**, on the argument that these reflect whether a system can be trusted at a *stated* risk level. — [arXiv:2603.21172](https://arxiv.org/pdf/2603.21172v1) `[preprint]`
- Verifier reliability is not uniform: a 2025 study finds **errors from weaker generators are easier for a verifier to catch** than errors from strong generators, and that easy problems let verifiers certify correct answers more reliably. — ["Variation in Verification", arXiv:2509.17995](https://arxiv.org/html/2509.17995v1) `[preprint]`

### Inferences
- **The project's "[gap]" tier is exactly the scorer in FrugalGPT / the self-verifier in AutoMix, not a third model.** The cheapest available escalation signal in a book pipeline is not a learned scorer at all — it is a *free, deterministic* one: whether pyzbar returned a syntactically valid ISBN with a correct check digit. A barcode decoder's success/failure is already a perfectly calibrated confidence signal for its own stratum, which is why the 95% clean-barcode number is trustworthy without any scorer.
- **The planned cover-embedding tier is a semantic cache in Huyen's sense**, and her specific warnings transfer intact: a vector search on every query, a similarity threshold that is "tricky" to set, and the failure mode that a wrong match returns a confidently *incorrect* answer. That last point is the hazard, because a cover-embedding near-miss (same series, different edition) produces a *well-formed, plausible, wrong ISBN* — the class the ISBN hard gate may not catch, since a wrong-but-real ISBN does resolve against Open Library.
- **Measuring the router means plotting a risk–coverage curve per stratum, not reporting one accuracy number.** For this system the stage-level metric that matters is: at what coverage does each tier stop, and what is the error rate *among the items it chose to answer*. The 15% hostile-barcode figure is a coverage failure (the VLM answers with `is_book=true` and no identifier — it neither abstains nor identifies), which is the worst cell of the risk–coverage table: zero useful coverage with a positive-looking response.
- **Huyen's build order argues against adding a mid-tier model before guardrails are solid.** Router is step 3; guardrails are step 2. Given a $50/month budget and an existing 15% hostile stratum that returns a *shaped but empty* answer, the cheaper intervention per her ordering is an output guardrail + abstention path, not a new model tier.
- **Huyen's "next-action predictor… including asking for clarification" maps directly to the missing fourth outcome in this cascade.** Today the pipeline has identify/fail; the literature's third state (AutoMix's *Unsolvable*) is "ask the human for the ISBN" — which, for a hostile barcode, is both the cheapest and the most accurate action available.

### Gaps
- **Huyen's book-specific treatment of cascades, confidence thresholds, and router evaluation could not be sourced.** Her public blog covers routing-by-intent-classifier but does **not** cover cheap-first-then-escalate cascades, confidence calibration, or how to measure a router. The nearest public statements of her position are the "specialised classifiers are small and fast enough to run several" and "scorers are typically smaller and faster than generation models" lines quoted above. If the report needs "Huyen on cascades", it must be stated as *not found in her public writing* and attributed to FrugalGPT/AutoMix instead.
- No source found giving guidance on **routing thresholds under a hard monthly dollar budget** (as opposed to a cost-per-query objective). FrugalGPT optimises cost at fixed quality, not quality under a fixed monthly ceiling.
- No published figures found on **barcode-decoder-first cascades for book/product identification specifically**; all cascade evidence is on text reasoning benchmarks.

## Key Question 2: Prompts as global state, few-shot leakage into outputs, and guardrails that catch WELL-FORMED wrong answers

*(The prompting incident: one prompt was changed to improve a weak stratum, only that stratum was measured, a small gain was observed, and a healthy stratum regressed from 91% → 9%. The prompt's own example value was emitted verbatim on 10 of 16 unrelated inputs.)*

### Takeaway
All three sub-problems are documented, but with uneven evidence quality: the **single-stratum blindness** failure is squarely covered by slice-based evaluation and Simpson's-paradox guidance (Huyen, *DMLS* ch. 6 — section confirmed via O'Reilly TOC, content via secondary notes); **few-shot examples being copied verbatim into outputs** is well attested in practitioner reports but I found **no peer-reviewed study** of in-context example leakage (the memorization literature is about *training* data and does not establish the same mechanism); and the guardrail literature explicitly distinguishes malformed from **"hallucinated, factually inconsistent"** outputs, with the Constraint Tax paper supplying the crucial metric name for this exact bug: **wrong-valid-schema rate**.

### Cited Findings

**(a) Prompts as global state; full-suite discipline**
- Huyen's section on pre-deployment evaluation in *Designing Machine Learning Systems* covers, per O'Reilly's public chapter listing: **perturbation tests, invariance tests, directional expectation tests, model calibration, confidence measurement, and slice-based evaluation** — "The last section of this chapter is dedicated to how to evaluate your model before deploying it to production." — [O'Reilly, DMLS Chapter 6 listing](https://www.oreilly.com/library/view/designing-machine-learning/9781098107956/ch06.html) `[primary — structure only; chapter body not retrieved]`
- **Slice-based evaluation and Simpson's paradox**: a course deck built on this framework gives the canonical shape — Model A wins on the aggregate while Model B beats it **within every subgroup**; aggregate metrics hide the reversal. A worked example: on a 90/10 majority/minority split, Model A scores 98%/80% (96.2% overall) and Model B scores 95%/95% (95% overall); overall accuracy prefers A, per-slice evaluation prefers B. — [Sharif University MLSD lecture deck](https://sharifmlsd.github.io/assets/MLSD_2023_chap_03_lec_12.pdf) `[secondary]`; [worked example](https://www.pulse.bot/ai/blogs/machine-learning-system-design-interview-42-the-base-rate-f1-trap-67185ab0-52a2-4c37-97a9-36874cef2647/) `[practitioner-blog]`
- Third-party notes on *AI Engineering* ch. 4 report Huyen recommends **data slicing** to "detect biases, find performance variations, and **avoid Simpson's paradox**," and cite OpenAI research that **100–1,000 samples** are typically sufficient per evaluation depending on required confidence. — [Alex Strick van Linschoten, notes on AI Engineering ch. 4](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html) `[secondary]`
- **Frameworks silently mutating prompts** is one of Huyen's named pitfalls: extra tools "abstract away critical details, making it hard to understand and debug your system," and a framework "can also change its default prompt without notice, so your application's behavior shifts and you may not know why." — [Huyen, "Common pitfalls"](https://huyenchip.com/2025/01/16/ai-engineering-pitfalls) `[primary]`
- **Open-ended products defeat targeted unit tests.** An ecommerce AI sales startup told Huyen it was "hard to create a specific set of unit tests because the **combination of queries is basically infinite**." — [ibid.](https://huyenchip.com/2025/01/16/ai-engineering-pitfalls) `[primary]`
- **Early gains mislead about later difficulty.** LinkedIn took "1 month to achieve 80% of the experience they wanted, and an additional **4 months to surpass 95%**." UltraChat (Ding et al. 2023): "the journey from 0 to 60 is easy, whereas progressing from 60 to 100 becomes exceedingly challenging." Huyen's summary: "It's easy to build a demo, but hard to build a product." — [ibid.](https://huyenchip.com/2025/01/16/ai-engineering-pitfalls) `[primary]`
- **Tiered test execution (the practitioner consensus):** Hamel Husain's three levels — "**Level 1: Unit tests. Level 2: Model & human eval. Level 3: A/B testing**" with "The cost of Level 3 > Level 2 > Level 1." Level 1 runs **on every code change**; Level 2 on a cadence; Level 3 only after significant product changes. Assertions "should run fast and cheaply as you develop your application." Rechat maintains "hundreds" of such unit tests, continuously updated as new failures appear. "Your pass rate is a **product decision**" — 100% is not required. Store metrics **alongside test and prompt versions**. — [Hamel Husain, "Your AI Product Needs Evals"](https://hamel.dev/blog/posts/evals/) `[primary, practitioner]`
- Practitioner guidance converges on: cheap deterministic checks on every PR, expensive LLM-judge suites when prompt files change, "only run the test cases most likely to be affected by the specific change — **then run the full suite before merge**," and fixing determinism (seed, temperature, state isolation) before comparing runs. — [fast.io, prompt regression testing](https://fast.io/resources/ai-agent-prompt-regression-testing/); [helpmetest.com](https://helpmetest.com/blog/prompt-regression-testing-version-control/) `[practitioner-blog]`
- Prompt-versioning guidance: a CI job on every PR that fails when regression exceeds a threshold; **semantic versioning with a major bump for structural changes such as a new output schema**; the runtime should **log which prompt version served each request**; rollback should not require a code deploy; "treat any update in a prompt chain as a potential breaking change for downstream prompts." — [alexcloudstar](https://alexcloudstar.com/blog/prompts-as-code-versioning-testing-production-2026/); [tianpan.co](https://tianpan.co/blog/2026-04-20-prompt-versioning-llm-production); [respan.ai](https://www.respan.ai/articles/prompt-versioning) `[practitioner-blog — none authoritative]`
- **Behavioural testing without ground-truth labels** (CheckList, ACL 2020): *invariance tests* apply label-preserving perturbations and require the prediction not to change; *directional expectation tests* require the prediction to move in a specified direction. Their key property is that they "test behaviors that **do not rely on ground truth labels**, but rather on relationships between predictions after perturbations are applied." In a user study, NLP practitioners with CheckList "created twice as many tests, and found almost **three times as many bugs**." — [Ribeiro et al., "Beyond Accuracy: Behavioral Testing of NLP Models with CheckList", arXiv:2005.04118](https://arxiv.org/pdf/2005.04118) `[peer-reviewed, ACL 2020 best paper]`

**(b) Few-shot examples leaking into outputs**
- Practitioner report of the exact mechanism: "if the new tenant's question is phrased close enough to the example's input, the model often emits an answer that **lifts named entities directly from the example**." — [tianpan.co, "Tenancy Leaks Through Few-Shot Examples"](https://tianpan.co/blog/2026-05-13-tenancy-leaks-few-shot-examples-cross-customer-prompt-store) `[practitioner-blog — anecdotal]`
- Related failure: a team's dynamic few-shot selector retrieved the eight nearest labelled examples per input, drawn from the same file as the eval set, "so the model **copied the label**." — [tianpan.co, "The Eval Set Your Prompt Engineers Turned Into Production Few-Shots"](https://tianpan.co/blog/2026-06-03-the-eval-set-your-prompt-engineers-turned-into-production-few-shots) `[practitioner-blog]`; [related dev.to account](https://dev.to/ethanwritesai/our-few-shot-examples-came-from-the-eval-set-the-094-was-fiction-b78) `[practitioner-blog]`
- **Prompt leaking** as a documented adversarial category: a system prompt's few-shot examples can be extracted via untrusted input. — [Prompt Engineering Guide, Prompt Leaking](https://www.promptingguide.ai/prompts/adversarial-prompting/prompt-leaking) `[reference guide]`
- **The memorization literature does not cover this.** Verbatim memorization is defined over *training* data via greedy decoding — "if the L tokens match a substring in any training example, we say the L tokens are verbatim memorized" — and Stanford's own write-up warns this extractability metric "can create **illusions of memorization**." — [Carlini et al., "Extracting Training Data from Large Language Models", arXiv:2012.07805](https://arxiv.org/pdf/2012.07805); [Stanford AI Lab, "What is verbatim memorization?"](https://ai.stanford.edu/blog/verbatim-memorization) `[peer-reviewed / primary]`

**(c) Guardrails that catch well-formed wrong answers**
- Huyen's placement principle: guardrails "should be placed **whenever there is potential for failures**." — [Huyen, "Building A Generative AI Platform"](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- Her **output guardrail** taxonomy explicitly separates structural from semantic failure: empty responses; **malformatted** responses (regex/JSON/Python validators, constrained sampling tools); toxic responses; **hallucinated, factually inconsistent responses**; responses containing sensitive information; brand-risk responses; and "generally bad responses, often caught by AI judges." — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Retry policy and its cost:** basic retries handle many failures such as empty or malformatted output, but add latency and cost; she suggests **running calls in parallel** (e.g. sending the same query twice and picking the better response) to bound added latency. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **The latency-vs-risk trade:** "Most teams find that the **increased risks are more costly than the added latency**." — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **The metric name for this bug class:** the Constraint Tax paper's recommendation is that production systems "report **schema validity, answer accuracy, executable accuracy, and wrong-valid-schema rate separately**," and its summary of the phenomenon is "**The error is semantic, not structural.**" — [Jaideep Ray, "The Constraint Tax", arXiv:2605.26128](https://arxiv.org/abs/2605.26128) `[preprint, single-author, May 2026 — unreviewed]`
- **AI judges are themselves non-deterministic artefacts needing their own evaluation:** "While AI judges can be very useful, they aren't deterministic… **AI judges must be evaluated and iterated over time, just like all other AI applications.**" — [Huyen, "Common pitfalls"](https://huyenchip.com/2025/01/16/ai-engineering-pitfalls) `[primary]`

### Inferences
- **The 91% → 9% regression is the textbook Simpson's-paradox / slice-blindness failure, and the published countermeasure is per-slice reporting as a gate, not as a report.** The strata in this system are already named (clean barcode / clear cover / hostile barcode); the enforceable rule implied by the literature is that a prompt change must emit all three slice numbers and fail on *any* slice regression, since an aggregate that averaged a small hostile gain against a catastrophic cover loss could still have looked acceptable.
- **A prompt is global state in the precise sense that a shared mutable singleton is: every stratum reads the same object.** The practitioner guidance (version the prompt, log the version per request, treat a schema change as a major version, run the full suite before merge) is the standard mitigation for shared mutable state applied to prompts — and Huyen's "a framework can change its default prompt without notice" is the same hazard arriving from outside your repo.
- **The "example value copied onto 10 of 16 inputs" failure is a directional-expectation test waiting to be written, and it needs no ground truth.** CheckList's key property — tests that assert *relationships* between outputs rather than correctness against labels — gives the cheapest possible guard here: an assertion that the emitted ISBN is **not** equal to any literal appearing in the prompt template. That is a string comparison, costs nothing, and would have failed loudly on 10 of 16 cases. No peer-reviewed study was found establishing *how often* few-shot values leak, but the detector does not require knowing the rate.
- **The guardrail that was missing is a value-level, not a shape-level, one.** Huyen's taxonomy puts "malformatted" and "factually inconsistent" in separate rows for a reason: the pipeline had the first and not the second. An output can be perfect JSON, pass every schema check, and carry the demo ISBN.
- **"Wrong-valid-schema rate" is the single most useful metric name to adopt from this research**, because it is precisely the quantity that was 0% before the prompt change and (at least) 62% after it, and which no existing gate measured.

### Gaps
- **No peer-reviewed measurement of in-context (few-shot) example leakage rates was found.** The only evidence is practitioner blogs of unverified provenance (tianpan.co posts and a dev.to account). This should be reported as an *observed-in-practice* phenomenon with a known mitigation, not a quantified one. The training-data memorization literature is a different mechanism and should not be cited as support.
- **Huyen's exact wording on slice-based evaluation and Simpson's paradox could not be retrieved** — the *DMLS* chapter-6 body and the *AI Engineering* chapter-4 body are both behind the paywall, and the O'Reilly preview page returned HTTP 403. The section's existence and contents list are confirmed from O'Reilly's public TOC; the content is cited to secondary notes and a university lecture deck.
- No source found that quantifies **how much of a full regression suite you can safely skip** for a prompt-only change; the "run affected cases, then full suite before merge" rule is asserted by practitioner blogs without evidence.

## Key Question 3: Separating components that fail NOISILY from components that fail QUIETLY

### Takeaway
The field has no single canonical name for this split, but it is consistently described as the defining difference between traditional software and generative components: deterministic stages (decoders, retrievers, validators) raise errors, while generative stages emit fluent wrong answers that are textually indistinguishable from correct ones and leave every operational dashboard green. The published design response is to **fail closed** — deny the generative stage the opportunity to fill a gap left by a failed deterministic stage — and to **validate tool/stage outputs, not just inputs**.

### Cited Findings
- The core asymmetry, stated plainly: "A confidently wrong answer and a confidently correct one are often **textually indistinguishable**," and when it happens the usual signals look fine — "**HTTP 200 all the way down. Everyone's dashboard is green.**" — [boundev.ai, "Silent failures in production AI agents"](https://www.boundev.ai/blog/silent-failures-production-ai-agents); [latitude.so, "Preventing silent failures in production LLMs"](https://latitude.so/blog/preventing-silent-failures-in-production-llms) `[practitioner-blog]`
- **The strongest empirical datapoint found:** an arXiv analysis of WildChat conversations reports **78% of AI failures were invisible to users**, grouped into eight "invisible failure archetypes" including a "confidence trap" and a "silent mismatch." — [arXiv:2603.15423](https://arxiv.org/pdf/2603.15423) `[preprint — numbers not independently verified; cite with the hedge]`
- **The canonical mechanism is a failed deterministic stage whose failure is passed to the model as ordinary text**: the model "reads 'could not fetch order' or an empty payload, and reasons: the user wants an order status, I should provide one. So it produces a plausible-sounding status." — [reliability-dca, "Agent tool call fails silently"](https://reliability-dca.pages.dev/blog/agent-tool-call-fails-silently.html) `[practitioner-blog]`
- Recommended design responses across these sources: validate **tool outputs**, not only inputs; **fail closed** so the model cannot fill gaps when a deterministic stage cannot answer; verify **outcomes** rather than only that a call was made; route low-confidence cases to human review or a fallback path; and log `finish_reason` so truncated outputs (e.g. cut-off JSON) are caught rather than processed downstream. The stated goal is systems that fail "**loudly, safely, and recoverably**." — [boundev.ai](https://www.boundev.ai/blog/silent-failures-production-ai-agents); [latitude.so](https://latitude.so/blog/preventing-silent-failures-in-production-llms) `[practitioner-blog]`
- Huyen's corresponding structural advice: build **observability in from the beginning rather than adding it later**, and place guardrails "whenever there is potential for failures." — [Huyen, "Building A Generative AI Platform"](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Human-in-the-loop as the noisy-failure escape hatch:** transfer to a human on specific key phrases, when a sentiment model detects "the user is getting angry," or **after a set number of turns to avoid endless loops**. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Streaming defeats output guardrails:** in streaming mode "it's hard to evaluate partial responses," so unsafe content can reach the user before it can be blocked. — [ibid.](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- The entity-linking field's structural answer to the same problem: keep the ID lookup in a deterministic component. LLMAEL uses the LLM only to *enrich* the mention and hands the final lookup to a conventional entity-linking model, "**minimizing the risk of obtaining invalid entity IDs due to LLM hallucination**." — [LELA, arXiv:2601.05192](https://arxiv.org/html/2601.05192v1) (surveying the field) `[preprint]`

### Inferences
- **The book pipeline already has a near-ideal noisy component and is wasting it.** pyzbar either returns a decoded string or it does not; an ISBN check digit either validates or it does not; Open Library either resolves an ISBN or returns 404. Three loud failures. The quiet one is exactly one stage — the VLM — and the `is_book=true, identifier=null` response is the pipeline *converting a loud failure into a quiet one*: the VLM is reporting success on a question nobody can act on.
- **The 15% hostile-barcode stratum is a fail-closed violation.** The honest output for a hostile barcode is an abstention that the system can route (ask the user, queue for retry, request a better photo). `is_book=true` with no identifier is the generative stage filling a gap left by a failed deterministic stage — the precise mechanism the tool-call literature describes, with the barcode decoder in the role of the failed tool.
- **The architectural rule this supports:** every boundary where a deterministic stage hands off to the generative stage should carry an explicit "this stage failed" token that the generative stage is *forbidden* to overwrite, and every generative output should be converted back to a deterministic verdict (resolved ISBN / not resolved) before it is allowed to affect state. The ISBN hard gate is already this conversion; it just needs to be the *only* exit.
- A corollary for metrics: the pipeline needs a counter for **"VLM returned a well-formed response that produced no actionable identifier."** Today that is presumably indistinguishable in logs from a genuine non-book photo.

### Gaps
- **No peer-reviewed treatment of the noisy/quiet component split as an architectural principle was found.** The idea is asserted consistently across practitioner writing but I located no primary engineering source (no Google SRE-style chapter, no Huyen passage) that names and formalises it. The 78% figure comes from a single unreviewed preprint and should be hedged.
- No source found on **what fraction of fluent-wrong outputs an independent verifier catches in a vision pipeline specifically**.

## Key Question 4: Structured output / constrained decoding — current approaches, their cost, and whether it would have prevented the echoed example value

### Takeaway
**No — constrained decoding would not have prevented it, and the best evidence says it could have made the underlying problem worse.** Grammar/schema enforcement constrains *shape*, not *content*; the Constraint Tax paper's headline result is that hard schema decoding drove schema validity to 100% while answer accuracy *fell* and the **wrong-valid-schema rate rose from 49.5% to 88.9%** on small models. The echoed ISBN is a perfectly schema-valid string. The practical consensus is "reason free, constrain late": let the model answer unconstrained, then project into the schema.

### Cited Findings
- **The Constraint Tax (small models, directly relevant to a 7B-class local model):** across 15,000 generations on Qwen2.5-0.5B, Qwen2.5-1.5B and SmolLM2-1.7B, hard answer-only schema decoding moved **schema validity 61.5% → 100.0%**, **answer accuracy 19.7% → 11.0%**, and **wrong-valid-schema outputs 49.5% → 88.9%**. On a deterministic calendar tool-call task, Qwen2.5-1.5B scored **91.5% executable accuracy with prompt-only JSON vs 48.0% under the hard tool-call schema** — with **both modes at 100.0% schema-valid**. The paper's prescription is "**reason free, constrain late**" and reporting the four metrics separately. A 3B model still showed a direct-schema tax. — [Jaideep Ray, arXiv:2605.26128](https://arxiv.org/abs/2605.26128) `[preprint, single-author, unreviewed — the numbers are specific and on-point but have not been replicated]`
- **"Let Me Speak Freely?" (peer-reviewed, EMNLP 2024 Industry Track):** reports "a significant decline in LLMs' reasoning abilities under format restrictions" and that "**stricter format constraints generally lead to greater performance degradation in reasoning tasks**." The effect **reverses for classification** — "while stricter formats degrade reasoning performance, they enhance classification accuracy." The paper compares three restriction levels; the loosest (natural-language instruction to use a format, with no schema enforcement) holds up better and reduces sensitivity to prompt variation. It proposes **NL-to-Format**: answer in natural language first, then convert to the target format. — [Tam et al., arXiv:2408.02442 / EMNLP 2024](https://aclanthology.org/2024.emnlp-industry.91.pdf) `[peer-reviewed]`
- **Counter-evidence on the mechanism:** a separate preprint argues most of the loss comes from the *format-requesting prompt* rather than from token masking, that recent closed-weight models show near-zero degradation, and that extended thinking recovers most of the lost accuracy. — [arXiv:2604.03616](https://arxiv.org/pdf/2604.03616) `[preprint]`. A 2026 follow-up, "Capacity, Not Format," argues the cost depends on the model's spare capacity and reports that a delayed-structure ablation (reason freely, then format) recovers most lost accuracy. — [arXiv:2606.09410](https://arxiv.deeppaper.ai/papers/2606.09410v1) `[preprint]` **Sources conflict on whether the penalty is caused by the decoder mask or by the prompt; both camps agree the fix is the same (reason first, format after).**
- **Field order inside a constrained schema matters:** constrained decoding generates keys in schema order, so putting an answer field before a reasoning field forces the model to commit before it reasons; put reasoning fields first. — [memx.app](https://memx.app/blog/structured-outputs-accuracy-tax/) `[practitioner-blog — plausible heuristic, mechanism-consistent with the papers above]`
- **Huyen's placement of constrained sampling:** she lists "constrained sampling tools" as a remedy for **malformatted responses** specifically — one row in an output-guardrail taxonomy whose other rows (hallucination, factual inconsistency) are handled by different mechanisms. — [Huyen, "Building A Generative AI Platform"](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Where constrained decoding genuinely helps in an identification pipeline:** the entity-linking literature uses it to keep identifiers *inside a known set*. InsGenEL notes that "unconstrained generation frequently fails to yield precise entity identifiers, because of the notorious hallucination issue of LLMs"; AGNUS applies constrained decoding for context-sensitive disambiguation and returns the disambiguated entity. — [LELA survey, arXiv:2601.05192](https://arxiv.org/html/2601.05192v1) `[preprint]`

### Inferences
- **Constrained decoding is the wrong tool for the observed bug and the right tool for a different one.** The echoed example ISBN is a 13-digit string with a valid check digit; every grammar, JSON Schema, regex and function-call signature accepts it. What would have caught it is a *value* predicate (`emitted_isbn ∉ prompt_literals`), not a *type* predicate.
- **However, constrained decoding over a closed candidate set would be powerful here** — and that is the entity-linking pattern, not the JSON-schema pattern. If the cascade's upstream stages can produce a shortlist of candidate ISBNs (from a barcode partial read, a cover-embedding neighbourhood, or an Open Library title search), constraining the VLM to *choose among them* rather than *emit a free string* removes the invented-identifier failure mode entirely and converts a generative step into a classification step — which is exactly the regime where "Let Me Speak Freely?" says format restriction *helps*.
- **If structured output is kept on a 7B VLM, the schema should put the reading before the answer** (what text is visible on the cover / what digits are legible) and the identifier last, per both the field-order heuristic and the "reason free, constrain late" finding. A schema that asks for `isbn` first is asking a small model to commit before it has looked.
- **The Constraint Tax numbers are for ≤3B text models and should not be transferred to Qwen2.5-VL-7B as predictions** — but its *measurement protocol* (report validity, accuracy, executable accuracy and wrong-valid-schema separately) transfers without any such caveat and is cheap to adopt.

### Gaps
- **No measurement found of constrained-decoding penalties on vision-language models**, and none on 7B-class models specifically; all cited numbers are text-only and ≤3B (Constraint Tax) or closed-weight API models (the counter-evidence preprint).
- The Constraint Tax paper is a **single-author, unreviewed May 2026 preprint**; its striking numbers have no replication I could find. Report them as such.
- **Sources genuinely conflict** on whether the accuracy penalty is caused by the decoder constraint or by the formatting instruction in the prompt. I did not find a study that isolates this cleanly for open-weight models.
- No cost/latency figures found for grammar-constrained decoding overhead (tokens/sec penalty) on A10G-class hardware.

## Key Question 5: Evaluation architecture for a PIPELINE rather than a model

### Takeaway
The consistent recommendation is **dual-track**: end-to-end metrics plus per-component metrics, because only per-component metrics identify which stage caused a failure, and only end-to-end metrics tell you whether the system works. Three specific defences against the single-stratum blindness described in the incident recur: **slice-based evaluation** (report per-slice, not aggregate), **behavioural/invariance tests that need no labels**, and **validating the evaluator itself** against human judgement. Huyen's own framing is "evaluation-driven development" — decide how the application will be judged *before* building it — and a daily human review of 30–1,000 examples.

### Cited Findings
- **Dual-track:** third-party notes on *AI Engineering* ch. 4 describe a "dual-track evaluation approach" combining end-to-end system evaluation with component-level assessment, which lets teams identify bottlenecks and failure points, understand how components interact, make targeted improvements, and maintain reliability during updates. — [Alex Strick van Linschoten, ch. 4 notes](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html) `[secondary]`
- **Evaluation-driven development** is defined in those notes as "the process of understanding how an application will be evaluated **before investing time, money, and resources** building something with it," and the chapter is structured as evaluation criteria → model selection → building evaluation pipelines. — [ibid.](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html); [Michael Bassili's notes](https://bassi.li/articles/evaluating-ai-models) `[secondary]`
- **Evaluate the evaluation pipeline itself** (meta-evaluation): signal quality and reliability, **metric correlation and redundancy**, resource utilisation and efficiency, and integration with development workflows. — [Alex Strick van Linschoten, ch. 4 notes](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html) `[secondary]`
- **Four criteria pillars** per the same notes: domain-specific capability; generation capability (local and global factual consistency, hallucination detection); instruction following with **custom benchmarks tailored to your application**; and cost and latency framed as **Pareto optimisation**. "Metric Alignment" = mapping technical metrics to business outcomes. — [ibid.](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html) `[secondary]`
- **Evaluate at every step:** "Evaluation is necessary at every step of the development process," and observability should be built in "from the beginning rather than added later." — [Huyen, "Building A Generative AI Platform"](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`
- **Human evaluation is not optional, and has a concrete cadence.** The strongest teams have human experts review a subset of outputs **daily**, "which can be anywhere from **30 – 1000 examples**." Three stated purposes: (1) correlate human and AI judgments — "if human scores fall while AI scores rise, investigate the judges"; (2) learn how users actually use the application; (3) **detect behaviour changes that automated analysis may miss**. Annotation guidelines improve reliability and refine model instructions — "if a human has a hard time following the instructions, the model will, too." And: "staring at data for just 15 minutes usually gives me some insight that could save me hours of headaches," with Greg Brockman quoted that manual data inspection has "probably the highest value-to-prestige ratio of any activity in machine learning." — [Huyen, "Common pitfalls"](https://huyenchip.com/2025/01/16/ai-engineering-pitfalls) `[primary]`
- **Sample sizes:** ch. 4 notes cite OpenAI research that **100–1,000 samples** are typically sufficient depending on required confidence level. — [Alex Strick van Linschoten, ch. 4 notes](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html) `[secondary]`
- **Data slicing** to detect biases, find performance variations, and avoid Simpson's paradox. — [ibid.](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html) `[secondary]`; corroborated by the DMLS ch. 6 section list (slice-based evaluation, perturbation tests, invariance tests, calibration) — [O'Reilly TOC](https://www.oreilly.com/library/view/designing-machine-learning/9781098107956/ch06.html) `[primary — structure only]`
- **Error analysis before metrics (Husain):** start by reading real traces rather than picking a metric; do not write a rubric before looking at data; the useful criteria *emerge* from recurring patterns found in real examples; get a domain expert doing the error analysis as fast as possible; Excel is an acceptable starting tool. — [Hamel Husain, "Automating Error Analysis"](https://hamel.dev/notes/llm/ai-product-engineering/evals-error-analysis.html) and [Arize interview](https://arize.com/blog/rise-of-the-ai-engineer-why-ai-evals-fail-before-the-evaluation-begins/) `[primary / secondary interview]`
- **Judge validation specifics (Husain):** align the judge in batches of **25–50 examples at a time**; start with **binary good/bad labels** rather than scores; raw agreement misleads on imbalanced data, so **measure precision and recall separately**; use the most powerful model you can afford for critiquing and keep a mini eval system tracking the judge's own quality. Also: "You must remove all friction from the process of looking at data," and "You can never stop looking at data." — [Hamel Husain, "Your AI Product Needs Evals"](https://hamel.dev/blog/posts/evals/) `[primary, practitioner]`
- **Label-free behavioural tests** are the cheapest per-stage regression gate available (invariance + directional expectation; 2× tests and ~3× bugs found in the CheckList user study). — [Ribeiro et al., arXiv:2005.04118](https://arxiv.org/pdf/2005.04118) `[peer-reviewed]`
- **Per-stage metrics for a cascade specifically** are risk/coverage: selective risk = loss on answered items ÷ coverage; evaluate with **AURC** and **Target Calibration Error** rather than a single accuracy number. — [arXiv:2509.01455](https://arxiv.org/html/2509.01455v2), [arXiv:2603.21172](https://arxiv.org/pdf/2603.21172v1) `[preprint]`

### Inferences
- **The minimum viable pipeline eval for this system is a 3×N matrix, not a number**: rows = strata (clean barcode / clear cover / hostile barcode / non-book), columns = per-stage outcome (decoded / escalated / VLM-answered / abstained / gate-passed / gate-rejected / wrong-valid-schema). The 95/91/15 figures are three cells of that matrix; the incident happened because only one cell was read.
- **A per-stage metric that ends at the ISBN gate is the one that matters commercially**, because the gate is the only place the pipeline's output becomes real. End-to-end metric = "fraction of photographs that produce a correct catalogued book"; per-stage metrics exist to attribute the failures. Both are needed, per the dual-track framing.
- **Husain's 25–50-example judge alignment batches and Huyen's 30–1,000 daily human reviews are both affordable at hobby scale** — the eval corpus for this system is photographs the owner already has, and 16 inputs is clearly below the 100–1,000 range the sources treat as the floor for a confident conclusion. The "small gain" observed on the weak stratum was almost certainly within noise at that sample size.
- **Meta-evaluation ("metric correlation and redundancy") has a concrete application here:** if the ISBN gate's pass rate and the VLM's self-reported confidence are highly correlated, one of them is redundant; if they are uncorrelated, the self-reported confidence is not a usable routing signal and a different scorer is needed.
- **Evaluation-driven development inverts the incident's order of operations.** The prompt change was made, then measured on the stratum it targeted. The cited discipline is: define the slice table first, make the change, re-run every slice, and treat any slice regression as a failing build.

### Gaps
- **Huyen's book text on pipeline evaluation is not publicly quotable**; the dual-track framing, the four pillars, and the meta-evaluation list all come from one blogger's notes and should be attributed as such ("as summarised by…"), not quoted as Huyen's words.
- No source found giving **per-stage metric definitions for vision identification cascades** specifically; the risk-coverage framework has to be transferred from text QA.
- No source found on **how to weight a regression gate when strata have very different traffic volumes** (e.g. whether a 2-point drop on a 70%-of-traffic slice should block a 10-point gain on a 5% slice).

## Key Question 6: Self-verification against an independent source (ISBN resolves against Open Library; resolved title compared with the title read off the cover)

### Takeaway
The pattern has two names depending on which half you emphasise: in the reasoning literature it is **self-verification with a verifier / meta-verifier** (AutoMix), and in the entity-resolution literature it is **candidate generation + re-ranking**, where the LLM is deliberately denied the ability to emit an identifier and only allowed to *choose* one. The critical published caveat is that self-verification is **noisy** and should not be trusted directly — AutoMix wraps it in a non-LLM meta-verifier for exactly this reason — and that verification is reliable where it is genuinely easier than generation (true for many reasoning tasks, **often not for factual recall**). The project's design — verify the ISBN against an external registry *and* cross-check the returned title against the cover text — is a stronger instance than most of the literature, because the second check is against an independent modality, not the model's own opinion.

### Cited Findings
- **AutoMix's structure is this pattern, named:** the small model answers, then "the answer is self-verified by the SLM, yielding a **noisy verification score**. The Meta-Verifier subsequently assesses verifier's results." The meta-verifier emits "a binary signal, where 1 means the verifier's output can be trusted," and deliberately "employs a **non-LLM setup for meta-verification to avoid escalating the self-correction problems seen with LLMs**." Its three routing states are **Simple / Complex / Unsolvable**. Reported: >50% cost reduction at comparable performance; code is three steps — inference, self-verification, meta-verification. — [AutoMix, arXiv:2310.12963](https://arxiv.org/abs/2310.12963); [github.com/automix-llm/automix](https://github.com/automix-llm/automix) `[preprint + code]`
- **Verification asymmetry — and where it fails.** A 2024 paper on verifier-based judges argues the approach works best "when verifying an answer is notably easier than producing it," framing this as **verification asymmetry**, and states it holds across **many reasoning and procedural tasks but often not for factual recall**. — summarised in search of [arXiv:2407.16831 / "Networks of Networks"](https://ar5iv.labs.arxiv.org/html/2407.16831) `[preprint — I did not fetch the full paper; treat the attribution as approximate]`
- **Verifier reliability varies systematically:** problem difficulty, generator strength and verifier strength all affect how reliably a verifier can judge; **errors from weak generators are easier to detect than errors from strong ones**, and easy problems let verifiers certify correct answers more reliably. — ["Variation in Verification", arXiv:2509.17995](https://arxiv.org/html/2509.17995v1) `[preprint]`
- **A weak verifier on a strong generator can hurt; a strong verifier on a weak generator helps a lot.** — [buildml.substack.com, "The Verification Problem"](https://buildml.substack.com/p/the-verification-problem-why-your) `[practitioner-blog]`
- **Entity linking is the closest structural analogue and it is a two-stage architecture by default:** "the most widely adopted procedure to tackle EL is a two-stage architecture… which divides EL into two sequential phases: **candidate generation and entity re-ranking**." LELA generates an initial candidate set, re-ranks pointwise to top-k, and passes those to the LLM "for final candidate selection through reasoning over the context and entity descriptions." — [LELA, arXiv:2601.05192](https://arxiv.org/html/2601.05192v1) `[preprint]`
- **The LLM is kept away from the ID:** LLMAEL uses the LLM to enrich the mention and hands the final lookup to a conventional EL model, "minimizing the risk of obtaining invalid entity IDs due to LLM hallucination." — [ibid.](https://arxiv.org/html/2601.05192v1) `[preprint]`
- **Consensus/consistency as a verification signal:** OneNet adds an "entity consensus judger [that] employs a unique consistency algorithm to alleviate the hallucination in the entity linking reasoning." — [OneNet, arXiv:2410.07549](https://arxiv.org/html/2410.07549v1) `[preprint]`
- **Known failure modes of candidate-set verification:** candidate sets get large — "entity linking typically recalls a substantial volume of candidate entities and their corresponding descriptions, often exceeding 10,000 tokens, which surpasses the capacity of most LLMs" — and **candidate order matters**: "these models are highly sensitive to the order in which candidate entities are presented." — [LELA, arXiv:2601.05192](https://arxiv.org/html/2601.05192v1) `[preprint]`
- **Huyen's corresponding guardrail row:** "hallucinated, factually inconsistent responses" is a named output-guardrail category distinct from malformatting, and her criteria pillars include "**local and global factual consistency**" with hallucination-detection approaches. — [Huyen, "Building A Generative AI Platform"](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`; [ch. 4 notes](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html) `[secondary]`
- **Cost framing:** Huyen notes retries can be run **in parallel** (e.g. the same query twice, pick the better) to bound added latency, and that "most teams find that the increased risks are more costly than the added latency." — [Huyen, "Building A Generative AI Platform"](https://huyenchip.com/2024/07/25/genai-platform.html) `[primary]`

### Inferences
- **The ISBN hard gate is already a non-LLM meta-verifier in AutoMix's sense, and that is its strongest architectural property.** Open Library resolution is deterministic, external, free, and cannot be talked into agreeing — which is precisely why AutoMix insists the meta-verifier not be an LLM.
- **But an ISBN gate alone is insufficient against the specific bug observed**, because the prompt's own example ISBN is a *real* ISBN and resolves. The title cross-check is the component that closes this hole: a fuzzy match between the registry title and the OCR/VLM-read cover text turns "the identifier is syntactically and registrably valid" into "the identifier describes *this* book." This is the single highest-value verification in the system and it is independent of the prompt.
- **The failure the title cross-check catches is also the failure a cover-embedding tier would introduce** (near-miss editions), so the cross-check pays for itself twice: it guards the existing prompt-leak class and pre-emptively guards the planned embedding tier's characteristic error.
- **The entity-linking pattern suggests a concrete restructure within budget:** replace "VLM emits an ISBN" with "VLM reads title/author/publisher text from the cover → Open Library search returns k candidates → compare, pick or abstain." This moves the generative stage into the regime where format restriction *helps* (classification, per "Let Me Speak Freely?"), removes invented identifiers structurally (per LLMAEL), and makes abstention natural (empty candidate set → abstain, rather than `is_book=true`). Watch the two documented pitfalls: candidate-set size and candidate *order* sensitivity.
- **The "verification asymmetry often does not hold for factual recall" caveat is the one to take seriously** — but it applies to a model verifying *its own* recall. Here verification is against an external registry, so the asymmetry is restored by construction: reading 13 digits and querying an API is categorically easier than knowing the book.
- **The verifier-strength finding argues this system is in a favourable regime:** a weak generator (7B VLM) paired with a strong, deterministic verifier (Open Library) is the configuration the literature says helps most; the weak-verifier-on-strong-generator failure mode does not apply.

### Gaps
- **No established name in the literature for "verify a generated identifier against an authoritative external registry and cross-check an attribute."** The closest named patterns are *self-verification + meta-verification* (AutoMix), *candidate generation and re-ranking* (entity linking), and *grounding/factual-consistency checking* (Huyen's guardrail taxonomy). The report should say the pattern is assembled from these rather than claim a canonical name.
- **No effectiveness figures found for external-registry verification specifically** — i.e. what fraction of fluent-wrong identifications an authoritative lookup catches. All quantified verification results in the sources are model-verifier results on reasoning benchmarks.
- The "verification asymmetry" claim and its factual-recall caveat come from a search summary of arXiv:2407.16831 that I did **not** fetch in full; the attribution should be checked before quoting.
- No source found on **threshold selection for fuzzy title matching** between a registry record and OCR'd cover text.

## Cross-Cutting Note for the Report Writer: the five cheapest implementable patterns the sources support

Ordered by cost, all sourced above, all within a $50/month constraint:

1. **A per-slice regression gate** that re-runs all strata on any prompt change and fails on any slice regression — the published countermeasure to Simpson's-paradox blindness ([DMLS ch.6 section list](https://www.oreilly.com/library/view/designing-machine-learning/9781098107956/ch06.html); [ch.4 notes](https://alexstrick.com/posts/2025-01-22-notes-on-ai-engineering-chip-huyen-chapter-4.html)). Cost: zero beyond compute already spent.
2. **A label-free invariance assertion that the emitted identifier is not a literal from the prompt template** — CheckList-style, needs no ground truth ([Ribeiro et al.](https://arxiv.org/pdf/2005.04118)). Cost: a string comparison. Would have caught 10 of 16.
3. **Report `wrong-valid-schema rate` as a first-class metric alongside validity and accuracy** ([Constraint Tax](https://arxiv.org/abs/2605.26128)). Cost: a counter.
4. **Fail closed at the deterministic→generative boundary**: forbid `is_book=true` with no identifier; make abstention a first-class third outcome ([AutoMix's *Unsolvable* state](https://arxiv.org/abs/2310.12963); [fail-closed guidance](https://www.boundev.ai/blog/silent-failures-production-ai-agents)). Cost: a schema change and a routing branch.
5. **Title cross-check against the Open Library record** as the second half of the verification, then — only if budget allows — restructure the VLM step from *emit an ISBN* to *choose among retrieved candidates* ([entity-linking two-stage architecture](https://arxiv.org/html/2601.05192v1)). Cost: one extra API call per identification.

**Sources the writer should treat with caution:** all `tianpan.co` posts (high-volume blog, unverifiable claims, used here only for framing), `arXiv:2603.15423` (the 78% invisible-failures figure, unreplicated), and `arXiv:2605.26128` (single-author, unreviewed, though its numbers are the most on-point in this entire set).

# Issue #285: Platform Discovery Search Sectioning

## Summary
Implement the US-1.5.3 platform-wide discovery experience de-scoped from Issue #115: search results split into "Your Collection" vs "On the Platform" sections, with multi-source results (marketplace listings, partner inventory, other users' public-bookshelf placements) and contextual source labels.

## User Stories
- US-1.5.3 — Platform-Wide Discovery Search (de-scoped from #115 at epic kickoff 2026-07-23; the one shipped AC — platform-wide visibility filtering on book results — stays validated under #115/US-1.5.1)

## Goal
A user searching the platform sees their own books separated from discoverable platform inventory, each result labelled by source (own shelf, marketplace, partner, public shelf).

- Sources: marketplace listings, partner inventory, other users' public bookshelves; contextual labels per source.
- Elm `Page.Search`: sectioned rendering; coexists with the #217 people-search section.
- Related dead code: see #286 (`Books.search_platform/2` is currently unwired and does not filter by visibility — resolve there or absorb here, but not both).

### Phases 1+2 evidence (elixir/protobuf specialist)
- **Phase 1 — Contract:** `proto/stacks/api/v1/book_responses.proto` — additive `SearchResponse.collection` (field 4) + `platform_hits` (field 5), each `repeated SearchHit`; new `SearchHit {book=1, source=2, owner_handle=3, price=4}`; `results` (field 3) retained for backward compat. `buf lint` exit 0. `mix proto.sync --check` → "All generated files are up to date." `scripts/gen-elm-proto.sh --check` → "up to date" (generated Elm carries `SearchHit`/`collection`/`platformHits` with `D.oneOf [..., D.succeed []]` back-compat fallbacks). Full `elm-test` → **1032 passed / 0 failed** (was 1031 at baseline; +1 from a concurrent frontend agent's `BookDetailProgramTest.elm`, not this change — this change adds no Elm tests, only additive decoders).
- **Phase 2 — Backend:** `Shelving.search_collection/3` (own active-placement title matches, distinct, `plainto_tsquery` bound param, no sanitiser), `Shelving.looking_for_home_labels/1` (LFH + `listing_status:"active"` marketplace-exception → owner handle), `Marketplace.active_listing_labels/1` (active listing → seller handle + `format_price/2`), `ProtoJSON.search_hit/2`, `SearchController.index` assembly (collection + platform_hits + `results` retained; collection de-duplicated out of platform_hits; "listed" precedence over "looking_for_home"). Scoped tests: **234 tests, 0 failures** (shelving + marketplace + search_controller + proto_json). `mix format --check-formatted` clean; `mix credo --strict` (4 lib files) — "found no issues".
- **GDPR lens (verdict: PASS):** No new persisted data — all three helpers are read-only queries; the proto `SearchHit` is a response type, not a table; no migration/schema/field added. Erasure (`GDPR.Deletion.delete_user_data/1`) and export (`GDPR.Export`) paths are **unchanged** — nothing new to reach. The only PII-adjacent field surfaced is `owner_handle`, which rides the **existing** public-handle exposure (already public via `/u/:handle`, people-search cards, blog author_handle) and is emitted **only** for discoverable-by-design provenance: active marketplace listings (US-7.2, intentionally public) and always-visible `looking_for_home` placements (the `Visibility.marketplace_exception?` rule). It is **never** emitted for ordinary/private placements — asserted by `search_controller_test.exs` ("another user's private library placement leaks no label or provenance": source="" and owner_handle="") and `shelving_test.exs` ("ignores active listing_status on a non-LFH bookshelf"). No event_log/audit/dbt write on the search path (pure read).

# Issue #285: Platform Discovery Search Sectioning

## Summary
Implement the US-1.5.3 platform-wide discovery experience de-scoped from Issue #115: search results split into "Your Collection" vs "On the Platform" sections, with multi-source results (marketplace listings, partner inventory, other users' public-bookshelf placements) and contextual source labels.

## User Stories
- US-1.5.3 — Platform-Wide Discovery Search (de-scoped from #115 at epic kickoff 2026-07-23; the one shipped AC — platform-wide visibility filtering on book results — stays validated under #115/US-1.5.1)

## Goal
A user searching the platform sees their own books separated from discoverable platform inventory, each result labelled by source (own shelf, marketplace, partner, public shelf).

- Does this issue combine unrelated concerns? No.

- Server: section search results by whether the viewer has an active placement ("Your Collection") vs platform-visible sources ("On the Platform"); placement/bookshelf-level platform-visibility scoping per US-1.5.3 §5 (join `op.bookshelf_placements`/`op.bookshelves`, respect the Audience/visibility ladder — coordinate with ADR-018/#209).
- Sources: marketplace listings, partner inventory, other users' public bookshelves; contextual labels per source.
- Elm `Page.Search`: sectioned rendering; coexists with the #217 people-search section.
- Related dead code: see #286 (`Books.search_platform/2` is currently unwired and does not filter by visibility — resolve there or absorb here, but not both).

- 2026-07-24 — **Reachability flag (LFH label):** the `looking_for_home` platform label ("Looking for a home on <handle>'s shelf") is **NOT independently reachable via any public API path**, so Phase-4 E2E asserts the **"listed"** variant instead (per the plan's "assert whichever label state IS reachable — do not fabricate"). Root cause: `Shelving.looking_for_home_labels/1` requires a `looking_for_home` placement whose `listing_status = "active"`, and the ONLY writer of that column is `Marketplace.activate_listing/2`, which simultaneously creates the active `Listing` row that `SearchController.discovery_labels/1` merges with **"listed" precedence** (`Map.merge(lfh, listed)`) — so activation always surfaces "listed", never a bare "looking_for_home". Seeds set `listing_mode`/`listing_price_cents` on LFH placements but never `listing_status`. The LFH label render remains covered at the Elm layer (`SearchProgramTest`). Follow-up (not in #285 scope): if a bare-LFH advert label is desired product-wise, it needs a distinct activation path that sets `listing_status:"active"` on an LFH placement without a competing marketplace `Listing` (or a precedence rule that surfaces LFH when the listing is absent) — flagged to `main`.

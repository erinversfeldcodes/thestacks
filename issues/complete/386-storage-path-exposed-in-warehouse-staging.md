# Issue #386: `stg_uploaded_images` exposes the R2 `storage_path` (and `user_id`) to the warehouse

> **Campaign assignment:** Wave 11 (launch gates) — `plans/staff-campaign-2026-07-30.md`. Tracked in the campaign state; completed as part of epic #321.


## Summary
`dbt/models/staging/stg_uploaded_images.sql` selects `storage_path` and `user_id`
straight from `op.uploaded_images` into the `wh` staging layer. `storage_path` is the
R2 object key for a user's uploaded image — a fetchable pointer to sensitive
external-personal data — and analytics have no use for it. Found by the `gdpr-review`
lens during #353 (the erasure fix for the same table). **Pre-existing, not introduced by
#353** — the model is `mix proto.sync`-generated from `stacks/common/v1/upload.proto`.

## User Stories
None directly — the GDPR data-minimisation / no-warehouse-leak invariant
(`docs/technical-architecture.md` GDPR section; the `retrieval_log.query` exclusion is
the established pattern).

## Goal
The warehouse staging layer carries the columns analytics needs about an uploaded image
(status, timestamps, book linkage) but **not** the raw storage key. A reader of the `wh`
schema cannot reconstruct a fetchable pointer to a user's image bytes.

## Scope Check
One dbt staging model + its proto/generation source + the `schema.yml`/`sources.yml`
column marking. No app code, no endpoints. Within a single issue.

## Wiring
`stg_uploaded_images` is a `materialized='view'` over `source('op','uploaded_images')`, so
it has no independent lifetime — #353's erasure (CASCADE FK + row delete) already
propagates through it, which is why this is data-minimisation (P2), not an erasure breach
(P0). The fix is to stop projecting `storage_path` (and reconsider `user_id`) at the
staging boundary.

## Feature-Completeness Pre-Check
n/a — invariant tightening, not a feature.

## Technical Requirements
1. The model is proto-generated (`-- Generated by mix proto.sync — DO NOT EDIT MANUALLY.`).
   The column set comes from the proto message + `proto/persisted.exs` staging projection —
   decide the mechanism: either a `persisted.exs` "exclude from staging" mark for
   `storage_path`, or the established source-declared-but-model-excluded pattern used for
   `retrieval_log.query`. Do **not** hand-edit the generated `.sql` (drift fails CI).
2. Keep `storage_path` **declared on the source** (`sources.yml`) with a
   personal/sensitive classification note, but **excluded from the `stg_` model** — mirroring
   how free-text is handled, so the column is documented, not silently dropped.
3. Decide whether `user_id` should remain in staging. UUIDs are generally permitted in `wh`
   for joins (the machinery uses UUIDs), so this is likely KEEP — but state the decision.
4. `mix proto.sync --check` green after regeneration; `just run just verify` green (dbt
   models compile, sources resolve).

## Reviewer Context
- The other staging models are the reference for what a personal column looks like when it
  is declared-but-excluded. `stg_retrieval_log` excludes `query` (free text) while the source
  still declares it — copy that shape.
- `storage_path` is not free-text but it is a pointer to sensitive bytes; treat it as
  sensitive for minimisation purposes.
- #353 (the erasure fix) is the sibling: it proved the same table's rows and R2 objects are
  now erased on request. This issue is purely about the warehouse projection.

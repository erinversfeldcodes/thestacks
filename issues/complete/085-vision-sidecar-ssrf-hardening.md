# Issue #085: Vision Sidecar SSRF Hardening

## Summary
Harden the vision sidecar's `image_url` download path against Server-Side Request Forgery (SSRF). The sidecar now accepts URLs for `/classify` and `/extract` endpoints — it must not fetch internal network resources or cloud metadata endpoints.

## User Stories
N/A — security hardening.

## Goal
The vision sidecar rejects any `image_url` that resolves to an internal, link-local, or loopback IP address. Industry-standard SSRF defenses are applied so that even if a code path ever passes user-influenced URLs to the sidecar, internal infrastructure remains protected.

## Scope Check
- 0 Elixir changes
- Python-only changes to `apps/vision/`
- ~100-150 LOC

## Wiring
- [x] This issue is implementation only. No new endpoints.

## Technical Requirements

### 1. Block RFC1918 / link-local / loopback ranges
Before fetching any `image_url`, resolve the hostname to an IP address and reject if it falls in:
- `127.0.0.0/8` (loopback)
- `10.0.0.0/8` (RFC1918 private)
- `172.16.0.0/12` (RFC1918 private)
- `192.168.0.0/16` (RFC1918 private)
- `169.254.0.0/16` (link-local / cloud metadata)
- `::1/128` (IPv6 loopback)
- `fc00::/7` (IPv6 unique local)
- `fe80::/10` (IPv6 link-local)
- `0.0.0.0/8` (unspecified)

### 2. DNS resolution check before fetch
Resolve the URL hostname via `socket.getaddrinfo()` before initiating the HTTP request. Verify ALL resolved IPs are safe (not just the first — DNS can return multiple records). Reject if any resolved IP is in a blocked range.

### 3. Prevent DNS rebinding
After resolving and validating the IP, pin the connection to the resolved IP rather than re-resolving during the HTTP request. This prevents a DNS rebinding attack where the first resolution returns a safe IP but a subsequent resolution (during the actual HTTP connection) returns an internal IP.

Implementation: use `httpx` (or `aiohttp` with a custom resolver) to connect directly to the resolved IP with the original hostname in the `Host` header.

### 4. Explore additional industry-standard defenses
Research and evaluate:
- **URL scheme restriction** — already done (Pydantic `HttpUrl` rejects non-HTTP)
- **Response size limit** — already done (10MB cap)
- **Timeout** — already done (10s)
- **Redirect following** — should we limit or disable redirects? An attacker could use an open redirect on an allowed domain to reach internal resources
- **Content-Type validation** — after download, verify the response is actually an image (check magic bytes, not just Content-Type header)
- **Network namespace isolation** — if running in Docker/Fly, can the sidecar's network be restricted to only reach R2 and the internet, not internal services?

### 5. Logging
Log blocked requests at WARNING level with the blocked URL, resolved IP, and the reason for blocking. Do not log the full URL in production if it could contain sensitive query parameters (presigned URLs have signatures).

## Reviewer Context
- The sidecar is HMAC-authenticated — only the core Elixir service can call it
- Currently `image_url` only comes from R2 presigned URLs generated by `Stacks.Storage`
- The risk is defense-in-depth: protecting against future code paths that might pass user-influenced URLs
- The sidecar runs on Fly.io which uses internal `.internal` hostnames for service-to-service communication

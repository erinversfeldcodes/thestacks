# US-10.2.1 — Set Bookshelf Visibility

## 1. User Story

> **As a** user, **I want to** control who can see each of my bookshelves **so that** I can share some reading lists while keeping others private.

> **Vocabulary note:** "Bookshelf" is the canonical name for a named virtual collection (library, antilibrary, wishlist, reading_pile, looking_for_home). The UI label "shelf" is shorthand only -- the schema (`op.bookshelves`), context (`Stacks.Shelving`), and routes (`/api/bookshelves/...`) all use "bookshelf".

On any bookshelf page, the user opens the bookshelf settings menu and chooses a visibility level:
- **Only me** -- bookshelf is not visible to anyone else (default for all bookshelves except `looking_for_home`).
- **Platform users** (`platform`, labelled "Members" in the control) -- any logged-in user can see the bookshelf and its contents. Explicitly **not** visible to a logged-out visitor.
- **Anyone with the link** (`public`) -- the top rung; visible without signing in.
- **Group** -- visible only to members of a specific group.
- **Specific people** -- visible only to a named list of users. Still future *from the user's side*: the grant endpoints exist (`POST`/`GET`/`DELETE /api/bookshelves/:bookshelf_id/grants`, `apps/core/lib/core_web/router.ex:271-273`) but there is no `Api` client function and no dropdown option, so no reader can reach it. Tracked as Issue #150 (visibility-grants-crud).

The bookshelf's visibility is bounded by the profile ceiling. If the profile is set to "Only me", bookshelf-level settings have no effect.

**Age-gating note:** age-gated books always require age verification before their detail overlays are accessible -- regardless of the bookshelf's visibility level.

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/settings/privacy`.
2. The page fetches the user's saved settings on init (`GET /api/settings/privacy`) and renders the "Shelf Visibility" section with per-shelf rows showing **their stored visibilities**, not defaults.
3. Each shelf shows a dropdown with the four rungs of the Audience ladder: "Only me" (`owner`), "Group" (`group`), "Members" (`platform`), "Anyone with the link" (`public`). Options above the profile ceiling render **disabled** (`shelfOptionExceedsCeiling`, `frontend/src/Page/Settings/Privacy.elm:746-747`, applied at `:760`), so the ceiling rule is visible on the control rather than only discoverable by being refused.
4. User selects visibility for a specific shelf.
5. User clicks "Save" next to that shelf row.
6. System sends shelf visibility update API call.
7. UI shows "Saved!" confirmation.

### Sad Paths
- **Exceeds profile ceiling**: The `Visibility.validate_visibility_ceiling/3` check prevents saving a shelf visibility less restrictive than the profile visibility. Returns error.
- **Save failure**: Elm model shows "Could not save. Please try again."

### Elm State Machine
- **Page module**: `Page.Settings.Privacy`
- **Model fields involved**: `shelfVisibilities : List ShelfVisibility`, `savingShelf : RemoteData Http.Error ()`
- **Msg flow**: `SetShelfVisibility shelfName value -> SaveShelfVisibility shelfName -> SaveShelfVisibilityCompleted (Ok/Err)`
- **RemoteData states**: NotAsked -> Loading -> Success / Failure

## 3. API Calls

### `GET /api/settings/privacy` (read, on page init)
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated` (`apps/core/lib/core_web/router.ex:255`)
- **Controller**: `StacksWeb.UserSettingsController.show_privacy/2` (`apps/core/lib/stacks_web/controllers/user_settings_controller.ex:129-143`)
- **Response (success)**: `{ profile_visibility: string, shelves: [{ name, visibility }] }` -- HTTP 200. Built from `Shelving.list_user_bookshelves/1`, so it reflects the bookshelves that actually exist for this user.
- **Client**: `Api.getPrivacySettings` (`frontend/src/Api.elm:3524-3538`)

### `PUT /api/bookshelves/:bookshelf_name/visibility` (write)
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated` (`router.ex:264`)
- **Controller**: `StacksWeb.BookshelfController.update_visibility/2`
- **Path param**: the bookshelf **name** (`library`, `antilibrary`, `wishlist`, `reading_pile`, `looking_for_home`), not a UUID -- the client only ever holds the name (`Api.updateShelfVisibility`, `frontend/src/Api.elm:3290-3294`).
- **Request body**: `{ visibility: "owner" | "group" | "platform" | "public", visibility_group_id?: uuid }`
- **Response (success)**: Updated bookshelf -- HTTP 200
- **Response (error)**: Changeset errors or ceiling violation -- HTTP 422. The ceiling violation is the one failure on this form a reader can act on, so it is reported distinctly rather than with the generic "could not save" copy (`Privacy.elm:790-799`, rendered by `viewFeedback` at `:801`).

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` -> `AuthPipeline` (`:authenticated` scope) -> controller action
- **Visibility checks**: At read time, `Stacks.Visibility.resolve_visibility/2` enforces:
  1. **Profile ceiling**: If `profile_visibility == "owner"`, all content is hidden from non-owners.
  2. **Block check**: Bidirectional via `Social.blocked?/2`.
  3. **Age gate**: Checked via `check_age_gate/2` for resources with `visibility_tier: "age_gated"`.
  4. **Resource visibility**: The shelf's `visibility` field is checked. `"owner"` means only the resource owner can see it; `"platform"` is open to all authenticated users; `"group"` checks group membership.
- **Age gate**: Independent of visibility -- always applies to age-gated books.
- **Ownership checks**: Only the shelf owner can change visibility.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.SettingsPrivacy`
- **URL**: `/settings/privacy`
- **Public or authenticated**: Authenticated

### Init
- **`initPage` branch**: `Main.elm:1237` (`SettingsPrivacy`) calls `Privacy.initWithToken maybeToken consentSeed` (`frontend/src/Page/Settings/Privacy.elm:167`, wired at `Main.elm:1253`). The bare `init` (`Privacy.elm:141`) is retained for tests and flows that don't need the network.
- **API calls on init**: when authenticated, `Cmd.batch [ Api.getPrivacySettings token GotPrivacySettings, Api.listBlockedUsers token 1 GotBlockedUsers ]` (`Privacy.elm:176-179`). With no token, no request is made and the defaults stand.
- **Initial model state**: `shelfVisibilities = defaultShelves` (`Privacy.elm:113-120`) -- the five named bookshelves, each provisionally "platform". These are **placeholders for one paint**, not the rendered answer.
- **Hydration**: `GotPrivacySettings (Ok settings)` (`Privacy.elm:70`, handled at `:342-351`) replaces `profileVisibility` with the stored value and sets `shelfVisibilities = seedShelves settings.shelves`. `seedShelves` (`Privacy.elm:127-138`) overlays the persisted visibilities onto the fixed set of named shelves, preserving each shelf's human label and its ordering; a shelf the user has never customised keeps its default. The server is the authority on the *value*, the client on the *label and order* -- which is why this is an overlay and not a wholesale replacement.
- **On hydration failure**: `GotPrivacySettings (Err err)` keeps the defaults on screen and the user can still save (`Privacy.elm:353-359`); a 401 returns `SessionExpired` to Main rather than a page-local error (US-14.3.2).

### Update cycle
- **Msg**: `SetShelfVisibility shelfName value` -- updates the local shelf visibility for the named shelf, resets save state.
- **Model change**: Updates the matching `ShelfVisibility` record in the list.
- **Cmd**: None (local state only)

- **Msg**: `SaveShelfVisibility shelfName` -- triggers API call.
- **Model change**: `savingShelf = Loading`
- **Cmd**: `Api.updateShelfVisibility shelfName vis token SaveShelfVisibilityCompleted`

- **Msg**: `SaveShelfVisibilityCompleted (Ok _)` -- `savingShelf = Success ()`
- **Msg**: `SaveShelfVisibilityCompleted (Err err)` -- `savingShelf = Failure err`

### View
- **Key elements** (`Privacy.elm:491-497`, rows by `viewShelfRow` at `:758-786`):
  - Section title: "Shelf Visibility"
  - Description: "Override visibility per shelf. Each shelf's visibility is capped by your profile visibility (the ceiling rule)."
  - Per-shelf rows with label, a four-option select (Only me / Group / Members / Anyone with the link) whose above-ceiling options are `disabled`, and a "Save" button.
  - `viewFeedback` (`:801-802`) renders "Visibility updated." on success and a ceiling-specific message on 422.
  - The consent controls are folded into this same page (#318 TR-4) — moving where they render did not change the save path; they remain `Page.Settings.Consent`.

## 13. Operational Metrics

- **Shelf visibility change count**: Total shelf visibility updates, segmented by shelf name (library, antilibrary, wishlist, reading_pile, looking_for_home) and target visibility level (owner, group, platform).
- **Ceiling violation rejection count**: Number of times `Visibility.validate_visibility_ceiling/3` rejects a shelf visibility change for exceeding the profile ceiling. Indicates users attempting visibility levels their profile does not permit.
- **Visibility change events**: No dedicated event is emitted for individual shelf visibility changes currently. Bulk changes are tracked via `VisibilityRecapJob` when the profile ceiling tightens (see US-10.1.1).

---

## 14. Performance & Usability Metrics

- **Shelf visibility save latency**: Round-trip time for the shelf visibility update API call. This is a single-row UPDATE on `op.bookshelves` -- expected sub-10ms at the database level.
- **Visibility resolution latency for shelves**: Time for `Visibility.can_view?/2` on shelf resources. This is called on every shelf access and involves profile ceiling check, block check, and resource visibility check.
- **Settings page load time**: Time to first *correct* paint of `/settings/privacy`. Two requests fire on init (`GET /api/settings/privacy` and the blocked-users list), so this is a hydrated render, not a static one. The number that matters is not the render but the gap between the placeholder paint (five rows reading "platform") and the hydrated one: while that gap is open the page is showing a value the user did not choose. `show_privacy/2` is a single `list_user_bookshelves/1` read, so the gap should be one round-trip.
- **Stale-default exposure**: how often a user sees the defaults because hydration *failed*. The failure branch deliberately keeps the defaults and stays saveable (`Privacy.elm:353-359`) rather than blanking the section — which means a user could save a "platform" they never picked over a stored "owner". Worth an error count on `GET /api/settings/privacy`; not currently instrumented.

## 15. Cost Tracking

- All shelf visibility operations are low-cost DB reads and writes only -- single-row UPDATE on `op.bookshelves`.
- **Neon**: Minimal compute cost per change. The indirect cost is in `Visibility.resolve_visibility/2` which runs the shelf visibility check on every shelf content access (scales with platform read traffic, not write frequency).
- No external service calls, no storage operations, no email notifications.

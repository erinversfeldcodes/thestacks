# US-14.3.2 — Session Expiry and Token Refresh

## 1. User Story

> **As a** user whose session has expired, **I want to** be gracefully returned to the sign-in page **so that** I can re-authenticate without losing context about where I was.

**Acceptance criteria:**
- Access tokens expire after 24 hours
- Refresh tokens are valid for 7 days and can silently renew access tokens
- Expired sessions result in a redirect to the sign-in page, not an error screen
- Re-authentication redirects the user to the AntiLibrary

---

## 2. UI Interaction Flow

### Current Implementation Status: NOT IMPLEMENTED

**What exists today:**
- Guardian issues JWT tokens with a TTL configured in `config.exs` (the `ttl` setting in `:guardian` config).
- The `AuthPipeline` plug verifies tokens on every authenticated request. If the token is expired or invalid, `AuthErrorHandler` returns a 401 JSON response.
- The Elm frontend does NOT currently handle 401 responses globally. Each API call handles its own error via `RemoteData.Failure`, which shows contextual error messages but does NOT redirect to the login page.
- There is NO refresh token mechanism implemented. Guardian is configured for single-token auth only.
- There is NO global 401 interceptor in the Elm app.
- Auth data persists in localStorage indefinitely until the user explicitly signs out.

### What SHOULD Happen (per spec)
1. JWT access token expires after 24 hours.
2. If a refresh token exists and is valid (7-day window), the system silently obtains a new access token without user intervention. The user sees nothing.
3. If both tokens have expired, the next API request returns 401.
4. The frontend detects the 401 globally and redirects to `/login`.
5. After re-authentication, the user is returned to `/antilibrary`.

### Sad Paths (future)
- **Silent refresh fails**: Redirect to login page. No error message — just the sign-in form.
- **Stale localStorage token**: API returns 401 on first request after page load. Frontend should clear auth state and redirect.

### Elm State Machine (future)
- **Missing component**: A global HTTP error handler that intercepts 401 responses across all API calls and dispatches a logout/redirect action in Main.elm.
- **Missing component**: A refresh token flow — either a periodic timer that refreshes before expiry, or an on-error retry that attempts refresh before redirecting.

## 3. API Calls

### Current State
- No refresh token endpoint exists.
- `GET /api/auth/me` (authenticated) can be used to verify token validity but is not called automatically.

### Future (per spec)
- `POST /api/auth/refresh` — accept a refresh token, return a new access token. Not yet implemented.

## 4. Auth & Middleware Guards

- **Current plugs**: `AuthPipeline` calls `Guardian.Plug.VerifyHeader` (scheme: "Bearer"), `Guardian.Plug.EnsureAuthenticated`, `Guardian.Plug.LoadResource` (allow_blank: false), and `RequireConfirmedEmail`.
- **On expired token**: `Guardian.Plug.EnsureAuthenticated` fails, delegates to `AuthErrorHandler` which returns `{ "error": "unauthenticated" }` with HTTP 401.
- **Missing**: Server-side refresh token support, token rotation, refresh token storage.

## 12. Elm Frontend State Machine (Detail)

### Current Behaviour
- **Route variant**: N/A — no dedicated route for session expiry
- **Token handling**: Token is loaded from localStorage flags on app init. If present and valid, user is authenticated. If expired, API calls fail with 401 but the frontend does not redirect — individual pages show their own error states.
- **No global 401 handler**: Each page's `RemoteData.Failure` branch shows a contextual error. The user must manually navigate to `/login` and re-authenticate.

### Required Implementation (per spec)
1. Add a global response handler in Main.elm that pattern-matches on `Http.BadStatus 401` across all API response messages.
2. On 401: set `model.auth = Nothing`, call `clearAuth ()`, navigate to `/login`.
3. Implement refresh token flow: before clearing auth, attempt a refresh. If refresh succeeds, retry the failed request. If refresh fails, redirect to login.
4. Store return URL so that after re-authentication, the user can be sent back to where they were (spec says `/antilibrary`, but returning to the original page would be better UX).

## 13. Operational Metrics

> **Note:** Session expiry and token refresh are NOT YET IMPLEMENTED. The following metrics document what WOULD be tracked once the feature is built.

- **Token expiry rate**: Number of JWTs that expire naturally (24h TTL) vs those revoked explicitly via logout. Indicates session duration patterns.
- **Silent refresh success rate**: Ratio of successful refresh token exchanges (`POST /api/auth/refresh` returning 200) to total refresh attempts. Low rates indicate refresh token expiry or corruption.
- **Silent refresh failure rate**: Count of refresh attempts that fail (expired refresh token, invalid token, server error). Each failure results in a redirect to `/login`.
- **401 response rate**: Count of HTTP 401 responses from authenticated endpoints due to expired access tokens. High rates before refresh is implemented indicate users hitting expiry without graceful handling.
- **Re-authentication rate**: Number of users redirected to `/login` due to session expiry per day. Proxy for session length vs token TTL alignment.
- **Refresh token issuance count**: Number of refresh tokens issued alongside access tokens. Should equal login count.
- **Guardian token validation count**: Number of `Guardian.Plug.VerifyHeader` checks per hour. Indicates overall API traffic from authenticated users.

## 14. Performance & Usability Metrics

> **Note:** These metrics apply to the PLANNED implementation, not the current state.

- **Silent refresh latency**: p50/p95 for `POST /api/auth/refresh` round-trip. Must be fast enough to be imperceptible (<200ms target).
- **Session continuity rate**: Percentage of sessions that survive a token expiry via silent refresh (user never sees login page). Target: >95%.
- **Re-authentication friction**: Average time from redirect-to-login to successful re-authentication. Shorter is better — indicates user remembers credentials.
- **Return-to-page success rate**: If return URL is stored, percentage of re-authentications that successfully redirect to the original page vs falling back to `/antilibrary`.
- **Stale localStorage detection time**: Time between app load with expired token and first 401 response. Should trigger redirect immediately on first API call.
- **Session length distribution**: Histogram of session durations (time from login to either logout or token expiry). Informs whether 24h access / 7-day refresh TTLs are appropriate.

## 15. Cost Tracking

> **Note:** Costs for the PLANNED implementation.

- **Guardian JWT (refresh flow)**: Each silent refresh involves one token decode + one token encode. HMAC-SHA512 operations — negligible CPU (<2ms combined).
- **Database reads (if using GuardianDb)**: Refresh token validation may require a DB lookup in a `refresh_tokens` table. One SELECT per refresh — negligible Neon cost.
- **Database writes (token rotation)**: If refresh tokens are rotated on use, one UPDATE or INSERT+DELETE per refresh. Negligible cost.
- **No external service calls**: Token refresh is entirely internal.
- **Fly.io compute**: Refresh endpoint is lightweight — no Argon2, no email, no external API calls.
- **Total per-refresh cost**: ~$0.0000001 (negligible).

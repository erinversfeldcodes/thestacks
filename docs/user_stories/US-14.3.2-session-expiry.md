# US-14.3.2 — Session Expiry and Token Refresh

## 1. User Story

> **As a** user whose session has expired, **I want to** be gracefully returned to the sign-in page **so that** I can re-authenticate without losing context about where I was.

**Acceptance criteria:** _(reconciled to the shipped implementation — `feat/124-e2e-auth`)_
- Access tokens expire after **8 hours** (a deliberately stricter posture than the original 24h draft, paired with server-side revocation and an absolute cap).
- The session is **silently renewed** by rotating the access token (revoke old + mint new) up to a **7-day absolute lifetime cap**, after which re-authentication is required. (Implemented as stateless access-token rotation, not a separate refresh-token table.)
- Expired/revoked sessions result in a redirect to the sign-in page, not an error screen.
- Re-authentication redirects the user to the AntiLibrary.

## 2. UI Interaction Flow

### Implementation Status: SHIPPED

> **History:** this story was NAMED by #124 but de-scoped to #173 (a design pass was skipped, which is why it landed as the #178/#179/#180/#182 cascade rather than one design). It is delivered end-to-end and live-driven.

**What is built, with its code:**
- **Global 401 interceptor** — each authed page emits a `SessionExpired` OutMsg (`Api.isUnauthorized`, 401-only) routed through one `Main.handleSessionExpiry` (`frontend/src/Main.elm:1427`) → clear auth → `/login` with an in-voice notice; covers all authed pages plus a boot-time hook (#173, #178).
- **Silent renewal** — `POST /api/auth/refresh` (`apps/core/lib/core_web/router.ex:217` → `AuthController.refresh/2`, `apps/core/lib/stacks_web/controllers/auth_controller.ex:292`) driven by a proactive 7h timer in the SPA (`scheduleRenewal` `Main.elm:1663`, `RenewToken` `:1915`, `TokenRefreshed` `:1916`) against an 8h server TTL (`apps/core/config/config.exs:137`) (#173).
- **Absolute cap + reuse detection** — a signed `sst` claim enforces the 7-day cap across rotations (`config.exs:147`; checked at `auth_controller.ex:322`); `op.auth_token_families` (`apps/core/lib/stacks/accounts/auth_token_family.ex:23`) plus a fail-closed `verify_claims` gate (`apps/core/lib/stacks/accounts/guardian.ex:54-82`) revoke a whole family on replay of a rotated token (#179).
- **Rotation-race handling** — a 20s backend grace on the immediately-previous jti (`apps/core/lib/stacks/accounts.ex:1413`), cross-tab `storage`-event propagation, and a re-check-before-logout net (`Main.elm:1552`), so in-flight and multi-tab rotations don't spuriously log anyone out (#180).
- **Mid-compose data preservation** — a CreateListing draft survives a mid-compose expiry; the flag rides inside the `SessionExpired { draftSaved }` arrival (`frontend/src/Page/Login.elm:117`) (#182).

**Design note — one credential, not two.** The original draft assumed a separate refresh token in a `refresh_tokens` table. What shipped is **access-token rotation**: `/api/auth/refresh` sits behind the `:authenticated` pipeline, so the presented access token is both the credential and the input, and the pipeline rejects an expired one before the action runs. The 7-day cap that a refresh token would have carried is instead a signed `sst` claim carried forward across every rotation — which is why the cap cannot be reset by renewing, and why there is no second secret for the SPA to store.

### Happy Path (shipped)
1. The access token is minted with the `{8, :hours}` Guardian TTL (`apps/core/config/config.exs:137`).
2. Seven hours after any token receipt — stored-auth boot, fresh login, or a prior successful renewal — a proactive tick fires. `renewalDelayMs = 7 * 60 * 60 * 1000` (`frontend/src/Main.elm:1655-1656`) is a fixed delay rather than a decode of the JWT `exp`, because the token is opaque to the SPA; `scheduleRenewal` (`:1663-1666`) sleeps then dispatches `RenewToken`.
3. `RenewToken` calls `Api.refresh auth.token TokenRefreshed` (`Main.elm:3154`; client at `frontend/src/Api.elm:1099-1108`) → `POST /api/auth/refresh`.
4. `AuthController.refresh/2` (`apps/core/lib/stacks_web/controllers/auth_controller.ex:292`) rotates: revokes the presented token server-side, mints a fresh one carrying the `sst` session-start anchor and `family_id` forward, and returns login's `%{token, user}` shape.
5. `TokenRefreshed (Ok _)` adopts only the new token — identity, role, and location are deliberately taken from the current auth, not the response (`renewAuthToken`, `Main.elm:1645-1647`) — persists it via `saveAuth`, and re-arms `scheduleRenewal` (`Main.elm:3159-3170`). The user sees nothing: no navigation, no logout.
6. Past the 7-day absolute cap (`config.exs:147`, `session_absolute_cap: {7, :day}`), `refresh/2` revokes the token and answers `401 {"error": "session_expired"}` instead of minting (`auth_controller.ex:322-340`) — which the 401 interceptor turns into a trip to `/login`.
7. On any 401 from an authed page, the page emits a `SessionExpired` OutMsg and `Main.handleSessionExpiry` (`Main.elm:1427-1432`) clears auth and pushes `/login` with an in-voice notice. It is called from a single place per page rather than duplicated (~10 call sites in `update`, e.g. `Main.elm:2082`, `:2122`, `:2162`).

### Sad Paths
- **Silent renewal fails**: the consumed tick has its own handler, `handleSessionExpiryFromRenewal` (`Main.elm:1438-1443`), so a failed renewal does not silently drop the tick and leave the session un-renewed. The reader lands on the sign-in card, no error screen.
- **Stale localStorage token**: the boot-time hook exercises the same path — the first authed request 401s, the interceptor clears auth and redirects. `Api.isUnauthorized` is 401-only, so a 403 (e.g. unconfirmed email) is deliberately NOT treated as an expiry.
- **Rotation race / multi-tab**: a 20s backend grace window honours the immediately-previous jti (`Accounts.within_rotation_grace?/2`, `apps/core/lib/stacks/accounts.ex:1413-1415`), a sibling tab's `storage` event propagates the new token (`AuthChangedExternally`), and a re-check-before-logout net confirms there is really no session (`Main.elm:1552`) — so an in-flight or cross-tab rotation does not spuriously log anyone out.
- **Replay of a rotated token**: `Guardian.verify_claims/2` (`apps/core/lib/stacks/accounts/guardian.ex:54-82`) runs the reuse gate on every authed request and revokes the whole family on replay.
- **Mid-compose expiry**: a CreateListing draft is saved and the notice says so — `SessionExpired { draftSaved }` carries the flag inside the constructor so "was a draft saved" cannot be asked of a non-expiry arrival (`frontend/src/Page/Login.elm:117`, `handleSessionExpiryWithDraft` at `Main.elm:1449`).

### Elm State Machine
- **Renewal**: `RenewToken` → `Api.refresh` → `TokenRefreshed (Result Http.Error Api.AuthResponse)` (`Main.elm:1915-1916`). Success re-arms the timer; failure routes to `handleSessionExpiryFromRenewal`.
- **Expiry**: each authed page's `Api.isUnauthorized err` branch returns a `SessionExpired` OutMsg, which `Main` funnels into the one `handleSessionExpiry`.
- **Arrival at `/login`**: `Login.Arrival` is a six-constructor type (`Login.elm:115-121`) rather than a bag of notice booleans, so an expiry notice and (say) a confirmation-expired notice cannot render one under the other.

## 3. API Calls

### `POST /api/auth/refresh`
- **Auth**: Required (Bearer). Deliberately behind `:authenticated` (`apps/core/lib/core_web/router.ex:217`, in the scope at `:206-207`), so an expired, revoked, or absent token is rejected with 401 by the pipeline *before* the action runs — there is no separate refresh-token credential to validate.
- **Controller**: `StacksWeb.AuthController.refresh/2` (`apps/core/lib/stacks_web/controllers/auth_controller.ex:292`)
- **Request body**: none (`Http.emptyBody`) — the presented access token *is* the input.
- **Response (success)**: `{ token: string, user: {...} }` — HTTP 200. Mirrors login's shape so the SPA can swap tokens transparently.
- **Response (error)**: `{ "error": "session_expired" }` — HTTP 401, when the session is past its 7-day absolute cap measured from original issue. `{ "error": "unauthenticated" }` — HTTP 401 from `AuthErrorHandler` when the presented token is already expired/revoked.

Rotation is stateless-token rotation, not a second credential: the old token's `guardian_tokens` row is deleted so it can never be used again, and the new token carries the `sst` (session-start) anchor and `family_id` claims forward.

### `GET /api/auth/me`
- Still available (`router.ex:218`) for verifying token validity; it is not part of the renewal loop.

## 4. Auth & Middleware Guards

- **Plugs fired**: `AuthPipeline` calls `Guardian.Plug.VerifyHeader` (scheme: "Bearer"), `Guardian.Plug.EnsureAuthenticated`, `Guardian.Plug.LoadResource` (allow_blank: false), and `RequireConfirmedEmail`.
- **On expired token**: `Guardian.Plug.EnsureAuthenticated` fails, delegates to `AuthErrorHandler` which returns `{ "error": "unauthenticated" }` with HTTP 401.
- **Reuse-detection gate**: `Stacks.Accounts.Guardian.verify_claims/2` (`apps/core/lib/stacks/accounts/guardian.ex:54-82`) runs on **every** authed request when the token carries a `family_id`, calling `Accounts.check_token_family/3`. Ordering is load-bearing: Guardian's `verify_claims` hook runs *before* guardian_db's row-presence check, so a replayed already-rotated token (whose row was deleted on rotation) reaches this gate and burns the family, rather than 401-ing opaquely with no chance to revoke. The gate fails closed and never crashes the request.
- **Absolute cap**: enforced in `refresh/2` from the signed `sst` claim, not from a table scan — so the cap survives rotation and cannot be reset by renewing.

## 5. Database Interactions

Rotation is handled by signed claims rather than a `refresh_tokens` table — but two tables are written.

### Write: revoke the presented token (every rotation)
- **Table(s)**: `op.guardian_tokens`
- **Operation**: DELETE, via `Guardian.revoke/1` in `revoke_refresh_token/1` (`apps/core/lib/stacks_web/controllers/auth_controller.ex:380-389`). The old token stops working immediately rather than lingering until its TTL.
- **Degraded case**: a failed revoke is logged **and** counted (`[:stacks, :auth, :refresh, :revoke_failed]`) rather than swallowed — it weakens rotation, so it is alertable.
- **Housekeeping**: `Stacks.Workers.GuardianTokenSweepJob` purges dead rows; without the configured `ttl` a token row would never expire and the store would grow unbounded (`config.exs:134-137`).

### Write: advance the token family (every rotation)
- **Table(s)**: `op.auth_token_families`
- **Schema module**: `Stacks.Accounts.AuthTokenFamily` (`apps/core/lib/stacks/accounts/auth_token_family.ex:23`) — hand-written, not proto-generated; the table has no `.proto` contract.
- **Operation**: UPSERT via `Accounts.rotate_token_family/1` (`auth_controller.ex:359-366`), setting `current_jti` to the newly minted jti, `previous_jti` to the superseded one, `rotated_at`, and carrying `session_started_at` forward. `family_id` is the primary key and is application-supplied (`autogenerate: false`) so login can embed it as a claim before minting.
- **Lazy-create**: a legacy/untracked session (no `family_id` claim) is adopted into a new family from now, mirroring the missing-`sst` policy — bounded from this moment, not immediately expired.
- **Read**: `Accounts.check_token_family/3` does one indexed PK lookup per authed request. The revoke-write only fires on the reuse branch and is idempotent.

### GDPR
Both tables are reachable by erasure — `Stacks.GDPR.Deletion` erases `op.auth_token_families` (via `user_id`) and `op.guardian_tokens` (`apps/core/lib/stacks/gdpr/deletion.ex:24`, `:277`).

## 9. Storage (R2 / Local)

- Auth data (token, userId, email, displayName, role) is stored in localStorage via the `saveAuth` port, and cleared via `clearAuth` on logout or expiry. There is no second credential to store: renewal rotates the *same* access token, so `saveAuth` on the `TokenRefreshed (Ok _)` path (`frontend/src/Main.elm:3169`) is the whole persistence story.
- The blob must stay **flat** — nesting the fields under a `user` key fails silently and is indistinguishable from logged-out.
- A stored credential that is present but unreadable raises `StoredSessionUnreadable reason` (`frontend/src/Page/Login.elm:120`) rather than being read as "logged out" — an unreported read failure is what made the private-browsing auth bug so slow to diagnose.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: N/A — expiry is not a route. It is a shell-level concern: the reader is pushed to `/login` and the *reason* travels as a `Login.Arrival`, not as a URL.

### Init
- Token is loaded from localStorage flags on app init. On a token receipt at boot, `scheduleRenewal` is armed (`frontend/src/Main.elm:1785`) so a restored session renews on the same 7h cadence as a fresh login.

### Update cycle

| Msg | Model change | Cmd |
|-----|-------------|-----|
| `RenewToken` (`Main.elm:1915`) | none | `Api.refresh auth.token TokenRefreshed` when authenticated; the tick is dropped when signed out |
| `TokenRefreshed (Ok authResponse)` | `auth = Authenticated (renewAuthToken authResponse auth)` — token only | `saveAuth` + `scheduleRenewal` |
| `TokenRefreshed (Err _)` | cleared by `handleSessionExpiryFromRenewal` | `clearAuth` + `Nav.pushUrl "/login"` |
| any page's `SessionExpired` OutMsg | cleared by `handleSessionExpiry` (`Main.elm:1427`) | `clearAuth` + `Nav.pushUrl "/login"` |

- **One funnel, not per-page handling**: every authed page tests `Api.isUnauthorized err` in its `Failure` branch and returns `SessionExpired`; `Main` is the only module that decides what an expiry *does*. That is why adding a page cannot reintroduce a page-local 401 error state.
- **Renewal is proactive, not on-error**: there is no retry-the-failed-request-after-refresh path. An active session renews an hour before the 8h TTL, so it never hits a hard 401; a 401 that *does* arrive means the session is genuinely gone (revoked, capped, or replayed) and is treated as terminal.
- **Return URL**: `Login.isSessionExpiry` (`frontend/src/Page/Login.elm:158`) is read by `Main.redirectAfterNavigation`, so an expiry bounce returns the reader to the page they were standing on — the same value that raises the notice, rather than a parallel boolean that could disagree with it.

### View
- The sign-in card renders an in-voice notice for the arrival, not a generic error screen. `Arrival` has six constructors (`Login.elm:115-121`) precisely so two simultaneous notices are unwritable.

## 13. Operational Metrics

Four of these are **instrumented and exported**, registered in `Core.PromEx.Plugins.Stacks`:

- **JWT issuance, split by cause** — `stacks_auth_jwt_issued_count_total{context=…}` (`apps/core/lib/core/prom_ex/plugins/stacks.ex:316-319`, emitted at `auth_controller.ex:371`). `context: :refresh` tags a rotation, distinguishing silent-renewal issuance from interactive login issuance. Renewals ≫ logins is the healthy shape; renewals ≈ logins means sessions are dying before their first tick.
- **Absolute-cap expiry** — `stacks_auth_session_expired_count_total{reason=…}` (`plugins/stacks.ex:378-381`, emitted at `auth_controller.ex:334-336` with `reason: :lifetime_cap`). Makes forced re-login spikes visible. `reason` is a bounded whitelisted atom, never PII.
- **Reuse detection** — `stacks_auth_refresh_reuse_detected_count_total` (`plugins/stacks.ex:367-370`). A non-zero rate is either token theft or a rotation-race bug; the 20s grace window exists so it is the former.
- **Degraded rotation** — `stacks_auth_refresh_revoke_failed_count_total` (`plugins/stacks.ex:296-299`). A failed revoke leaves the old token valid until TTL, so this is alertable rather than merely logged.

Not yet instrumented, and derivable rather than emitted:

- **Renewal success/failure ratio**: HTTP status distribution for `POST /api/auth/refresh` is visible in the endpoint metrics, but the SPA-side outcome (`TokenRefreshed Ok` vs `Err`) is not reported.
- **401 rate on authed endpoints**: available from Phoenix endpoint telemetry, not broken out by "was this an expiry".
- **Session length distribution**: derivable from `auth_token_families.session_started_at` vs `rotated_at`, not exported as a histogram.

## 14. Performance & Usability Metrics

- **Silent renewal latency**: p50/p95 for `POST /api/auth/refresh`. The action does no Argon2 and no external call — one revoke (DELETE), one encode, one upsert — so it should be imperceptible (<200ms target). Renewal fires while the reader is idle-or-working, never blocking a click, so a slow renewal degrades to "the next request 401s" rather than a visible stall.
- **Session continuity rate**: fraction of sessions that cross the 8h TTL without the reader seeing the sign-in card. Target >95%. Not currently instrumented — needs the SPA-side renewal outcome.
- **Re-authentication friction**: time from expiry-redirect to a successful login. The return-URL behaviour (`Login.isSessionExpiry` → `Main.redirectAfterNavigation`) is what keeps this low; landing back on `/antilibrary` instead of the page they were reading is the regression to watch for.
- **Cross-tab spurious-logout rate**: how often the re-check-before-logout net (`Main.elm:1552`) *saves* a session that a naive interceptor would have dropped. This is the metric that would prove the 20s grace + `storage`-event propagation is sized correctly; it is not instrumented.
- **Renewal tick reliability**: `scheduleRenewal` is a single `Process.sleep` per token receipt, so a tab suspended past its tick renews late (on resume) rather than never. Worth watching if browsers start throttling background timers more aggressively — a missed tick degrades to a 401 and a re-login, not a stuck session.
- **Session length distribution**: derivable from `op.auth_token_families` (`session_started_at` → last `rotated_at`). Informs whether the 8h access TTL and 7-day cap are sized right.

## 15. Cost Tracking

- **Guardian JWT (rotation)**: one decode + one encode per renewal. HMAC operations — negligible CPU (<2ms combined). No Argon2 (that is login's cost, not renewal's).
- **Database, per renewal**: one DELETE on `op.guardian_tokens` (the revoke) + one UPSERT on `op.auth_token_families`. Negligible Neon cost.
- **Database, per authed request**: the reuse gate adds one indexed primary-key lookup on `op.auth_token_families` to **every** request carrying a `family_id` — the one ongoing cost of this story that scales with total API traffic rather than with session count. The revoke-write only fires on the reuse branch.
- **Renewal volume**: one renewal per active session per 7h — an 8h-TTL session that a reader keeps open all week costs ~24 rotations, capped at 7 days by `session_absolute_cap`.
- **No external service calls**: rotation is entirely internal. No email, no vision, no enrichment.
- **Total per-renewal cost**: ~$0.0000001 (negligible). The material cost is the per-request family lookup, absorbed into Neon compute.

# US-17.1.1 — Settings Index Page

## 1. User Story

> **As a** user, **I want** a central settings page that links to all my account, privacy, and profile settings **so that** I can find and manage everything about my account in one place.

**Acceptance criteria:**
- `/settings` renders the settings index page with sidebar navigation
- Clicking each sidebar link loads the corresponding sub-page
- The settings page is accessible from the display name dropdown in the top navigation
- All sub-pages are only accessible to authenticated users
- The sidebar highlights the active sub-page
- All sub-pages use the platform's parchment background and serif typography

---

## 2. UI Interaction Flow

### Happy Path
1. User clicks their display name in the top navigation and selects "Settings".
2. `UserMenu.SettingsClicked` fires, Main.elm navigates to `/settings/profile`.
3. Route resolves to `SettingsProfile` (note: `Settings` route also resolves to `/settings/profile` in `toPath`).
4. `initPageAuthenticated` creates `PageSettingsProfile (Profile.init auth.user)`.
5. `viewSettingsHub` wraps the sub-page content in the `Settings.view` layout.
6. Settings hub layout: left sidebar with navigation links, main content area with the active sub-page.

### Settings Categories (Sidebar Items)
As defined in `Page.Settings.sidebarItems`:
1. **Profile** (`/settings/profile`) — `SettingsProfile` route
2. **Password** (`/settings/password`) — `SettingsPassword` route
3. **Notifications** (`/settings/notifications`) — `SettingsNotifications` route
4. **Consent** (`/settings/consent`) — `SettingsConsent` route
5. **Age Verification** (`/settings/age-verification`) — `SettingsAgeVerification` route
6. **Privacy** (`/settings/privacy`) — `SettingsPrivacy` route

### Mobile Navigation
On mobile screens, the sidebar collapses to a `<select>` dropdown. Selecting an option fires `SettingsMobileNavChanged path`, which calls `Nav.pushUrl` with the selected path.

### Active State
- `viewSidebarItem` compares `currentRoute == item.route` and applies `settings-hub__nav-item--active`.
- `viewMobileOption` sets `selected` attribute on the matching option.

### Elm State Machine
- **Module**: `Page.Settings` (layout/wrapper only — no model, no messages)
- **Config type**: `{ currentRoute : Route, content : Html msg, onMobileNavChange : String -> msg }`
- **In Main.elm**: `viewSettingsHub` calls `Settings.view` with the current route, wrapped sub-page content, and the mobile nav change handler.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.Settings` (redirects to `Route.SettingsProfile` in `toPath`)
- **URL**: `/settings` (parsed), resolves to `/settings/profile` (displayed)
- **Public or authenticated**: Authenticated only

### Init
- **`Settings` route**: Creates `PageSettingsProfile (Profile.init auth.user)` — the Settings route defaults to the Profile sub-page.
- **`SettingsProfile` route**: Same as above.
- **Other settings routes**: Each creates its respective page model.
- **`isSettingsRoute`**: Helper function returns `True` for `Settings`, `SettingsProfile`, `SettingsPassword`, `SettingsNotifications`, `SettingsConsent`, `SettingsAgeVerification`, `SettingsPrivacy`.

### Update cycle
- **Msg**: `SettingsMobileNavChanged path` — `Nav.pushUrl model.key path` (navigates to the selected settings sub-page)
- Sub-page messages are handled by their respective handlers (`ProfileMsg`, `PasswordMsg`, `NotificationsMsg`, etc.).

### View
- **`viewSettingsHub`**: Calls `Settings.view` with the current route and wrapped content.
- **`Settings.view`**: Renders:
  - `div.page.page--settings.settings-hub`
  - `h1.page__title` — "Settings"
  - `div.settings-hub__layout` containing:
    - `nav.settings-hub__sidebar` with `ul.settings-hub__nav` and sidebar items
    - `div.settings-hub__mobile-nav` with `select.settings-hub__mobile-select`
    - `div.settings-hub__content` with the active sub-page content
- **Sidebar item rendering**: `li.settings-hub__nav-item` (or `settings-hub__nav-item--active`) with `a.settings-hub__nav-link`.
- **CSS classes**: `page--settings`, `settings-hub`, `settings-hub__layout`, `settings-hub__sidebar`, `settings-hub__nav`, `settings-hub__nav-item`, `settings-hub__nav-item--active`, `settings-hub__nav-link`, `settings-hub__mobile-nav`, `settings-hub__mobile-select`, `settings-hub__content`

## 13. Operational Metrics

- **Settings page visit rate**: Count of `Route.Settings` and `Route.SettingsProfile` renders per day.
- **Sub-page navigation distribution**: Which settings sub-pages are visited most frequently (Profile, Password, Notifications, Consent, Age Verification, Privacy).
- **Mobile dropdown usage rate**: Count of `SettingsMobileNavChanged` events (indicates mobile settings navigation).
- **Settings entry point**: How users reach settings — via user menu dropdown ("Settings" click) vs direct URL navigation.

---

## 14. Performance & Usability Metrics

- **Settings page load time**: Time from navigation to settings hub render. Should be <50ms (layout shell only, no API calls).
- **Sub-page discovery rate**: Percentage of settings visitors who navigate to more than one sub-page per session.
- **Sidebar vs mobile dropdown effectiveness**: Task completion rate comparison between desktop sidebar and mobile dropdown navigation.
- **Active state accuracy**: Verification that `settings-hub__nav-item--active` correctly highlights the current sub-page.
- **Time-to-target-setting**: Average time from settings hub entry to reaching the desired sub-page.

## 15. Cost Tracking

- **Total cost**: $0.00 (layout shell is client-side only).

# US-17.2.2 — Set Location

## 1. User Story

> **As a** user, **I want to** set my city and country **so that** Third Spaces, partner inventory, and events are filtered to my area.

This is an explicit setting, not device-based geolocation.

**Acceptance criteria:**
- Location fields appear on the profile settings page
- Saving a location triggers the geographic discovery sweep (US-2.5.2) via `user.location_updated` event
- Third Spaces, partner inventory, and event results are filtered by the user's configured location
- No device geolocation APIs are used
- Location is optional — the platform functions without it, but Third Spaces will be empty

---

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/settings/profile`.
2. Below the Personal Information section, a "Location" section shows two fields: Country Code (text input) and City (text input).
3. User enters country code (e.g., "ZA", "US", "GB") and city name.
4. User clicks "Save Location".
5. Button shows "Saving..." during the API call.
6. On success: "Location saved." confirmation.

### Sad Paths
- **Invalid data**: API returns 422 with changeset errors. User sees: "Could not save location. Please try again."
- **No token**: Save button does nothing (Elm guard checks `maybeToken`).

### Elm State Machine
- **Page module**: `Page.Settings.Profile` (location is part of the profile page, not a separate page)
- **Model fields**: `countryCode`, `city`, `savingLocation : RemoteData Http.Error ()`
- **Msg flow**: `SetCountryCode`/`SetCity` -> `SaveLocation` -> `Api.updateLocation` -> `SaveLocationCompleted`

---

## 3. API Calls

### `PUT /api/settings/location`
- **Auth**: Required (Bearer JWT)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.UserSettingsController.update_location/2`
- **Request body**: `{ "country_code": string, "city": string }`
- **Response (success)**: `{ "country_code": string, "city": string }` — HTTP 200
- **Response (error)**: `{ "errors": { ... } }` — HTTP 422
- **Context function**: `Accounts.update_location/2`

## 4. Auth & Middleware Guards

- **Plugs fired**: `SecurityHeaders` -> `AuthPipeline`

## 5. Database Interactions

### Write: Update location
- **Table(s)**: `op.users`
- **Operation**: UPDATE
- **Changeset**: `User.location_changeset/2` — casts `country_code` and `city`
- **Default**: `country_code` defaults to `"ZA"` in the schema.

## 6. Event Flow & Lifecycle

- **Payload**: `%{country_code: updated.country_code, city: updated.city}`

- **Emission method**: `Events.emit_safe/1`

### Event Handlers Triggered
- Per the spec, `user.location_updated` should trigger a geographic discovery sweep. This handler is not yet implemented in the current codebase.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.SettingsProfile` (location is part of the profile page)
- **URL**: `/settings/profile`

### Init
- `countryCode = Maybe.withDefault "" user.countryCode`
- `city = Maybe.withDefault "" user.city`
- `savingLocation = NotAsked`

### Update cycle
- **Msg**: `SetCountryCode val` / `SetCity val` — update field, reset `savingLocation`
- **Msg**: `SaveLocation` — `Api.updateLocation { countryCode, city } token SaveLocationCompleted`
- **Msg**: `SaveLocationCompleted (Ok _)` -> `savingLocation = Success ()`
- **Msg**: `SaveLocationCompleted (Err err)` -> `savingLocation = Failure err`

### View
- `div.settings-section` with `h2` "Location"
- Country Code: text input, placeholder "US, GB, ZA, etc."
- City: text input, placeholder "Your city"
- Save Location button with loading/saved states
- Feedback: "Location saved." on success, "Could not save location. Please try again." on error
- **Note**: The spec describes a country dropdown and city autocomplete, but the current implementation uses plain text inputs.

## 13. Operational Metrics

- **Location update rate**: Count of `PUT /api/settings/location` requests per day.
- **Location update success rate**: Ratio of HTTP 200 to total location update requests.
- **Location update failure rate**: Count of HTTP 422 responses (changeset validation errors).
- **Event emission reliability**: Count of `user.location_updated` events successfully written to `event_log`.
- **Geographic discovery trigger rate**: Once the handler is implemented, count of geographic discovery sweeps triggered by `user.location_updated` events.
- **Country code distribution**: Most common country codes set by users (informs Third Spaces and partner coverage priorities).

---

## 14. Performance & Usability Metrics

- **Location save latency**: p50/p95 for `PUT /api/settings/location` round-trip. Should be <200ms (simple DB UPDATE).
- **Location completion rate**: Percentage of users who set a location vs leave it empty. Low rates indicate the feature is not discoverable or not perceived as valuable.
- **Location update frequency**: How often users change their location after initial setup. Frequent changes may indicate moves or travel patterns.
- **Country code input accuracy**: Rate of validation errors from improperly formatted country codes (suggests need for dropdown selector as spec describes).
- **Third Spaces population after location set**: Whether setting a location results in visible Third Spaces content (measures the downstream value of the feature).

---

## 15. Cost Tracking

- **Database writes**: One UPDATE to `op.users` per location save. Negligible Neon cost.
- **Event writes**: One INSERT to `event_log` per update. Negligible.
- **Geographic discovery (future)**: When implemented, `user.location_updated` will trigger a Brave Search API call to find nearby bookshops, cafes, and events. Estimated cost: ~$0.005-0.01 per discovery sweep (Brave Search pricing). This is the primary cost driver for this story.
- **No current external service calls**: Location update itself is purely internal.
- **Total per-save cost (current)**: ~$0.00. **Total per-save cost (with discovery)**: ~$0.005-0.01 (dominated by Brave Search).

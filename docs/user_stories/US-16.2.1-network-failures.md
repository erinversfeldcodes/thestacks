# US-16.2.1 — Handle Network Failures Gracefully

## 1. User Story

> **As a** user whose network connection is unreliable, **I want** API failures to be communicated clearly **so that** I understand what went wrong and can retry when my connection is restored.

**Acceptance criteria:**
- All API-backed pages use RemoteData to model loading, success, and failure states
- Network failures display contextual inline error messages, not generic browser errors
- Form inputs are preserved when a submission fails
- Failures in one section do not affect the rest of the page
- The user can retry failed actions without refreshing the page

---

## 2. UI Interaction Flow

### Pattern
The Stacks uses the `RemoteData` pattern universally for all API interactions. This provides explicit modelling of four states:

1. **NotAsked** — No request has been made yet. Nothing renders.
2. **Loading** — Request in flight. Spinners or "Loading..." text.
3. **Success data** — Data received. Normal content renders.
4. **Failure error** — Request failed. Contextual error message renders inline.

### Examples by Page

**Login/Registration** (`Page.Login`):
- `submitState : RemoteData Http.Error AuthResponse`
- On `Failure`, error messages are contextual:
  - `Http.BadStatus 401` -> "The door remains shut. Invalid credentials."
  - `Http.BadStatus 409` -> "A reader by that name already frequents these halls."
  - `Http.BadStatus 422` -> "Please ensure all fields are properly filled."
  - `Http.NetworkError` -> "The library is unreachable. Please try again."
  - `Http.Timeout` -> "The library took too long to respond."
- Form inputs (`email`, `password`, `displayName`) are preserved in the model — the user can fix and retry.

**Bookshelves** (`Page.Bookshelf`, `Page.Bookshelf.LookingForHome`):
- `books : RemoteData Http.Error (List Placement)`
- On `Failure`: "Could not load your books. Please try again." / "Could not load your books looking for a home."
- On `Loading`: "Loading your books..." / spinner.

**Settings pages** (`Page.Settings.Profile`, `Page.Settings.Password`, `Page.Settings.Notifications`):
- `savingProfile : RemoteData Http.Error ()`, `saving : RemoteData Http.Error ()`
- On `Failure`: "Could not save profile. Please try again." / "Current password is incorrect." (for 422) / "Could not change password."
- Form inputs are preserved — user can correct and resubmit.
- On `Success`: "Profile saved." / "Password changed successfully." / "Preferences saved."

### Elm State Machine
- **Type**: `Types.RemoteData.RemoteData` — `NotAsked | Loading | Success a | Failure e`
- **Pattern**: Each API-backed field in a page model is typed as `RemoteData Http.Error SomeData`.
- **View pattern**: Pattern match on the RemoteData value to render appropriate state.
- **Error isolation**: Each RemoteData field is independent — failure in one does not affect others. For example, `Page.Settings.Profile` has separate `savingProfile` and `savingLocation` fields.

---

## 3. API Calls

All API calls follow the same pattern:
1. Elm sends an HTTP request via `Api.*` functions.
2. The response handler (`Result Http.Error a -> msg`) updates the corresponding `RemoteData` field.
3. On `Ok data` -> `Success data`
4. On `Err error` -> `Failure error`

Error types from Elm's `Http.Error`:
- `Http.BadStatus statusCode` — server returned a non-2xx status
- `Http.NetworkError` — network connectivity issue
- `Http.Timeout` — request timed out
- `Http.BadUrl` — malformed URL (programming error)
- `Http.BadBody` — response body could not be decoded

## 12. Elm Frontend State Machine (Detail)

### Route
N/A — This is a cross-cutting pattern applied to all API-backed pages.

### RemoteData Type
```elm
type RemoteData e a
    = NotAsked
    | Loading
    | Success a
    | Failure e
```

### Common View Patterns

**Data loading pages** (bookshelves, search results):
```elm
case model.books of
    NotAsked -> text ""
    Loading -> div [ class "loading" ] [ text "Loading..." ]
    Success placements -> viewPlacements placements
    Failure _ -> p [ class "error" ] [ text "Could not load. Please try again." ]
```

**Form submission pages** (settings, login):
```elm
-- Submit button changes based on state:
case model.saving of
    Loading -> button [ disabled True ] [ text "Saving..." ]
    _ -> button [ onClick Save ] [ text "Save" ]

-- Feedback after submission:
case model.saving of
    Success _ -> p [ class "success" ] [ text "Saved." ]
    Failure _ -> p [ class "error" ] [ text "Failed. Please try again." ]
    _ -> text ""
```

### Error Display
- Login errors use `aria-live="polite"` for screen reader announcement.
- Settings errors use `p [ class "error" ]` for inline display.
- Bookshelf errors use `p [ class "error" ]` with contextual messages.
- Form inputs are never cleared on failure — model fields persist, allowing retry.

## 13. Operational Metrics

- **API failure rate by type**: Breakdown of `Http.Error` types across all API calls — `NetworkError`, `Timeout`, `BadStatus` (by status code), `BadBody`.
- **Failure rate per endpoint**: Which API endpoints fail most frequently. Identifies reliability hotspots.
- **Retry rate**: How often users retry failed actions (detected by repeated identical API calls within a short window).
- **RemoteData state distribution**: Percentage of time API-backed fields spend in each state (NotAsked, Loading, Success, Failure) — indicates overall system health.
- **Timeout frequency**: Count of `Http.Timeout` errors. May indicate slow backend responses or network latency.

---

## 14. Performance & Usability Metrics

- **Error message clarity**: Support request rate related to network errors. Lower rates indicate effective error messaging.
- **Recovery rate after failure**: Percentage of `Failure` states that are followed by a successful retry (user was able to recover).
- **Form preservation effectiveness**: Percentage of form submission failures where the user successfully resubmits without re-entering data (validates that inputs are preserved).
- **Error display accessibility**: Screen reader announcement rate for `aria-live="polite"` error regions (login errors).
- **Time-to-recovery**: Average time between a `Failure` state and the next `Success` state for the same field/action.
- **Per-page error impact**: Whether errors on one page cause users to abandon the platform vs continue using other features.

---

## 15. Cost Tracking

- **No direct costs**: Network failure handling is a client-side pattern. The `RemoteData` type and error display logic run entirely in the Elm frontend.
- **Indirect cost impact**: Failed API calls that are retried double the server-side cost for that endpoint. However, individual endpoint costs are already negligible (see respective story cost sections).
- **Total cost**: $0.00 (error handling itself is free; retries incur the normal endpoint cost).

# US-14.4.1 — Reset a Forgotten Password

## 1. User Story

> **As a** returning user who has forgotten my password, **I want to** request a reset link by email and choose a new password **so that** I can regain access to my book collection without contacting support.

A locked-out user requests a password reset from the login card, receives a time-limited link by email, follows it to a page where they set a new password (entered twice), and is returned to the login card to sign in with the new credentials. The system never reveals whether an email address is registered, expires reset links after 24 hours, and enforces the same password rules as registration.

**Acceptance criteria:**
- The login card exposes a "Forgot password?" link that opens a request-reset page.
- The request-reset page collects an email address and, on submit, always shows the same neutral confirmation ("If that email exists, a reset link has been sent") regardless of whether the account exists — no email enumeration.
- A registered user receives an email containing a link to a reset page carrying a signed, single-use token.
- The reset page collects a new password and a confirmation of that password; the two must match and the password must be at least 8 characters (same rule as registration).
- On success the user sees a confirmation and is directed back to `/login` to sign in with the new password.
- Following an expired link (older than 24 hours) or a tampered/invalid token shows a clear "this link is no longer valid — request a new one" state, not a generic error.
- A weak or mismatched password is rejected with field-level guidance before or on submit.
- Both endpoints are rate-limited (IP-level `:auth` bucket + per-user/global email-send throttle) to prevent abuse and reset-email flooding.

**Technical note:** this began as a gap story — backend built, frontend absent. Both halves now ship. See the Implementation Status block below.

## 2. UI Interaction Flow

### Happy Path
1. On `/login`, beneath the submit button, the user clicks **"Forgot your password?"** (`frontend/src/Page/Login.elm:986-992`, `testId "forgot-password-link"`). It renders in `LoginMode` only.
2. The card switches to `ForgotPasswordMode` in place — no navigation, no scene change. Its subtitle becomes "Reset your password" (`Login.elm:743-744`) and `viewForgotForm` replaces the credentials form (`:725-726`). Arriving at `/forgot-password` directly opens the same mode (`Main.elm:1385`).
3. The form shows the helper line "Enter your email and we'll send you a link to set a new password.", one Email field (`testId "forgot-email"`, `aria-required="true"`), and a "Send reset link" button.
4. The user enters their email; `viewFieldHint` shows the same real-time validation the login form uses.
5. Clicking "Send reset link" dispatches `ForgotSubmitted` (`Login.elm:427`) → `Api.forgotPassword model.email GotForgotResponse` (`:436`) → `POST /api/auth/forgot-password`. The button shows `spinner spinner--small` while `forgotState = Loading`.
6. The API always returns HTTP 200. `Api.forgotPassword` decodes it as `()` via `resolveNoContent` (`frontend/src/Api.elm:779`) — the honest type, because the caller genuinely cannot learn whether the address was registered.
7. On success the button label becomes the past-tense, inert **"Reset link sent"** and a `notice` appears: "If that email is registered, a reset link is on its way. Check your inbox." (`Login.elm:817-821`, `testId "forgot-success"`). A "Back to sign in" button returns to `LoginMode`.
   - Two deliberate details here. The acknowledgement is a **`notice`** (which stamps `role="status"`), not a `login-card__subtitle` — it was previously rendered in the same class as the helper text two elements above, in a live region belonging to nobody, so a screen-reader user pressed the button and was told nothing (`Login.elm:801-816`). And the button label changes because a button still reading "Send reset link" after a send invites a second press even while `disabled` refuses it (`:787-796`).
   - `isForgotDisabled` (`Login.elm:314-318`) locks the button on an empty email, while `Loading`, **and after `Success`** — one send per form, because the endpoint answers 200 to every well-formed address and so cannot itself refuse a duplicate.
8. The user opens the email ("Reset your password — The Stacks") and clicks through to `/reset-password/{token}` — built by the worker as `base_url <> "/reset-password/#{token}"` (`apps/core/lib/stacks/workers/email_delivery_job.ex:113`).
9. The SPA parses `/reset-password/:token` (`Route.elm:113`) and mounts `Page.ResetPassword` with the token in its model (`Main.elm:1393-1394`; `ResetPassword.init`, `frontend/src/Page/ResetPassword.elm:67-73`). The page reuses the login page's static scene — library background, dim, vignette — and centres a card headed "Choose a new password". The animated door layers are login-only, so this renders the background statically (`ResetPassword.elm:192-203`).
10. The user enters the new password twice (`reset-password`, `reset-confirm`). `validate` (`:78-87`) requires `PasswordRule.isLongEnough` and an exact match, and the message is only shown once a field is non-empty (`:230-239`) — so an untouched form is not scolded.
11. The user clicks "Reset password" (`testId "reset-submit"`). During `Loading` the button is replaced by a disabled "Resetting..." button.
12. `Submit` → `Api.resetPassword { token, password } Completed` (`ResetPassword.elm:122-124`; client at `Api.elm:815-829`) → `POST /api/auth/reset-password`.
13. The API returns HTTP 200. The token is consumed (the `password_reset_token` column is cleared) and the Argon2 hash is updated.
14. The card shows the terminal state: "Your password has been reset. Taking you to sign in…" plus a "Sign in" link (`testId "reset-success"`, `reset-login-link`). After `advanceDelayMs = 2000` the page raises `AdvanceToLogin` and `Main.resetPasswordDestination` (`Main.elm:928-935`) navigates to `/login`. The delay is a floor on how long the confirmation is readable, not a wait imposed on anyone — the "Sign in" link is present throughout, and an instant redirect reads as "nothing happened, and now I am somewhere else" (`ResetPassword.elm:53-64`).
15. The user signs in with the new password via the normal US-14.2.1 flow. No JWT is issued by the reset itself and no door animation plays — a reset does not authenticate.

### Sad Paths
- **Unknown email (no enumeration)**: the API still returns 200 and the card still shows the identical "If that email is registered…" notice. No email is sent (`do_send_password_reset(nil)` short-circuits to `:ok`, `apps/core/lib/stacks/email.ex:141`), but nothing on screen distinguishes the two cases. `Api.forgotPassword` decoding to `()` makes that structural: there is no richer value for a caller to accidentally branch on.
- **Missing email field**: the API returns 422 `{ "error": "email is required" }`. Not reachable from the form (`isForgotDisabled` blocks an empty address), so this guards direct callers.
- **Expired link (>24h)**: `POST /api/auth/reset-password` returns HTTP 400 `{ "error": "token_expired" }` (`apps/core/lib/stacks_web/controllers/auth_controller.ex:257-260`).
- **Invalid / tampered / already-used token**: HTTP 400 `{ "error": "invalid_token" }` (`auth_controller.ex:262-265`). A used token no longer matches the now-cleared `password_reset_token` column, so replays land here.
- ⚠️ **Residue — the page does not distinguish the two 400s, and offers no way back.** `ResetPassword.elm:283-285` matches `Failure (Http.BadStatus 400)` once and shows a single combined message: "This reset link is invalid or has expired. Request a new one." The distinct `token_expired` / `invalid_token` bodies the backend goes to the trouble of returning are never decoded, and there is **no link to `/forgot-password`** on that state — the reader is told to request a new link and left to find the way themselves. Both halves of "decode the error field and branch" are still open.
- **Weak password (< 8 chars)**: `validate` blocks the submit and `viewForm` shows `PasswordRule.tooShort`. ⚠️ Note the button is **not** `disabled` on a validation failure — it is clickable and `Submit` returns unchanged (`ResetPassword.elm:117-118`), so the guard is in the update function rather than on the control. If the client is bypassed, the API returns 422 `{ "error": "validation_failed", "details": { "password": [...] } }` and the page renders `PasswordRule.tooShort` for it (`:287-289`).
- **Mismatched confirmation**: client-side only — `validate` returns "Passwords do not match." and `Submit` no-ops. The backend only ever receives a single `password`.
- **Missing token or password**: HTTP 422 `{ "error": "token and password are required" }` (`auth_controller.ex:276-280`).
- **Rate limited (IP)**: HTTP 429 from the `:auth` bucket. On the forgot form this is reported by `mailRequestError`; on the reset page it falls into the catch-all "Something went wrong. Please try again." (`ResetPassword.elm:291-293`), which is not the most useful thing to tell someone who should simply wait.
- **Reset-email flood (per-user/global)**: the throttle (10/hr per user, 100/hr global) skips the enqueue and the endpoint still returns 200. Deliberately silent, to preserve non-enumeration.
- **Double-submit against a single-use token**: guarded in two places. `Submit` refuses from `Loading` **or** `Success` (`ResetPassword.elm:110-118`), and `clearStaleError` clears only a `Failure` on keystroke — never `Loading`, `NotAsked`, or `Success` (`:180-187`). The bug this closes is worth keeping in view: a flat `submitting = NotAsked` on every keystroke let a reader correct a character mid-flight, un-disable the button, and fire a second request against a single-use token; the first returned 200 and the second 400, so the confirmation was **replaced** by "this link is invalid" on a reset that had genuinely succeeded, and the message they were left holding was the false one (`:161-177`).
- **A late or duplicate response after success**: ignored. `Completed` matches `( Success _, _ )` first and returns unchanged (`:130-135`) — a success is final, and the one thing this page must never do is take it back.
- **Network error**: the catch-all "Something went wrong. Please try again."

### Elm State Machine
Two modules, split at the arrival rather than at the step.

**Request a link — `Page.Login`, `ForgotPasswordMode`.**
- **Mode**: `Mode = LoginMode | RegisterMode | RegistrationPending String | ForgotPasswordMode | ResendConfirmationMode` (`frontend/src/Page/Login.elm:168-173`).
- **Model fields**: the card's shared `email` / `emailValidation`, plus `forgotState : RemoteData RequestError ()` (`:65`).
- **Msg flow**: `EmailChanged -> ForgotSubmitted -> Api.forgotPassword -> GotForgotResponse (Result RequestError ())` (`:195-196`).
- **Reached by**: `ModeSwitched ForgotPasswordMode` from the login-card link, **or** `Login.init Login.ForgotPassword` for the `/forgot-password` deep link. `init` takes the arrival as an argument and derives the mode from it (`:228-243`) — ⛔ there used to be five separate inits (`init`, `forgotInit`, `expiredInit`, `expiredDraftInit`, `farewellInit`), each setting a different subset of notice booleans, so adding a sixth reason meant remembering which flags it must *not* set. Taking the reason as an argument makes the set of buildable cards exactly the set of `Arrival` constructors.
- **`ModeSwitched` clears `forgotState`** (`:413`) so a mode change does not carry a stale acknowledgement.
- **OutMsg**: `NoOut` throughout — a reset request is not a sign-in, so the card has nothing to hand `Main`.

**Set the new password — `Page.ResetPassword`.**
- **Model fields**: `token` (from the URL), `password`, `confirmPassword`, `submitting : RemoteData Http.Error ()` (`frontend/src/Page/ResetPassword.elm:24-29`). Note `confirmPassword`, and note there are **no** separate validation fields: `validate : Model -> Maybe String` (`:78-87`) is derived on each render rather than stored, so a validation state cannot drift from the fields it describes.
- **Msg flow**: `SetPassword`/`SetConfirmPassword -> Submit -> Api.resetPassword -> Completed (Result Http.Error ()) -> AdvanceToSignIn` (`:32-37`).
- **RemoteData states**: `NotAsked -> Loading -> Success ()` / `Failure Http.Error`, with `Success` treated as absorbing (see §2).
- **OutMsg**: `NoOut | AdvanceToLogin` (`:48-50`). The page cannot navigate itself — the navigation key lives in `Main` — so it raises `AdvanceToLogin` once, `advanceDelayMs` after success, and `Main.resetPasswordDestination` (`Main.elm:928-935`) is its only reader. `AdvanceToSignIn` re-checks that `submitting` is still `Success` before raising it (`ResetPassword.elm:146-155`): a message that can be delivered late must not assume the state it was scheduled in still holds.
- No JWT is issued and no door animation plays — a reset does not authenticate; the reader signs in afterwards.

## 3. API Calls

### `POST /api/auth/forgot-password`
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.AuthController.forgot_password/2`
- **Request body**: `{ "email": string }`
- **Response (success)**: `{ "message": "If that email exists, a reset link has been sent" }` — HTTP 200 (returned for both registered and unregistered emails)
- **Response (error)**: `{ "error": "email is required" }` — HTTP 422 (missing `email` param)
- **FallbackController handling**: N/A — the action returns explicit `json/2` responses; it never returns an error tuple to the fallback.

### `POST /api/auth/reset-password`
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.AuthController.reset_password/2`
- **Request body**: `{ "token": string, "password": string }`
- **Response (success)**: `{ "message": "Password updated successfully" }` — HTTP 200
- **Response (error)**:
  - `{ "error": "token_expired" }` — HTTP 400 (token older than `max_age: 86_400` / 24h)
  - `{ "error": "invalid_token" }` — HTTP 400 (bad signature, unknown user, or token no longer matches the stored column, e.g. already used)
  - `{ "error": "validation_failed", "details": { "password": [ ... ] } }` — HTTP 422 (changeset failure, e.g. password < 8 chars)
  - `{ "error": "token and password are required" }` — HTTP 422 (missing params)
- **FallbackController handling**: N/A — the action pattern-matches `Email.reset_password/2` results and emits explicit responses.

### Emailed link — `GET {endpoint_url}/reset-password/{token}` (frontend route)
- **Not an API call.** This is the SPA route the reset email points at: `reset_url = base_url <> "/reset-password/#{token}"` (`apps/core/lib/stacks/workers/email_delivery_job.ex:113`).
- **It resolves.** `Parser.map ResetPassword (s "reset-password" </> string)` (`frontend/src/Navigation/Route.elm:113`) → `Page.ResetPassword`. The route and the worker's string must stay in step; nothing but a test holds them together, so `e2e/tests/password-reset.spec.ts` following the real emailed URL is the guard that matters here rather than a unit test asserting a hardcoded path on either side.

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` -> `RateLimiter` (bucket: `:auth`) for both endpoints.
- **No authentication required** — both endpoints are public (a locked-out user has no valid session). This is distinct from the authenticated "change password while signed in" flow, which lives behind `:authenticated` + its own rate-limit bucket and is out of scope for this story.
- **Email enumeration prevention**:
  - `forgot_password/2` always returns the same 200 message; `Email.send_password_reset/1` looks the user up and hands off to `do_send_password_reset/1`, whose `nil` clause short-circuits to `:ok` (`apps/core/lib/stacks/email.ex:58-60`, `:141`). No status difference distinguishes registered from unregistered addresses.
  - `reset_password/2` maps both "bad signature" and "token doesn't match the stored column" to the same `invalid_token` / HTTP 400 (`email.ex:132-133`, `:226`), so a used or forged token cannot be distinguished from a never-issued one.
  - Abuse is bounded by the per-IP `:auth` bucket, consumed in the plug **before** the action runs — so a caller guessing addresses is throttled at exactly the rate a reader retrying their own is, and the limiter cannot become the oracle the body refuses to be.
- **Token mechanism**: `Phoenix.Token` signed with salt `"password_reset"` over the user's `id` (`email.ex:146`), verified with `max_age: 86_400` (24h) (`email.ex:124`). The signed token is *also* persisted to `op.users.password_reset_token`; verification additionally requires `Repo.get_by(User, id: user_id, password_reset_token: token)` to match (`email.ex:126`), which makes each issued token single-use — completing a reset clears the column, invalidating replays.
- ⚠️ **A completed reset revokes every existing session.** `do_reset_password/2` calls `Accounts.revoke_all_user_sessions(updated.id)` after the password update (`email.ex:243`). This is load-bearing, not housekeeping: a reset is the recovery path for a *compromised* account, so an attacker's still-valid token would otherwise outlive the credential the victim just changed. The authenticated change-password path had always done this; the reset path did not, which left the victim less safe than the success message implied (`email.ex:237-242`). It is also why the reset page ends at the sign-in card rather than logging the reader in — any session it could have handed them would have been revoked a line later.
- **Ownership checks**: ownership is proven by possession of the signed token bound to the user id; no session or `verify_ownership/2` is involved.

## 5. Database Interactions

### Read: Look up user by email (forgot-password)
- **Table(s)**: `op.users`
- **Query**: `Accounts.get_user_by_email(email)` (`apps/core/lib/stacks/email.ex:59`).
- **Schema module**: `Stacks.Accounts.User`

### Write: Store reset token (forgot-password, registered user only)
- **Table(s)**: `op.users`
- **Operation**: UPDATE via `Accounts.password_reset_changeset/2` inside `Repo.transaction/1` (`email.ex:149-163`).
- **Changeset validations**: `password_reset_changeset/2` casts `password_reset_token` and `password_reset_sent_at` only (`apps/core/lib/stacks/accounts.ex:217-220`) — no validation, just token storage.
- **Transaction**: the `Repo.update!` of the token/timestamp and the `Oban.insert!` of the delivery job commit atomically — so there is never a stored token with no email on its way, nor an email carrying a token the database does not recognise.
- **Rate-limit precondition**: `check_rate_limit/1` (`email.ex:251-276`) runs *before* the transaction; if the per-user (10/hr) or global (100/hr) cap is hit, no write and no enqueue occur, but the endpoint still returns `:ok`/200.

### Read + Write: Verify token and update password (reset-password)
- **Read**: `Repo.get_by(User, id: user_id, password_reset_token: token)` after `Phoenix.Token.verify/4` (`email.ex:124-127`). A `nil` here is mapped to `{:error, :invalid}` by `do_reset_password(nil, _)` (`:226`).
- **Write**: UPDATE via `Accounts.password_update_changeset/2` (`email.ex:228-235`).
- **Changeset validations**: `password_update_changeset/2` (`accounts.ex:223-229`) casts `password`, `password_reset_token`, `password_reset_sent_at`; `validate_required([:password])`; `validate_length(:password, min: 8, message: "must be at least 8 characters")`; then `hash_password/1` (`:231-237`) puts `Argon2.hash_pwd_salt/1` into `password_hash` and **deletes** the plaintext `password` change, so the plaintext cannot reach the database even if the schema grew such a column.
- **Single-use enforcement**: the same changeset sets `password_reset_token: nil` and `password_reset_sent_at: nil` (`email.ex:232-233`), so the link cannot be reused.
- **Write: revoke all sessions** — `Accounts.revoke_all_user_sessions(user_id)` (`accounts.ex:1402-1411`), called at `email.ex:243`. Two writes: `op.auth_token_families` rows with a null `revoked_at` get one stamped, and `GuardianDbToken.destroy_by_sub/1` deletes the user's `op.guardian_tokens` rows. See §4 for why. Note it runs **after** `Repo.update/1` returns rather than inside a transaction with it: a failure here leaves the password changed and the old sessions alive.

## 6. Event Flow & Lifecycle

### Events Emitted
- **None on the event bus.** Neither `forgot_password/2` nor `reset_password/2` calls `Events.emit/1` or `Events.emit_safe/1`. (Unlike registration, which emits `user.registered`.)
- ⚠️ **Still no audit entry on a completed reset.** A successful reset changes a credential *and* revokes every session, which is exactly the shape of event an account-recovery audit trail exists for — and US-8.5's audit page would show it to the account holder, which is how a victim would notice a reset they did not request. `Audit.log(user.id, "user.password_reset", ...)` mirroring the `user.login` pattern remains unwritten.

### Event Handlers Triggered
- N/A — no event is emitted, so no handler fires. The reset email is enqueued *directly* by the context (`Oban.insert!` in `do_send_password_reset/1`, `apps/core/lib/stacks/email.ex:157-162`), not via the `user.registered`-style handler indirection used at registration. That directness is what lets the token write and the enqueue share one transaction (§5).

## 7. Background Jobs (Oban)

- **Worker**: `Stacks.Workers.EmailDeliveryJob`
- **Queue**: `:notifications`
- **Args**: `%{ "template" => "password_reset", "user_id" => user_id, "params" => %{ "token" => token } }` (`apps/core/lib/stacks/email.ex:157-161`)
- **Enqueued by**: `Email.do_send_password_reset/1`, inside the token-write transaction (`email.ex:149-163`).
- **What it does**: `build_email(user, :password_reset, %{"token" => token})` (`apps/core/lib/stacks/workers/email_delivery_job.ex:111-119`) composes the Swoosh email — subject "Reset your password — The Stacks", body `Templates.password_reset(reset_url)` (`apps/core/lib/stacks/email/templates.ex:35`) where `reset_url = base_url <> "/reset-password/#{token}"` (`email_delivery_job.ex:113`) — and delivers it via Resend (prod) or logs it (dev/test).

- **On success**: Reset email delivered with a 24-hour link.
- **On failure**: Standard Oban retry behaviour on the `:notifications` queue.

## 10. Cache Interactions

- **Cache**: `RateLimiter` (ETS-backed)
- **Operation**: Check and increment
- **Key**: `:auth` bucket, keyed by client IP (shared with login/register/forgot).
- **TTL**: Configured per bucket (prod `:auth` default 60/60s; test override 5/60s).
- **Invalidation trigger**: Time-based expiry.
- **Note**: The per-user/global reset-email throttle is *not* cache-backed — it is a live `Oban.Job` row count over the last hour (`apps/core/lib/stacks/email.ex:251-276`), so it survives restarts and is exact rather than approximate. It counts **all** `EmailDeliveryJob` rows, not only `password_reset` ones, so a burst of any transactional mail eats into the reset budget.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variants**: `Route.ForgotPassword` (`frontend/src/Navigation/Route.elm:57`) and `Route.ResetPassword String` (`:59`) — the `String` carries the token from the URL.
- **URLs**: `/forgot-password` and `/reset-password/:token`.
- **Parser**: `Parser.map ForgotPassword (s "forgot-password")` (`Route.elm:111`) and `Parser.map ResetPassword (s "reset-password" </> string)` (`:113`).
- **`toPath`**: `ForgotPassword -> "/forgot-password"` (`:243-244`), `ResetPassword token -> "/reset-password/" ++ token` (`:249`).
- **Public or authenticated**: both public — a locked-out reader must reach them without a session.

### Init
- **`initPage` branches**: `ForgotPassword -> PageLogin (Login.init Login.ForgotPassword)` (`frontend/src/Main.elm:1379`, `:1385`) — *not* a page of its own; `ResetPassword token -> PageResetPassword (ResetPassword.init token)` (`:1393-1394`).
- **API calls on init**: none, on either. The token is deliberately **not** pre-validated on load; validity is discovered on submit. Pre-validating would burn a single-use token on a page view — including on a link-preview fetch by an email client.
- **Initial model state (forgot)**: the login card's own initial state with `mode = ForgotPasswordMode`, `forgotState = NotAsked`.
- **Initial model state (reset)**: `{ token = <from URL>, password = "", confirmPassword = "", submitting = NotAsked }` (`frontend/src/Page/ResetPassword.elm:67-73`).

### Update cycle
**Forgot mode (`Page.Login`):**

| Msg | Model change | Cmd |
|-----|-------------|-----|
| `EmailChanged` | `email`, `emailValidation` | none |
| `ForgotSubmitted` when `isForgotDisabled` | none | none |
| `ForgotSubmitted` otherwise | `forgotState = Loading` | `Api.forgotPassword model.email GotForgotResponse` |
| `GotForgotResponse (Ok ())` | `forgotState = Success ()` | none |
| `GotForgotResponse (Err err)` | `forgotState = Failure err` | none |
| `ModeSwitched mode` | `mode`, all validations `Pristine`, `arrival = Fresh`, `forgotState`/`resendState` `NotAsked` | none |

`ForgotSubmitted` re-applies `isForgotDisabled` in `update` rather than trusting the button's `disabled` (`Login.elm:427-433`) — one send per form, enforced where it cannot be bypassed. The `ModeSwitched` reset is one assignment clearing what used to be three separate notice booleans, which is why they can no longer be cleared unevenly (`:408-421`).

**Reset page (`Page.ResetPassword`):**

| Msg | Model change | Cmd / OutMsg |
|-----|-------------|--------------|
| `SetPassword` / `SetConfirmPassword` | the field; `submitting` via `clearStaleError` (clears a `Failure` only) | none |
| `Submit` from `Loading` or `Success`, or with a validation error | none | none |
| `Submit` otherwise | `submitting = Loading` | `Api.resetPassword { token, password } Completed` |
| `Completed _` when already `Success` | none | none — a success is final |
| `Completed (Ok _)` | `submitting = Success ()` | `Process.sleep advanceDelayMs -> AdvanceToSignIn` |
| `Completed (Err err)` | `submitting = Failure err` | none |
| `AdvanceToSignIn` while `Success` | none | OutMsg `AdvanceToLogin` |

- **Api clients**: `Api.forgotPassword` (`frontend/src/Api.elm:772-783`) decodes via `resolveNoContent` to `()`, not `authResponseDecoder` — the backend answers identically for every address, so `()` is the honest type. `Api.resetPassword` (`:815-829`) uses `Http.expectWhatever`, which is why the page sees `Http.BadStatus 400` and **not** the `"error"` string inside it (see the residue in §2).

### Submit gating
- **Forgot**: `isForgotDisabled` (`Login.elm:314-318`) — empty email, `Loading`, **or** `Success ()`. The `Success` clause exists because `/api/auth/forgot-password` answers 200 to every well-formed address, so the endpoint cannot itself refuse the duplicate.
- **Reset**: the button carries `disabled` only while `Loading` (`ResetPassword.elm:274-281`); validation failures are refused inside `Submit` instead. Functionally safe, but the control does not show the reader that it will not act.

### View
- **Login card**: "Forgot your password?" renders beneath the submit button in `LoginMode` (`Login.elm:984-995`, class `login-card__forgot`, `testId "forgot-password-link"`).
- **Forgot mode key elements** (`viewForgotForm`, `Login.elm:757-837`): the card keeps the title "The Stacks" with subtitle "Reset your password" (`:743-744`); helper line; one Email field (`forgot-email`, `aria-required="true"`) with `viewFieldHint`; a submit whose label goes `"Send reset link"` → spinner → `"Reset link sent"`; a `notice` (`role="status"`) for success (`forgot-success`) or error (`forgot-error`); and a "Back to sign in" button (`forgot-back`).
- **Reset page key elements** (`ResetPassword.elm:190-297`): the login scene rendered statically (`layer-arrival`, `layer-bookshelf`, `layer-bookshelf-dim`, `layer-vignette`, `login-overlay`) around a `login-card` titled "Choose a new password"; New password + Confirm new password fields (`reset-password`, `reset-confirm`) with `PasswordRule.requirementHint` as the placeholder; a submit that becomes a disabled "Resetting..."; a single error paragraph (`reset-error`); and the terminal success state (`reset-success`) with a `role="status"` notice plus a "Sign in" link (`reset-login-link`).
- **ARIA**: `aria-required="true"` on the forgot email input; `role="status"` on both terminal notices (via `notice` on the card, explicitly on the reset page). The reset page's **error** paragraph has no live-region role, so a failed reset is not announced — the gap that `notice` was introduced to close on the forgot side.
- **CSS classes**: `page--login`, `login-card`, `login-card__title`, `login-card__subtitle`, `login-card__field`, `login-card__label`, `login-card__input`, `login-card__submit`, `login-card__back`, `login-card__forgot`, `login-card__forgot-form`, `login-card__notice`, `login-card__error`, `spinner spinner--small`, plus `btn btn--primary` on the reset page's sign-in link.

## 13. Operational Metrics

- **Reset-request rate**: Count of `POST /api/auth/forgot-password` requests per day. A spike may indicate credential-stuffing probing or a UX regression in login.
- **Reset-completion rate**: Ratio of HTTP 200 `POST /api/auth/reset-password` responses to reset emails enqueued — the request → email → click → new-password funnel conversion.
- **Token-failure breakdown**: Counts of `token_expired` (400), `invalid_token` (400), and `validation_failed` (422) responses. High `token_expired` suggests the 24h window is too short or emails are delayed; high `invalid_token` may indicate link mangling by email clients or replay attempts.
- **Enumeration-probe signal**: Volume of forgot-password requests for emails that resolve to `nil` (no user). Because the response is uniform, this is only observable server-side via the `do_send_password_reset(nil)` path — worth logging as a metric without surfacing it to callers.
- **Rate-limiter trigger count**: HTTP 429s from the `:auth` bucket on these two endpoints, plus the count of reset emails suppressed by the per-user (10/hr) / global (100/hr) throttle.
- **Reset-email delivery rate**: Ratio of successfully delivered `password_reset` emails (via Resend) to `password_reset` jobs enqueued on the `:notifications` queue.

## 14. Performance & Usability Metrics

- **Request-to-email latency**: Time from `POST /api/auth/forgot-password` to the `EmailDeliveryJob` completing on the `:notifications` queue.
- **Email-to-click latency**: Time between reset-email delivery and the `/reset-password/:token` page load — indicates how promptly users act (and informs the 24h expiry choice).
- **Reset endpoint latency**: p50/p95 for `POST /api/auth/reset-password` (dominated by `Argon2.hash_pwd_salt/1` in `password_update_changeset/2`).
- **Client-side validation feedback latency**: Keypress-to-validation-state change on the reset form (should be <16ms, synchronous in Elm).
- **Reset abandonment rate**: Fraction of reset-page loads that never submit — flags confusion or password-rule friction.
- **Post-reset sign-in success rate**: Fraction of completed resets followed by a successful `POST /api/auth/login` within a short window — the true measure of "did the user regain access".

## 15. Cost Tracking

- **Resend**: One reset email per throttled request at ~$0.001/email. Bounded by the per-user (10/hr) and global (100/hr) caps, which also cap the blast radius of a reset-email flooding attempt.
- **Argon2 (Fly.io compute)**: One `Argon2.hash_pwd_salt/1` per successful reset (~200-400ms CPU on shared-cpu-1x, ~$0.0000025/s of CPU). Failed/invalid token attempts do NOT reach hashing — they short-circuit at `Phoenix.Token.verify/4` or the `get_by` lookup.
- **Database**: One `get_user_by_email` read + one token-write UPDATE per registered forgot-request; one `get_by` read + one password UPDATE per completed reset. Negligible Neon cost.
- **Oban job processing**: `EmailDeliveryJob` on `:notifications` — minimal compute; the cost is the Resend call, not the job.
- **No other external services**: Password reset does not touch vision, the scraper, R2, or any enrichment API.
- **Total per-completed-reset cost**: ~$0.001 (dominated by Resend email delivery; the Argon2 hash is absorbed into Fly.io machine billing).

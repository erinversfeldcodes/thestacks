# US-14.4.1 — Reset a Forgotten Password

## 1. User Story

> **As a** returning user who has forgotten my password, **I want to** request a reset link by email and choose a new password **so that** I can regain access to my book collection without contacting support.

A locked-out user requests a password reset from the login card, receives a time-limited link by email, follows it to a page where they set a new password (entered twice), and is returned to the login card to sign in with the new credentials. The system never reveals whether an email address is registered, expires reset links after 24 hours, and enforces the same password rules as registration.

**Acceptance criteria:**
- The login card exposes a "Forgot password?" link that opens a request-reset page.
- The request-reset page collects an email address and, on submit, always shows the same neutral confirmation ("If that email exists, a reset link has been sent") regardless of whether the account exists — no email enumeration.
- A registered user receives an email containing a link to a reset page carrying a signed, single-use token.
- The reset page collects a new password and a confirmation of that password; the two must match and the password must be at least 8 characters (same rule as registration).
- On success the user sees a confirmation and is directed back to `/login` to sign in with the new password.
- Following an expired link (older than 24 hours) or a tampered/invalid token shows a clear "this link is no longer valid — request a new one" state, not a generic error.
- A weak or mismatched password is rejected with field-level guidance before or on submit.
- Both endpoints are rate-limited (IP-level `:auth` bucket + per-user/global email-send throttle) to prevent abuse and reset-email flooding.

**Technical note:** This is a **gap story**. The entire backend for password reset is already implemented and tested; the user-facing frontend and the email-link wiring are not. See the Implementation Status block below.

## 2. UI Interaction Flow

### Happy Path
1. On `/login`, below the sign-in form, the user clicks a "Forgot password?" link. **(MUST BUILD — no such link today.)**
2. The SPA navigates to `/forgot-password`. **(MUST BUILD — no such route today.)** The request-reset card renders with a single Email field and a "Send reset link" button.
3. The user enters their email. Real-time validation requires `@` and `.` (same rule as the login form).
4. The user clicks "Send reset link". The button shows a spinner (`spinner spinner--small`) during the request.
5. The SPA calls `POST /api/auth/forgot-password` with `{ "email": "..." }`. **(MUST BUILD `Api.forgotPassword`.)**
6. The API always returns HTTP 200 `{ "message": "If that email exists, a reset link has been sent" }`.
7. The card transitions to a neutral **Reset Requested** state: "If an account exists for [email], a reset link is on its way. Check your inbox — the link expires in 24 hours." No form fields, a "Back to Sign In" link.
8. The user opens the email ("Reset your password — The Stacks") and clicks "Reset password", which points at `/reset-password/{token}`.
9. The SPA parses `/reset-password/:token` **(MUST BUILD — route + page)**, showing a reset card with New Password and Confirm Password fields.
10. The user enters a new password twice. Validation: password >= 8 characters; confirmation must match (same rules as the register form).
11. The user clicks "Set new password" (disabled until both fields validate and match). Spinner during the request.
12. The SPA calls `POST /api/auth/reset-password` with `{ "token": "...", "password": "..." }`. **(MUST BUILD `Api.resetPassword`.)**
13. The API returns HTTP 200 `{ "message": "Password updated successfully" }`. The token is consumed (cleared server-side) and the password hash is updated.
14. The card transitions to a **Reset Complete** state: "Your password has been updated. You can now sign in." with a "Sign in" link to `/login`.
15. The user signs in with the new password via the normal US-14.2.1 flow.

### Sad Paths
- **Unknown email (no enumeration)**: The user submits an email with no account. The API still returns 200 and the UI still shows the identical "If an account exists…" message. No email is sent (the context short-circuits on `nil`), but the UI is indistinguishable from the registered case, so an attacker cannot enumerate accounts.
- **Missing email field**: The API returns 422 `{ "error": "email is required" }`. The UI keeps the user on the form with "Please enter your email address."
- **Expired link**: The user follows a link older than 24 hours. `POST /api/auth/reset-password` returns HTTP 400 `{ "error": "token_expired" }`. The reset page shows "This reset link has expired. Request a new one." with a link back to `/forgot-password`.
- **Invalid / tampered / already-used token**: The API returns HTTP 400 `{ "error": "invalid_token" }`. The reset page shows "This reset link is not valid. Request a new one." with a link back to `/forgot-password`. (A used token no longer matches the now-cleared `password_reset_token` column, so replays fall here.)
- **Weak password (< 8 chars)**: Client validation disables submit and shows "Password must be at least 8 characters." If the client is bypassed, the API returns HTTP 422 `{ "error": "validation_failed", "details": { "password": ["must be at least 8 characters"] } }`.
- **Mismatched confirmation**: Purely client-side — submit stays disabled and the Confirm Password field shows "Passwords do not match." (The backend only receives a single `password`.)
- **Missing token or password**: The API returns HTTP 422 `{ "error": "token and password are required" }`.
- **Rate limited (IP)**: Too many requests from an IP to either endpoint return HTTP 429 via the `:auth` bucket. The UI shows a generic "Please wait a moment and try again."
- **Reset-email flood (per-user/global)**: The email-send throttle (10/hr per user, 100/hr global) silently skips enqueuing another email. The forgot-password endpoint still returns 200 — the user simply does not get an additional email. No error surfaces (by design, to preserve non-enumeration).
- **Network error**: The UI shows "The library is unreachable. Please try again."

### Elm State Machine
- **Page modules (MUST BUILD)**: `Page.ForgotPassword` (request a link) and `Page.ResetPassword` (set a new password). May instead be folded into `Page.Login` as additional `Mode` values (`ForgotMode`, `ResetMode token`) — but a dedicated pair of pages keeps the token-bearing URL and the login card cleanly separated and is the recommended shape.
- **`Page.ForgotPassword` model fields**: `email`, `emailValidation`, `submitState : RemoteData Http.Error ()`.
- **`Page.ResetPassword` model fields**: `token` (from the URL), `password`, `passwordConfirm`, `passwordValidation`, `passwordConfirmValidation`, `submitState : RemoteData Http.Error ()`.
- **Msg flow (forgot)**: `EmailChanged -> validate -> FormSubmitted -> Api.forgotPassword -> GotForgotResponse (Ok ()) -> RequestSent`.
- **Msg flow (reset)**: `PasswordChanged`/`PasswordConfirmChanged -> validate -> FormSubmitted -> Api.resetPassword -> GotResetResponse (Ok ()) -> ResetComplete`.
- **RemoteData states**: `NotAsked -> Loading -> Success`/`Failure Http.Error`.
- **OutMsg pattern**: `NoOut` during interaction; on reset success, either an `OutMsg` `PasswordReset` prompting Main to `Nav.pushUrl "/login"`, or a plain in-page "Sign in" link. No JWT is issued and no door animation plays — password reset does not authenticate the user; they must sign in afterward.

## 3. API Calls

### `POST /api/auth/forgot-password`
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.AuthController.forgot_password/2`
- **Request body**: `{ "email": string }`
- **Response (success)**: `{ "message": "If that email exists, a reset link has been sent" }` — HTTP 200 (returned for both registered and unregistered emails)
- **Response (error)**: `{ "error": "email is required" }` — HTTP 422 (missing `email` param)
- **FallbackController handling**: N/A — the action returns explicit `json/2` responses; it never returns an error tuple to the fallback.

### `POST /api/auth/reset-password`
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.AuthController.reset_password/2`
- **Request body**: `{ "token": string, "password": string }`
- **Response (success)**: `{ "message": "Password updated successfully" }` — HTTP 200
- **Response (error)**:
  - `{ "error": "token_expired" }` — HTTP 400 (token older than `max_age: 86_400` / 24h)
  - `{ "error": "invalid_token" }` — HTTP 400 (bad signature, unknown user, or token no longer matches the stored column, e.g. already used)
  - `{ "error": "validation_failed", "details": { "password": [ ... ] } }` — HTTP 422 (changeset failure, e.g. password < 8 chars)
  - `{ "error": "token and password are required" }` — HTTP 422 (missing params)
- **FallbackController handling**: N/A — the action pattern-matches `Email.reset_password/2` results and emits explicit responses.

### Emailed link — `GET {endpoint_url}/reset-password/{token}` (frontend route, MUST BUILD)
- **Not an API call.** This is the SPA route the reset email points at (`reset_url = CoreWeb.Endpoint.url() <> "/reset-password/#{token}"`, `email_delivery_job.ex:88-89`).
- **Currently 404** — no matching `Route` variant / parser branch exists. Building this route (and its page) is the core gap this story closes.

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` -> `RateLimiter` (bucket: `:auth`) for both endpoints.
- **No authentication required** — both endpoints are public (a locked-out user has no valid session). This is distinct from the authenticated "change password while signed in" flow, which lives behind `:authenticated` + `:rate_limit_password_change` (`router.ex:251-252`, `SettingsPassword`) and is out of scope for this story.
- **Email enumeration prevention**:
  - `forgot_password/2` always returns the same 200 message; `Email.send_password_reset/1` short-circuits to `:ok` when `Accounts.get_user_by_email/1` returns `nil` (`email.ex:104`). No timing or status difference distinguishes registered from unregistered emails at the response level.
  - `reset_password/2` maps both "bad signature" and "token doesn't match the stored column" to the same `invalid_token` / HTTP 400, so a used or forged token cannot be distinguished from a never-issued one.
- **Token mechanism**: `Phoenix.Token` signed with salt `"password_reset"` over the user's `id` (`email.ex:109`), verified with `max_age: 86_400` (24h) (`email.ex:87`). The signed token is *also* persisted to `op.users.password_reset_token`; verification additionally requires `Repo.get_by(User, id: user_id, password_reset_token: token)` to match (`email.ex:89`), which makes each issued token single-use — completing a reset clears the column, invalidating replays.
- **Ownership checks**: Ownership is proven by possession of the signed token bound to the user id; no session or `verify_ownership/2` is involved.

## 5. Database Interactions

### Read: Look up user by email (forgot-password)
- **Table(s)**: `op.users`
- **Query**: `Accounts.get_user_by_email(email)` (`email.ex:59`).
- **Schema module**: `Stacks.Accounts.User`

### Write: Store reset token (forgot-password, registered user only)
- **Table(s)**: `op.users`
- **Operation**: UPDATE via `Accounts.password_reset_changeset/2` inside `Repo.transaction/1` (`email.ex:112-126`).
- **Changeset validations**: `password_reset_changeset/2` casts `password_reset_token` and `password_reset_sent_at` only (`accounts.ex:127-130`) — no validation, just token storage.
- **Transaction**: `Repo.transaction/1` wraps the `Repo.update!` of the token/timestamp and the `Oban.insert!` of the delivery job so the token write and the email enqueue commit atomically (`email.ex:112-126`).
- **Rate-limit precondition**: `check_rate_limit/1` (`email.ex:161`) runs *before* the transaction; if the per-user (10/hr) or global (100/hr) email cap is hit, no write and no enqueue occur, but the endpoint still returns `:ok`/200.

### Read + Write: Verify token and update password (reset-password)
- **Read**: `Repo.get_by(User, id: user_id, password_reset_token: token)` after `Phoenix.Token.verify/4` (`email.ex:88-89`).
- **Write**: UPDATE via `Accounts.password_update_changeset/2` (`email.ex:148-158`).
- **Changeset validations**: `password_update_changeset/2` casts `password`, `password_reset_token`, `password_reset_sent_at`; `validate_required([:password])`; `validate_length(:password, min: 8, message: "must be at least 8 characters")`; then `hash_password/1` computes `Argon2.hash_pwd_salt/1` into `password_hash` and deletes the plaintext `password` change (`accounts.ex:133-147`).
- **Single-use enforcement**: On success the changeset also sets `password_reset_token: nil` and `password_reset_sent_at: nil` (`email.ex:151-154`), so the same link cannot be reused.

- **On failure**: Standard Oban retry behaviour on the `:notifications` queue.

### Init
- **`initPage` branches (new)**: `Route.ForgotPassword -> PageForgotPassword ForgotPassword.init`; `Route.ResetPassword token -> PageResetPassword (ResetPassword.init token)`.
- **API calls on init**: None. The token is not pre-validated on load; validity is discovered on submit (the backend rejects expired/invalid tokens at `POST /api/auth/reset-password`).
- **Initial model state (forgot)**: `email = ""`, `emailValidation = Pristine`, `submitState = NotAsked`.
- **Initial model state (reset)**: `token = <from URL>`, `password = ""`, `passwordConfirm = ""`, validations `Pristine`, `submitState = NotAsked`.

### Update cycle
**Forgot-password page:**
- **Msg**: `EmailChanged String` — updates `email`, runs `validateEmail`, resets `submitState`.
- **Msg**: `FormSubmitted` — calls `Api.forgotPassword { email = model.email }`, sets `submitState = Loading`.
- **Msg**: `GotForgotResponse (Ok ())` — sets a `RequestSent` view state; renders the neutral "if an account exists…" notice. OutMsg `NoOut`.
- **Msg**: `GotForgotResponse (Err err)` — sets `submitState = Failure err` (422 for missing email, 429 for rate limit, network error otherwise).

**Reset-password page:**
- **Msg**: `PasswordChanged String` — updates `password`, runs `validatePassword` (>= 8), re-validates `passwordConfirm` if non-empty.
- **Msg**: `PasswordConfirmChanged String` — updates `passwordConfirm`, runs `validatePasswordConfirm password confirm`.
- **Msg**: `FormSubmitted` — calls `Api.resetPassword { token = model.token, password = model.password }`, sets `submitState = Loading`.
- **Msg**: `GotResetResponse (Ok ())` — sets a `ResetComplete` view state; renders "Password updated — sign in". OutMsg `PasswordReset` (Main may `Nav.pushUrl "/login"`), or an in-page "Sign in" link.
- **Msg**: `GotResetResponse (Err (Http.BadStatus 400))` — the page must distinguish `token_expired` from `invalid_token` by decoding the `"error"` field of the body and show the matching message; both offer a "request a new link" path to `/forgot-password`.
- **Msg**: `GotResetResponse (Err (Http.BadStatus 422))` — surface the `details` map as field errors (primarily `password`).
- **Api client (new)**: `Api.forgotPassword` (decodes only `{"message": ...}` as unit — mirror the register-response fix from US-14.1.1 Bug 2, do *not* reuse `authResponseDecoder`) and `Api.resetPassword` (same unit-decode; on non-2xx, decode the `"error"` string so the page can branch on `token_expired` vs `invalid_token`).

## 13. Operational Metrics

- **Reset-request rate**: Count of `POST /api/auth/forgot-password` requests per day. A spike may indicate credential-stuffing probing or a UX regression in login.
- **Reset-completion rate**: Ratio of HTTP 200 `POST /api/auth/reset-password` responses to reset emails enqueued — the request → email → click → new-password funnel conversion.
- **Token-failure breakdown**: Counts of `token_expired` (400), `invalid_token` (400), and `validation_failed` (422) responses. High `token_expired` suggests the 24h window is too short or emails are delayed; high `invalid_token` may indicate link mangling by email clients or replay attempts.
- **Enumeration-probe signal**: Volume of forgot-password requests for emails that resolve to `nil` (no user). Because the response is uniform, this is only observable server-side via the `do_send_password_reset(nil)` path — worth logging as a metric without surfacing it to callers.
- **Rate-limiter trigger count**: HTTP 429s from the `:auth` bucket on these two endpoints, plus the count of reset emails suppressed by the per-user (10/hr) / global (100/hr) throttle.
- **Reset-email delivery rate**: Ratio of successfully delivered `password_reset` emails (via Resend) to `password_reset` jobs enqueued on the `:notifications` queue.

## 14. Performance & Usability Metrics

- **Request-to-email latency**: Time from `POST /api/auth/forgot-password` to the `EmailDeliveryJob` completing on the `:notifications` queue.
- **Email-to-click latency**: Time between reset-email delivery and the `/reset-password/:token` page load — indicates how promptly users act (and informs the 24h expiry choice).
- **Reset endpoint latency**: p50/p95 for `POST /api/auth/reset-password` (dominated by `Argon2.hash_pwd_salt/1` in `password_update_changeset/2`).
- **Client-side validation feedback latency**: Keypress-to-validation-state change on the reset form (should be <16ms, synchronous in Elm).
- **Reset abandonment rate**: Fraction of reset-page loads that never submit — flags confusion or password-rule friction.
- **Post-reset sign-in success rate**: Fraction of completed resets followed by a successful `POST /api/auth/login` within a short window — the true measure of "did the user regain access".

## 15. Cost Tracking

- **Resend**: One reset email per throttled request at ~$0.001/email. Bounded by the per-user (10/hr) and global (100/hr) caps, which also cap the blast radius of a reset-email flooding attempt.
- **Argon2 (Fly.io compute)**: One `Argon2.hash_pwd_salt/1` per successful reset (~200-400ms CPU on shared-cpu-1x, ~$0.0000025/s of CPU). Failed/invalid token attempts do NOT reach hashing — they short-circuit at `Phoenix.Token.verify/4` or the `get_by` lookup.
- **Database**: One `get_user_by_email` read + one token-write UPDATE per registered forgot-request; one `get_by` read + one password UPDATE per completed reset. Negligible Neon cost.
- **Oban job processing**: `EmailDeliveryJob` on `:notifications` — minimal compute; the cost is the Resend call, not the job.
- **No other external services**: Password reset does not touch vision, the scraper, R2, or any enrichment API.
- **Total per-completed-reset cost**: ~$0.001 (dominated by Resend email delivery; the Argon2 hash is absorbed into Fly.io machine billing).

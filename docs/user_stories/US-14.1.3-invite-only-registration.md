# US-14.1.3 — Invite-Only Registration (Closed Beta)

## 1. User Story

> **As a** platform owner, **I want** registration to be gated behind an invitation **so that** the closed beta admits only the people I have chosen, and the claim "currently in closed beta" is true rather than aspirational.

> **As an** invited reader, **I want to** redeem the invitation I was sent **so that** I can create my account and start shelving books.

**What they want to accomplish:** Two complementary goals. The owner needs a small, contained gate on account creation — no public sign-ups during the beta — and a way to hand out and revoke individual invitations. The invited reader needs redemption to feel like being handed a key, not like passing a checkpoint.

**How they accomplish it (owner):**
1. The owner signs in, verifies MFA, and opens `/admin/invites`.
2. They write a short private note ("Mara — book club"), optionally bind the invitation to one email address, set an expiry, and click "Write an invitation".
3. The invitation code is shown **once**, in full, with a copy button and a ready-made deep link.
4. They send it however they like — the platform does not send it for them.

**How they accomplish it (invited reader):**
1. The reader follows `https://<host>/login?invite=STK-4F2A-9C1D` (or types the code by hand).
2. The authentication page opens on the **Register** tab with the invitation code already filled and confirmed valid.
3. They fill in display name, email, password, and confirmation, and click "Request Entry".
4. Registration proceeds exactly as US-14.1.1 describes — the confirmation email is sent, and the "Check your inbox" pending state appears.

**What they see on the page (invited reader, code prefilled):**
- The login card carries a fifth field above Display Name, set apart by a hairline rule: **Invitation code**, monospaced, pre-filled and already showing the green valid border (`login-card__field--valid`).
- Beneath it, in the small caption voice: "Invitation accepted. Welcome — the door is open." If the invitation names an expiry within seven days, the caption adds "Expires 14 August."
- Everything else is the familiar Register form. No extra step, no separate page.

**What they see on the page (uninvited visitor):**
- The two tabs still read "Sign In" and "Register", because hiding the tab would be a small lie about what the platform is.
- Clicking **Register** does not show a form. The card body is replaced by a quiet panel (`login-card__invite-only`):
  > **The Stacks is in closed beta.**
  >
  > New accounts are opened by invitation for now — a small, trusted circle while the shelves are still being built. If you have a code, paste it below. If you don't, the [FAQ](/faq) explains what The Stacks is and how the beta works.
- Below the prose sits a single **Invitation code** field and a "Redeem" button. Entering a valid code reveals the full Register form in place. Nothing navigates; the card grows.
- No email capture, no waitlist form, no "request access" — the platform does not collect addresses from people it has not invited.

**Acceptance criteria:**
- `POST /api/auth/register` rejects a request with no invitation code, an unknown code, an expired code, a revoked code, or an exhausted code, whenever the gate is on.
- The gate is a runtime feature flag (`INVITE_ONLY_REGISTRATION`), read through `Stacks.FeatureFlags`, and surfaced to the SPA on `GET /api/config`. Flipping it off restores open registration with no code change.
- An invitation code is never stored in a readable form — only a SHA-256 hash plus a short display prefix.
- Redemption is atomic: two simultaneous redemptions of a single-use code produce exactly one account.
- An invitation consumed by a signup that is later reaped as abandoned is **restored**, not burnt — on **both** reap paths (registration-time and the nightly job). Performed inside `GDPR.Deletion.delete_user_data/2`, gated on an explicit opt.
- An invitation consumed by a real account that is **later erased at the user's own request** is **not** restored. A spent bearer credential must not come back to life.
- Email confirmation, onboarding (US-14.1.2), and login are untouched — the invitation is consumed at registration, never at confirmation.
- No invitation code, invitee email, or owner note is ever written to `event_log`.
- Erasing a user erases the note and bound email of any invitation that names them, and nulls their `redeemed_by_id`.

## 2. UI Interaction Flow

### Happy Path
1. Reader opens `/login?invite=STK-4F2A-9C1D`. `Main.initPage` passes the `invite` query parameter into `Login.init`.
2. `Login.init` sets `mode = RegisterMode`, `inviteCode = "STK-4F2A-9C1D"`, and fires `Api.checkInvite code`.
3. `GotInviteCheck (Ok Valid)` sets `inviteValidation = Valid` — green border, "Invitation accepted" caption.
4. Reader fills the four existing fields. Validation is exactly US-14.1.1's.
5. "Request Entry" is enabled only when all five validations pass.
6. `FormSubmitted` calls `Api.register { email, password, displayName, inviteCode = Just code }`.
7. HTTP 201 `{"message": "confirmation_email_sent"}` → `mode = RegistrationPending email`. Identical to US-14.1.1 from here on.

### Uninvited Path
1. Visitor opens `/login`, clicks the **Register** tab.
2. `Main`'s `serverConfig.inviteOnly` is `True`, so `Login.view` renders `viewInviteOnlyPanel` instead of the registration form.
3. Visitor pastes a code and clicks "Redeem" (`InviteSubmitted`) → `Api.checkInvite`.
4. `GotInviteCheck (Ok Valid)` → `inviteGateState = Unlocked`, the full Register form renders in place with the code field filled and locked.

### Sad Paths
- **Unknown or malformed code**: `GET /api/auth/invite/:code` returns 404. Field shows red border and: "We don't recognise that code. Check it against the message you were sent." The Register form stays closed.
- **Expired code**: 410 `{"error": "invite_expired"}`. Field message: "That invitation has expired. Ask whoever sent it for a fresh one."
- **Revoked code**: 403 `{"error": "invite_revoked"}`. Same wording as expired — the reader learns nothing about *why* it stopped working, and neither wording implies the code was ever valid for someone else.
- **Exhausted code**: 409 `{"error": "invite_exhausted"}`. "That invitation has already been used."
- **Email-bound code, different email**: registration returns 403 `{"error": "invite_email_mismatch"}`. "This invitation was written for a different email address."
- **Code races another redemption**: the losing request gets 409 `invite_exhausted`; no account is created for it.
- **Flag on, code omitted entirely** (e.g. a script posting straight at the API): 403 `{"error": "invite_required"}`.
- **`/api/config` unreachable**: `Main` treats `inviteOnly` as **True** on decode failure. Failing closed is the safe default for a gate — a config blip must not reopen public registration.

### Elm State Machine
- **Page module**: `Page.Login`
- **Model fields involved**: `inviteCode`, `inviteValidation`, `inviteGateState`, plus every US-14.1.1 field
- **Msg flow**: `InviteCodeChanged` → `InviteSubmitted` → `Api.checkInvite` → `GotInviteCheck` → `FormSubmitted` → `Api.register` → `GotRegisterResponse`
- **RemoteData states**: invite check is `NotAsked → Loading → Success InviteStatus / Failure Http.Error`
- **OutMsg pattern**: unchanged — `RegistrationSucceeded email` on success. The invitation adds no new OutMsg; it is a precondition, not an outcome.

## 3. API Calls

### `GET /api/auth/invite/:code`
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.InviteController.show/2`
- **Response (success)**: `{ "valid": true, "expires_at": "2026-08-14T00:00:00Z" | null, "email_bound": true | false }` — HTTP 200
- **Response (error)**: `{ "error": "invite_not_found" }` 404 · `{ "error": "invite_expired" }` 410 · `{ "error": "invite_revoked" }` 403 · `{ "error": "invite_exhausted" }` 409
- **Deliberately absent from the payload**: the owner's note, the bound email address (even masked), and the identity of anyone who has already redeemed it. The code is a bearer secret; a valid guess must reveal nothing about a person. `email_bound` is a boolean so the form can say "this invitation was written for a specific address" without naming it.

### `POST /api/auth/register` (extended)
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.AuthController.register/2`
- **Request body**: `{ "email": string, "password": string, "display_name": string, "invite_code": string }` — `invite_code` required when the flag is on, ignored when off
- **Response (success)**: `{ "message": "confirmation_email_sent" }` — HTTP 201
- **Response (error)**: `{ "error": "invite_required" | "invite_invalid" | "invite_expired" | "invite_revoked" | "invite_exhausted" | "invite_email_mismatch" }` — HTTP 403/409/410; `{ "errors": {...} }` — HTTP 422 for the existing changeset failures
- **Note**: the invitation is checked **inside** the registration `Ecto.Multi`, not in a plug. A plug would validate against a row that another request could consume before the insert lands.

### `GET /api/config` (extended)
- **Response**: `{ "ageGatingEnabled": bool, "inviteOnly": bool }` — the flat-map contract ADR-020 established, one more boolean.

### `GET /api/admin/invites`
- **Auth**: Owner + MFA
- **Pipeline**: `:api`, `:admin`, `:require_owner`, `:rate_limit_admin`
- **Controller**: `StacksWeb.InviteAdminController.index/2`
- **Response**: `{ "invites": [{ id, code_prefix, note, invited_email, max_uses, use_count, expires_at, revoked_at, redeemed_at, redeemed_by_handle, created_at }] }` — HTTP 200. `code_prefix` only; the full code is unrecoverable after issue.

### `POST /api/admin/invites`
- **Request body**: `{ "note": string | null, "invited_email": string | null, "max_uses": int (default 1), "expires_in_days": int | null (default 30) }`
- **Response**: `{ "invite": { id, code, code_prefix, ... } }` — HTTP 201. **The only response that ever contains `code`.**

### `DELETE /api/admin/invites/:id`
- **Response**: `{ "invite": { id, revoked_at } }` — HTTP 200. Revocation is a timestamp, not a row delete: the audit trail of who was invited during the beta is itself worth keeping.

## 4. Auth & Middleware Guards

- **Plugs fired (invite check / register)**: `SecurityHeaders` → `RateLimiter(bucket: :auth)`. Sharing the `:auth` bucket with login and password reset is deliberate (#373): a code-guessing sweep and a password-guessing sweep are the same attack against the same door, and one shared budget is what makes the 60/60s ceiling meaningful.
- **Plugs fired (admin)**: `SecurityHeaders` → `AdminAuthPipeline` → `RequireMFA` → `AuditAdminCall` → `RequireOwner` → `RateLimiter(bucket: :admin)`. `:require_owner` sits above `:admin` for the same reason the data-correction routes do (#340): an admin token outlives the role it was minted under, so the role is re-checked where the write happens.
- **Visibility checks**: N/A — no user content is involved.
- **Age gate**: N/A.
- **Ownership checks**: issuing and revoking are owner-only. A future `admin` role that is not `owner` must not be able to widen the beta.
- **Enumeration posture**: the invite lookup returns a distinct status per failure mode, which is safe only because the code space is large (128 bits of randomness behind a 4+4 display prefix) and the `:auth` limiter caps guessing at 60/minute/IP. Do not shorten the code to make it prettier.

## 5. Database Interactions

### Write: New table `op.invite_codes`
- **Proto source**: add `InviteCode` to `proto/stacks/common/v1/user.proto`, register it in `proto/persisted.exs`, then `mix proto.sync`. Do **not** hand-write the Ecto schema — `apps/core/lib/stacks/gen/accounts/invite_code.ex` is generated. Remember to `git add` the generated migration immediately; `mix test` deletes untracked `_add_*` migrations.
- **Columns**: `id` (uuid PK) · `code_hash` (text, NOT NULL, unique index) · `code_prefix` (text, NOT NULL) · `issued_by_id` (uuid FK `op.users`, ON DELETE SET NULL) · `note` (text, nullable) · `invited_email` (citext, nullable) · `max_uses` (int, NOT NULL, default 1) · `use_count` (int, NOT NULL, default 0) · `expires_at` (timestamptz, nullable) · `redeemed_by_id` (uuid FK `op.users`, ON DELETE SET NULL) · `redeemed_at` (timestamptz, nullable) · `revoked_at` (timestamptz, nullable) · timestamps
- **Indexes**: `invite_codes_code_hash_index` (unique) — the redemption lookup; `invite_codes_created_at_index` (desc) — the admin list.
- **Changeset validations**: `max_uses` >= 1, `invited_email` format when present, `note` length <= 500.
- **Code generation**: `:crypto.strong_rand_bytes(16)` → Base32 (Crockford, no ambiguous glyphs) → grouped as `STK-XXXX-XXXX`. `code_hash = :crypto.hash(:sha256, normalised_code)`. SHA-256 rather than Argon2 because the row must be *found* by its code; Argon2's per-row salt makes lookup impossible. The code is high-entropy and short-lived, so a fast hash is the right trade — unlike a password, it is not user-chosen and not reused elsewhere.

### Write: Redeem inside the registration transaction
- **Table(s)**: `op.invite_codes`, `op.users`
- **Operation**: SELECT … FOR UPDATE, then UPDATE
- **Transaction**: a new first step in `Accounts.register/1`'s `Ecto.Multi`, ordered **before** `:user`:
  1. `:lock_invite` — `from(i in InviteCode, where: i.code_hash == ^hash, lock: "FOR UPDATE")`. Returns `{:error, :invite_invalid}` on no row.
  2. `:validate_invite` — checks `revoked_at` is nil, `expires_at` is nil or future, `use_count < max_uses`, and `invited_email` is nil or matches the submitted email case-insensitively.
  3. `:user` — the existing insert.
  4. `:consume_invite` — `use_count + 1`; sets `redeemed_by_id` and `redeemed_at` on the first redemption only (a multi-use invitation records its first taker; per-redemption attribution is not worth a second table for a closed beta).
- The row lock is what makes the single-use guarantee real. A read-then-write without it lets two concurrent registrations both see `use_count = 0`.

### Write: Restore an invitation when an abandoned signup is reaped
- **Table(s)**: `op.invite_codes`
- **Operation**: UPDATE — `use_count - 1`, and null `redeemed_by_id`/`redeemed_at` when the reaped user was the recorded redeemer.
- **Why**: without this, a reader who mistypes their email, never confirms, and comes back to try again finds their one invitation already spent — locked out by a retention job. The reap already exists to stop an abandoned account blocking a real one; the invitation is the second thing it blocks.

#### Where it goes, and why not in the reap
⚠️ **Not in `reap_abandoned_signups/1`.** Three verified reasons (`apps/core/lib/stacks/accounts.ex:612`, `:627`):
1. It is **`defp`**, not public API — a story naming `Accounts.reap_abandoned_signups/1` implies a callable surface that does not exist.
2. There is **no transaction to join**. It is `Enum.each` over per-id `Deletion.delete_user_data/2` calls, each its own `Ecto.Multi`, and the whole body sits inside a `rescue` that deliberately swallows failures so a registration never fails over someone else's abandoned signup. A restore placed there could silently not happen.
3. **It is not the only reap path.** `Stacks.Workers.ExpiredUnverifiedAccountsJob` calls `Deletion.delete_user_data/2` **directly** (`expired_unverified_accounts_job.ex:29`) and never touches the reap — so a requirement placed in the reap would not apply to any cron-reaped account, which is most of them.

**Performed by**: `GDPR.Deletion.delete_user_data/2`, which is the one site all callers share.

#### ⛔ Conditional, not unconditional — `restore_invite: true`
`delete_user_data/2` already accepts `opts` (`:reason`, `:actor`). Add `:restore_invite`, defaulting to **false**:

| Caller | Passes `restore_invite:` | Why |
|---|---|---|
| `reap_abandoned_signups/1` (registration-time) | `true` | The invitee never got in. Burning their key is the bug. |
| `ExpiredUnverifiedAccountsJob` (nightly) | `true` | Same case, different trigger. |
| User-requested erasure (`DELETE /api/gdpr/account`) | *omitted* → `false` | **The invitation was legitimately spent.** |
| Owner break-glass erasure (`Stacks.Release.do_erase/2`) | *omitted* → `false` | Operator erasure is not evidence the signup was abandoned. |

**The user-requested case is where a plausible-sounding generalisation goes wrong.** "Erasing your account releases your invitation" reads as a courtesy, and is a security regression: the owner issued one key, a real beta participant redeemed it and used the platform for months, and on their way out the code in that months-old message becomes live again for anyone who still has it. The invitation was *consumed*, and consumption is not undone by the consumer leaving. Only an **abandoned** signup — one that never confirmed an email, so never became a participant at all — leaves the key unspent.

Do **not** infer this from `opts[:actor]`. The two reap paths do carry distinguishable actor strings (`"system:registration_reap"` and the job's own), but those are free-text audit labels; branching security behaviour on a log string breaks the first time someone improves the wording. An explicit boolean says what it means and fails closed.

### GDPR: erasure + export reachability
This story introduces personal data on a table `op.users` erasure does not reach by cascade, so both directions need explicit steps. Run the `gdpr-review` skill against the diff.

- **Erasure** (`GDPR.Deletion.delete_user_data/2`) gains **one** step, ordered before `:delete_user`:
  - `:settle_invites_naming_user` — for rows where `redeemed_by_id == user_id` **or** `invited_email` matches the user's email, in this order within the step:
    1. **Restore, only when `opts[:restore_invite]`** — `use_count - 1`, null `redeemed_at`.
    2. **Scrub, always** — set `note = nil`, `invited_email = nil`, `redeemed_by_id = nil`.
  - ⚠️ **The order is load-bearing and the two must not be separate steps.** The scrub nulls `redeemed_by_id`, which is the only thing identifying *which* invitation to restore. Scrub first — or scrub in an earlier step — and the restore silently matches nothing, on every reap, forever. A single ordered step makes that impossible to get wrong by reordering the Multi later.
  - The row survives either way (the beta's issue/revoke history is legitimate platform record-keeping), but every field that names a person is gone. Author-nulling alone would be a breach: `note` is owner-written free text about the invitee, and `invited_email` is the invitee's address.
  - **Test both branches.** `restore_invite: true` → `use_count` back to 0 and the code redeemable again; omitted → `use_count` stays 1 and a second redemption attempt gets `invite_exhausted`. A test that only exercises the reap path would let the spent-credential resurrection ship.
  - Rows where `issued_by_id == user_id` are handled by the FK's `ON DELETE SET NULL` — `issued_by_id` is a reference, not free text.
  - The `op.users` schema-sweep guard in `test/stacks/gdpr_test.exs` never inspects this table, so this step **is** the guarantee. Add a test that inserts an invitation naming the user, erases, and asserts `note` and `invited_email` are nil.
- **Export** (`GDPR.Export.export_user_data/2`) gains an `invitations` key: for invitations the user redeemed, `{ code_prefix, redeemed_at, expires_at }`. Deliberately excluded: `code_hash` (a credential), `note` (the *owner's* writing about them, not their own data — and disclosing it would expose the owner's private annotation), and any invitation they merely issued if they are the owner (that is platform-operations data, available via the admin surface).
- **Not written to `event_log`**: code, hash, note, invited email. The payload contract must reject them — add the assertion to `Stacks.Events.PayloadContract`.

## 6. Event Flow & Lifecycle

### Events Emitted

#### `invite.issued`
- **Aggregate**: `invite` / invite_id
- **Payload**: `%{max_uses: integer, expires_at: iso8601 | nil, email_bound: boolean}`
- **Emitted by**: `Stacks.Accounts.Invites.issue/2`
- **Emission method**: `Events.emit_safe/1`
- No code, no note, no address. `email_bound` is the boolean, never the address.

#### `invite.redeemed`
- **Aggregate**: `invite` / invite_id
- **Payload**: `%{user_id: uuid, use_count: integer}`
- **Emitted by**: `Stacks.Accounts.register/1` (inside the Multi)
- **Emission method**: `Events.emit_safe/1`
- `user_id` is a pointer, not content — the same shape `user.registered` already uses, and `GDPR.Deletion`'s `:scrub_event_log` step already redacts payloads that reference an erased user.

#### `invite.revoked`
- **Aggregate**: `invite` / invite_id
- **Payload**: `%{}` — the timestamp is the fact; the reason lives in the admin audit entry.

### Event Handlers Triggered
None registered. All three events are audit record only, in the `event_log`. The owner is the one issuing invitations, so there is nobody to notify.

### Audit Log
- `Audit.log(owner_id, "invite.issued" | "invite.revoked", resource_type: "invite", resource_id: id, ip: …)`. `AuditAdminCall` already logs the admin call itself; these entries name the *resource*, which is what the audit-log settings page (US-8.5) renders.

## 7. Background Jobs (Oban)

### `Stacks.Workers.ExpiredInvitesSweepJob` (new)
- **Queue**: `:default`
- **Schedule**: daily
- **Args**: `%{}`
- **What it does**: deletes invitations that expired more than 90 days ago **and** were never redeemed. An unredeemed expired invitation still holds the owner's note and possibly an invitee's email address — data about a person who never became a user and therefore can never exercise erasure. Nobody can ask for it to go, so the platform must drop it on a clock. This is the same reasoning as the 30-day image retention sweep.
- **On failure**: standard Oban retry. The sweep is idempotent.

No job is involved in redemption — that is synchronous inside the registration transaction.

## 8. External Service Calls

None. The platform deliberately does not email invitations: the owner sends them personally, through whatever channel they already use with that person. Adding an "invite by email" button would mean storing addresses for people who have not consented to anything and may never register — a new class of personal data for a small convenience.

The confirmation email that follows registration is unchanged (Resend, via `EmailDeliveryJob`).

## 13. Operational Metrics

- **Invite gate rejection count**: `:telemetry.execute([:stacks, :auth, :invite], %{count: 1}, %{result: :required | :invalid | :expired | :revoked | :exhausted | :email_mismatch | :ok})`. `result` is a bounded label derived from the outcome, never from user input, so `stacks_auth_invite_count_total{result=…}` stays low-cardinality. A spike in `invalid` is a code-guessing sweep; a spike in `expired` means the owner's expiry window is too short.
- **Registration outcome counter**: the existing `[:stacks, :auth, :registration]` counter is unchanged. Invite failures are counted on the invite event, not as registration errors, so the registration-failure alert does not fire on a working gate.
- **Invitations outstanding**: gauge — issued, not revoked, not expired, `use_count < max_uses`. The owner's real question ("how many keys are out there?").
- **Redemption latency**: time between `invite.issued` and `invite.redeemed` in `event_log`. A long tail means invitations are being sent and forgotten.
- **Rate limiter rejections**: `stacks_rate_limit_rejected_count_total{bucket="auth"}` — shared with login, so read it alongside the invite-result counter to tell guessing from a login storm.
- **Sweep job**: `ExpiredInvitesSweepJob` rows deleted per run, plus Oban completed/failed counts.

## 14. Performance & Usability Metrics

- **Invite-check endpoint latency**: p50/p95 for `GET /api/auth/invite/:code`. One indexed lookup on `code_hash` plus a SHA-256 — target p95 < 30ms.
- **Registration endpoint latency**: unchanged apart from one indexed `SELECT … FOR UPDATE`; Argon2 still dominates. Confirm the added lock does not measurably move p95.
- **Redemption conversion**: invitations redeemed / invitations issued. The single number that says whether the beta is actually filling.
- **Deep-link vs manual entry**: share of redemptions arriving with the `invite` query parameter already set. If manual entry is common, the copy button or the code format needs work.
- **Failed-then-succeeded rate**: readers who hit one invite error before succeeding. High means the code format is error-prone (ambiguous glyphs, case sensitivity).
- **Uninvited-visitor bounce**: share of visitors who open the Register tab, see the invite-only panel, and click through to `/faq` rather than leaving. The panel earns its place only if it sends people somewhere.

---

## 15. Cost Tracking

- **Compute**: one SHA-256 and one indexed lookup per check; a row lock per registration. Immaterial against Argon2's 200–400ms.
- **Database**: `op.invite_codes` holds one small row per invitation — hundreds of rows across a closed beta. Negligible Neon cost.
- **Email**: none added. The owner sends invitations by hand; the only email is the existing confirmation (~$0.001 via Resend).
- **Total per invitation**: effectively zero. The value is that it makes a beta claim true, not that it costs anything.

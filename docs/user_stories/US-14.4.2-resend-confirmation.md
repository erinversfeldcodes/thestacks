# US-14.4.2 — Resend Confirmation Email

## 1. User Story

> **As a** newly-registered reader who never received (or has lost) my confirmation email, **I want to** request that The Stacks send it again **so that** I can confirm my address and cross the threshold into the collection instead of being stranded outside a locked door.

Registration succeeds, the "check your inbox" card appears — and then nothing arrives. The email is caught in a spam filter, mistyped-but-valid inbox, a 48-hour-expired token, or a transient Resend outage. Today there is no way back: the user cannot log in (a 403 `email_unconfirmed` bars them) and cannot re-trigger the email. This story closes that dead-end with a single public, enumeration-safe, rate-limited endpoint and two frontend entry points.

**Acceptance criteria:**
- A public `POST /api/auth/resend-confirmation` endpoint accepts an email address and, if it belongs to an existing **unconfirmed** account, re-issues a fresh confirmation token and enqueues the same `registration_confirmation` email.
- **No email enumeration.** The endpoint returns an identical generic success response whether the email is unknown, already confirmed, or unconfirmed-and-resent. Timing and status code must not distinguish these cases. (Mirrors the existing `POST /api/auth/forgot-password` contract.)
- **Rate limited.** The endpoint sits behind the `:rate_limit_auth` pipeline (IP bucket, 60/60s) AND reuses the existing per-user (10/hr) and global (100/hr) email caps enforced in `Stacks.Email`. A user hammering resend cannot flood their own or others' inboxes.
- **Expired-token replacement.** If the account's original confirmation token has expired (>48h) or is otherwise stale, resend generates and persists a **new** signed `Phoenix.Token`, so the delivered link is always valid for a fresh 48h window. (The current `send_registration_confirmation/1` only re-delivers the persisted token — resend must re-sign.)
- **Already-confirmed no-op.** If the account is already confirmed (`email_confirmed == true`, token nulled), no email is sent, but the generic success response is still returned.
- **Frontend entry points.** A "Didn't get the email? Resend" action appears (a) on the `RegistrationPending` card and (b) on the 403-unconfirmed login error state, so both a just-registered user and a returning unconfirmed user can trigger a resend.
- The resend button shows a loading state, then a persistent "If that account exists and is unconfirmed, we've re-sent the confirmation email." confirmation, and enters a short client-side cooldown to discourage mashing.

**Technical note:** This is purely additive. No existing route, controller action, context function, event, or Oban worker changes behaviour. Resend is a thin new orchestration over machinery that already exists and is already tested by the registration flow.

There is **no** `POST /api/auth/resend-confirmation` route, **no** controller action, **no** `Stacks.Email` context function, and **no** frontend Msg/button/state. A returning unconfirmed user hits a hard dead-end: they are barred from login by a 403 and have no way to re-trigger the confirmation email.

- **Email rate limits** — `Stacks.Email.check_rate_limit/1` enforces a per-user 10/hr and global 100/hr cap by counting `EmailDeliveryJob` rows in `oban_jobs` (`apps/core/lib/stacks/email.ex:161-186`). Resend calls through this identical gate.
- **Confirmation route + redirect UX** — `GET /api/auth/confirm/:token` → `EmailVerificationController.confirm/2` (`apps/core/lib/core_web/router.ex:130-133`, `apps/core/lib/stacks_web/controllers/email_verification_controller.ex:14-24`).

- **Enumeration-safe reference pattern** — `AuthController.forgot_password/2` + `Email.send_password_reset/1` already implement the "always return a generic 200, never reveal existence" contract (`apps/core/lib/stacks_web/controllers/auth_controller.ex:153-157`, `apps/core/lib/stacks/email.ex:57-62,104-130`). Resend copies this shape.
- **Frontend scaffolding** — `Page.Login` already has the `RegistrationPending String` mode + `viewPendingCard` (`frontend/src/Page/Login.elm:65,308-325`) and already renders a specific 403-unconfirmed message via `httpErrorMessage` (`frontend/src/Page/Login.elm:647-648`). Both are the anchor points for the new resend action.

## 2. UI Interaction Flow

### Happy Path (from the RegistrationPending card)
1. User registers; `Page.Login` transitions to `RegistrationPending email` and shows the "Check your inbox!" card (`viewPendingCard`).
2. Below the "Back to Sign In" button, the card now shows a muted line: "Didn't get the email?" and a "Resend" button.
3. User clicks "Resend". The button enters a loading state (spinner, disabled).
4. The frontend calls `POST /api/auth/resend-confirmation` with `{ "email": <the pending email> }`.
5. Backend always returns HTTP 200 `{"message": "If that account exists and is unconfirmed, we've re-sent the confirmation email."}`.
6. The card swaps the button for a persistent confirmation line echoing that message, and starts a ~30s client-side cooldown before "Resend" can be clicked again.

### Happy Path (from the 403-unconfirmed login state)
1. A returning user with an unconfirmed email submits the Sign In form.
2. Backend returns HTTP 403 `email_unconfirmed`; `httpErrorMessage` renders "Please confirm your email address before signing in. Check your inbox for the confirmation email."
3. Immediately beneath that error, a "Resend confirmation email" button now appears (only in this 403 state).
4. Clicking it calls the same endpoint with the email currently typed in the form. Same loading → generic-success → cooldown behaviour as above.

### Sad Paths
- **Unknown / already-confirmed email**: Backend still returns the identical generic 200. The UI shows the same "if that account exists…" confirmation — it never reveals which case occurred. (By design; this is the anti-enumeration guarantee, not an error.)
- **Per-IP rate limit hit** (`:rate_limit_auth`, 60/60s): API returns HTTP 429 `{"error": "rate_limit_exceeded"}` with `Retry-After: 60`. UI shows: "Too many attempts. Please wait a minute and try again."
- **Per-user / global email cap hit** (10/hr or 100/hr): the context silently declines to enqueue but the endpoint **still returns the generic 200** (no email actually goes out). The user simply won't receive another email until the window rolls; the UI cannot and must not distinguish this from success.
- **Missing email field**: API returns HTTP 422 `{"error": "email is required"}`. UI shows: "Please enter your email address."
- **Network error**: UI shows "The library is unreachable. Please try again." and re-enables the button.

### Elm State Machine
- **Page module**: `Page.Login`
- **New Model fields**: `resendState : RemoteData Http.Error ()` (or a dedicated `ResendState = ResendIdle | ResendSending | ResendSent | ResendFailed Http.Error`), `resendCooldownUntil : Maybe Time.Posix` (optional, for the cooldown gate).
- **New Msg flow**: `ResendConfirmationClicked → Api.resendConfirmation email → GotResendResponse (Ok () | Err _)` → update `resendState`.
- **RemoteData states**: `ResendIdle → ResendSending → ResendSent` (terminal, with cooldown) or `ResendFailed err`.
- **OutMsg pattern**: `NoOut` — resend is self-contained within `Page.Login`; it does not navigate, store a JWT, or notify Main.

## 3. API Calls

### `POST /api/auth/resend-confirmation`  *(new)*
- **Auth**: None (public).
- **Pipeline**: `:api`, `:rate_limit_auth` — placed in the same router scope as `register` / `login` / `forgot-password` (`core_web/router.ex:122-128`). Chosen because resend is an unauthenticated, email-sending, enumeration-adjacent surface identical in risk profile to `forgot-password`; the `:auth` bucket (60/60s per trusted client IP) is the correct throttle and no new bucket is warranted.
- **Controller**: `StacksWeb.AuthController.resend_confirmation/2` *(new action)*.
- **Request body**: `{ "email": string }`
- **Response (success)**: `{ "message": "If that account exists and is unconfirmed, we've re-sent the confirmation email." }` — **HTTP 200**, returned unconditionally for known-unconfirmed, unknown, and already-confirmed emails alike.
- **Response (error)**:
  - `{ "error": "email is required" }` — HTTP 422 (missing param; the only shape-level error).
  - `{ "error": "rate_limit_exceeded" }` — HTTP 429 with `Retry-After: 60` (from the `RateLimiter` plug, before the controller runs).
- **FallbackController handling**: none needed — the controller never returns an error tuple for a valid-shaped request; it always renders the generic 200 (matching `forgot_password/2`).

### `GET /api/auth/confirm/:token`  *(existing, unchanged)*
- The re-issued token is delivered in an email whose link points here; verification is identical to the registration flow (`EmailVerificationController.confirm/2`).

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` → `RateLimiter` (bucket: `:auth`, keyed on the trusted `fly-client-ip`, 60 requests / 60s — `rate_limiter.ex:54,110,169-173`).
- **No authentication required.**
- **Enumeration defence** lives in the context/controller layer, not a plug: the response is invariant across the unknown / confirmed / unconfirmed branches, mirroring `send_password_reset/1`'s `nil`-user no-op.
- **Visibility / Age gate / Ownership**: N/A.

## 5. Database Interactions

### Read: Look up user by email
- **Table(s)**: `op.users`
- **Query**: `Accounts.get_user_by_email(email)` — `Repo.get_by(User, email: String.downcase(email))` (same lookup used by `send_password_reset/1`).
- **Schema module**: `Stacks.Accounts.User`

### Write: Re-issue confirmation token (only for an existing, unconfirmed user)
- **Table(s)**: `op.users`
- **Operation**: UPDATE via `Accounts.email_confirmation_changeset/2` (`accounts.ex:121-124`) setting a freshly signed `email_confirmation_token` (and `email_confirmed: false`, already the case).
- **Guard**: skip entirely when `user == nil` (unknown) or `user.email_confirmed == true` (already confirmed) — no write, no email, generic 200.
- **Transaction**: token UPDATE + `EmailDeliveryJob` insert wrapped in a single `Repo.transaction` so a job-insert failure rolls back the token write — the exact pattern already used by `do_send_password_reset/1` (`email.ex:112-127`).
- **Changeset validations**: `email_confirmation_changeset/2` casts only `email_confirmation_token` and `email_confirmed`.

### Read: Email rate-limit counters
- **Table(s)**: `public.oban_jobs`
- **Query**: `check_rate_limit/1` counts `Stacks.Workers.EmailDeliveryJob` rows for this `user_id` (per-user) and overall (global) within the last hour (`email.ex:161-186`). Reused verbatim.

## 6. Event Flow & Lifecycle

### Events Emitted
- **None.** Unlike registration (which emits `user.registered` to *trigger* the confirmation email via `EmailConfirmationHandler`), resend is a direct, synchronous call from the controller into `Stacks.Email` — it does not emit an event and does not go through the event bus. This avoids a second `user.registered` and keeps resend idempotent.

### Event Handlers Triggered
- **None.** `EmailConfirmationHandler` (`stacks/notifications/email_confirmation_handler.ex`) is **not** involved in resend; it only fires on `user.registered`.

## 7. Background Jobs (Oban)

- **Worker**: `Stacks.Workers.EmailDeliveryJob` *(existing, unchanged)*
- **Queue**: `:notifications`
- **Args**: `%{"template" => "registration_confirmation", "user_id" => user_id, "params" => %{"token" => <freshly re-issued token>}}`
- **Max attempts**: 3
- **Rate limiting**: gated by `Stacks.Email.check_rate_limit/1` (per-user 10/hr, global 100/hr) *before* enqueue — shared with registration and password-reset emails.
- **What it does**: `registration_confirmation` bypasses notification prefs (`@bypass_prefs`), builds `CoreWeb.Endpoint.url() <> "/api/auth/confirm/#{token}"`, and delivers via Swoosh/`Mailer` (`email_delivery_job.ex:76-85`).
- **On success**: confirmation email delivered with a link valid for 48h.
- **On failure**: standard Oban retry (3 attempts); unknown-template jobs are `:discard`ed (not applicable here — template is known).

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.Login` (`/login`) — resend is an action within the existing login page, not a new route.
- **Public or authenticated**: Public.

### Init
- **`initPage` branch**: `Route.Login → PageLogin Login.init` (unchanged).
- **New initial state**: `resendState = ResendIdle`, `resendCooldownUntil = Nothing`.

### Update cycle
- **Msg**: `ResendConfirmationClicked`
  - **Model change**: `resendState = ResendSending`.
  - **Cmd**: `Api.resendConfirmation { email = resolvedEmail } GotResendResponse`, where `resolvedEmail` is the `RegistrationPending email` payload when on the pending card, or `model.email` when in the 403-unconfirmed login state.
  - **Guard**: no-op if within cooldown (`resendCooldownUntil` in the future) or already `ResendSending`.
  - **OutMsg**: `NoOut`.
- **Msg**: `GotResendResponse (Ok ())`
  - **Model change**: `resendState = ResendSent`, set `resendCooldownUntil = now + 30s`.
- **Msg**: `GotResendResponse (Err err)`
  - **Model change**: `resendState = ResendFailed err`; button re-enabled (except on 429, where the cooldown message is shown).

### New Api function
- `Api.resendConfirmation : { email : String } -> (Result Http.Error () -> msg) -> Cmd msg`
  - Mirrors `Api.register` (`frontend/src/Api.elm:263-279`) but posts to `/api/auth/resend-confirmation` and decodes only the presence of `"message"` (unit result). A 429 surfaces as `Http.BadStatus 429`.

### View
- **On the RegistrationPending card** (`viewPendingCard`, `Login.elm:308-325`): add, above "Back to Sign In", a `p [ class "login-card__resend-prompt" ]` reading "Didn't get the email?" followed by a `button [ testId "resend-confirmation" ]`. In `ResendSending` the button shows `spinner spinner--small` and is disabled; in `ResendSent` it is replaced by a `p [ class "login-card__resend-sent", attribute "aria-live" "polite" ]` with the generic confirmation text.
- **On the 403-unconfirmed login error** (rendered near `Login.elm:589`, driven by `httpErrorMessage … (Http.BadStatus 403)`): render the same "Resend confirmation email" button immediately below the error line, wired to `ResendConfirmationClicked`. Only shown when the current `SubmitError` is the 403 case.
- **ARIA**: the resend outcome region is `aria-live="polite"`; the button carries `aria-busy="true"` while `ResendSending`.
- **CSS classes / test hooks**: `login-card__resend-prompt`, `login-card__resend`, `login-card__resend-sent`; `testId "resend-confirmation"` and `testId "resend-confirmation-sent"` for E2E reference.

## 14. Operational Metrics

- **Resend request rate**: count of `POST /api/auth/resend-confirmation` requests per hour/day. A sustained spike indicates a systemic delivery problem upstream (registration email not arriving).
- **Resend-to-confirmation conversion**: ratio of resend requests followed by a successful `GET /api/auth/confirm/:token` within 48h. Low conversion suggests deliverability or token-link issues.
- **Enumeration-probe signal**: rate of resend requests for emails that resolve to `nil` or already-confirmed accounts (measurable server-side only). A high proportion from one IP flags credential-stuffing / enumeration probing.
- **Rate-limit trigger count**: HTTP 429s from the `:auth` bucket on this route, plus per-user/global email-cap declines inside `check_rate_limit/1`.
- **Email delivery reliability**: ratio of `registration_confirmation` jobs enqueued *by the resend path* that Resend delivers successfully (shared `:notifications` queue metric, segmented by trigger).

## 15. Performance & Usability Metrics

- **Resend endpoint latency**: p50/p95 for `POST /api/auth/resend-confirmation` (one email lookup + one token sign + one UPDATE + one job insert — should be well under registration latency, since no Argon2 hashing occurs).
- **Time-to-recovery**: elapsed time from a user's first 403-unconfirmed login to a successful confirmed login, before vs after this feature ships. This is the core UX metric the story exists to move.
- **Resend button engagement**: click-through rate on the "Resend" action from (a) the pending card and (b) the 403 login state — reveals which entry point users actually reach.
- **Cooldown friction**: rate of resend clicks blocked by the client-side cooldown; if high, the 30s window may be too aggressive.
- **Support-ticket deflection**: reduction in "I never got my confirmation email" support requests once a self-service path exists.

## 16. Cost Tracking

- **Resend (email)**: ~$0.001 per re-sent confirmation email. Bounded above by the per-user 10/hr and global 100/hr caps, so worst-case incremental cost is small and hard-limited even under abuse.
- **Database**: one `Repo.get_by` (email lookup) + one UPDATE (token) + one `oban_jobs` INSERT per genuine resend; unknown/confirmed emails incur only the lookup. Two `count` queries on `oban_jobs` for the rate check. Negligible Neon cost.
- **Compute**: `Phoenix.Token.sign` is HMAC — sub-millisecond. **No Argon2** on this path, so per-request CPU cost is far below register/login.
- **Oban processing**: one `EmailDeliveryJob` on the shared `:notifications` queue; the real cost is the Resend API call, not the job.
- **Total per genuine resend**: ~$0.001 (dominated by Resend delivery); ~$0 for the no-op (unknown / already-confirmed / rate-capped) branches.

# US-19.1.2 — Keyboard Navigation

## 1. User Story

> **As a** keyboard-only user, **I want to** navigate between shelves, browse books, and open detail overlays using only the keyboard **so that** I can use the platform without a mouse.

**Acceptance criteria:**
- All interactive elements are reachable via Tab
- Arrow key navigation works within the bookshelf grid (BUILT — #388, 2026-08-09; see the column-model decision below)
- Focus returns to the triggering element when an overlay is closed
- Skip links are provided to jump past navigation to main content
- Focus indicators are visible and styled consistently with the platform aesthetic

---

## 2. UI Interaction Flow

### What Exists in the Codebase

**Skip Link**:
- `a [ class "skip-link", href "#main-content" ] [ text "Skip to main content" ]` — rendered first in the app layout.
- `main_ [ id "main-content" ]` — the target of the skip link.
- CSS: `.skip-link` is positioned off-screen (`top: -100%`). On focus, `.skip-link:focus` moves it to `top: 0` with a visible outline.

**Escape Key Handling** (Main.elm subscriptions):
- Global `Browser.Events.onKeyDown` subscription listens for the Escape key.
- If a `bookDetailOverlay` is open: closes the overlay and returns focus to the triggering spine element (`Browser.Dom.focus ("spine-" ++ bookId)`).
- If no overlay: closes the user menu dropdown (`UserMenu.Close`).

**Focus Management for Overlays**:
- When a book detail overlay opens: `Browser.Dom.focus "book-overlay-close"` moves focus to the close button.
- When the overlay closes: `Browser.Dom.focus spineId` returns focus to the spine that triggered it (stored as `triggerSpineId = Just ("spine-" ++ bookId)` in the overlay model).

**Focus Indicators** (CSS):
- `*:focus-visible` — amber outline (`2px solid #d4a029`, `outline-offset: 2px`) on all focusable elements.
- Specific overrides for `.book-button:focus-visible`, `.book-overlay__close:focus-visible`, `.btn:focus-visible`, `.app-nav__link:focus-visible`.
- `.book-pile__book:focus-visible .book` — accent-colored outline for book pile items.

**Tab Order**:
- Standard HTML tab order: skip link -> navigation items -> main content -> footer.
- Navigation links are `<a>` elements (naturally focusable).
- Buttons are `<button>` elements (naturally focusable).
- The user menu dropdown is keyboard-navigable (trigger button -> dropdown items).

### What Is Missing (per spec)
- ~~**Arrow key navigation within bookshelves**~~ — BUILT by #388 (2026-08-09): roving-tabindex arrow-key navigation over the bookcase grid, nearest-x column model. See the decision below.
- **Focus trapping in overlays**: The spec calls for focus trapping within the book detail overlay. Currently, focus is moved to the close button on open, but there is no focus trap preventing tabbing outside the overlay.
- **Tab from last nav item to first shelf item**: Standard browser tab order handles this naturally if elements are in DOM order.

### Decision — column model for ↑/↓ over the width-packed grid (#388, owner-decided, BUILT 2026-08-09)

> **Decision: nearest-x.** A vertical move lands on the book in the adjacent row whose
> horizontal centre is closest to the current book's centre. The grid is width-packed
> (`groupIntoRows` fills ~990px per row from variable spine widths), so there is no stable
> column index for "same column" to mean; nearest-x is what the eye does scanning up a real
> bookcase of uneven spines. Ties go to the earlier book so repeated ↑↓ does not drift.
>
> **Built as:** `Page.Bookshelf.GridNav` — a pure function over rows of `(bookId, spineWidth)`
> using the SAME widths the packer laid the rows out with (`placementSpineWidth`). One tab
> stop per bookcase (roving tabindex: the last arrow-focused spine, else the first); ←/→
> within a row, ↑/↓ nearest-x between rows, Home/End to row ends; the keydown decoder claims
> exactly those six keys, so Tab keeps tabbing and Enter/Space keep clicking. Keydown is
> handled ON the spine buttons — deliberately not a global subscription — so `Main.elm`'s
> Escape/overlay focus routing is untouched. Focus ring: the existing amber
> `.book-button:focus-visible` outline (motion-free, so reduced-motion safe).

### Decision — grid arrow-key navigation was DEFERRED in Wave 8 (#318, phase 8f) — since built by #388

> **Decision:** The bookcase/shelf grid is reachable and operable by keyboard **today** — every spine renders as a real `<button class="book-button">` (`Page.Bookshelf.Helpers.viewClickableSpine`), so each is a natural Tab stop and opens its detail overlay on Enter/Space, and Escape returns focus to the triggering spine. **Full roving-tabindex arrow-key navigation across the grid is deferred to a dedicated a11y issue** and is NOT built in Wave 8.
>
> **Rationale.**
> 1. **It is not a reachability gap, it is an ergonomics improvement.** WCAG 2.1 2.1.1 (Keyboard) is already satisfied — nothing on the bookcase is keyboard-unreachable. Arrow-key roving is a "better than Tab" enhancement (a composite-widget convenience), not a defect that locks anyone out. Wave 8's a11y follow-through is scoped to closing genuine gaps (unlabelled controls, un-announced progress, touch/keyboard-unreachable disclosures), and this is not one.
> 2. **Cost is real and cross-cutting.** A correct roving-tabindex implementation over the bookcase means: a single tabindex="0" / tabindex="-1" ownership model across a two-dimensional, width-packed grid whose row membership is computed at render (`groupIntoRows` packs by spine width, not a fixed column count, so "up/down" has no stable column to land on); a keydown handler and focus-management commands (`Browser.Dom.focus`) threaded through `Page.Bookshelf`'s two Msg families; and interaction with the existing global Escape/overlay focus-return logic in `Main.elm`. That is a new stateful widget, well beyond an "add an attribute" touch-up, and it would need its own live AT/keyboard drive across browsers to prove it does not regress the current clean Tab order.
> 3. **The grid geometry needs a design answer first.** Because rows are width-packed and variable-length, up/down arrow behaviour (nearest-column? wrap? clamp?) is a genuine UX decision, not a mechanical one. Building it before that decision is made would bake in an arbitrary answer.
>
> **What this leaves for the dedicated issue:** roving-tabindex ownership over `shelf-row__books` items, arrow-key keydown handling with a defined up/down column model, and a cross-browser keyboard + screen-reader drive. Acceptance criterion in this story's list ("Arrow key navigation works within the bookshelf grid") is therefore marked **deferred**, not done.
>
> ⚠️ **Owner nod wanted** on the defer-vs-build call and on whether the dedicated issue is cut now or parked until a reader actually asks for arrow-key browsing.

## 12. Elm Frontend State Machine (Detail)

### Route
N/A — Keyboard navigation is a cross-cutting concern.

### Subscriptions (Main.elm)
```elm
subscriptions _ =
    Sub.batch
        [ ...
        , Browser.Events.onKeyDown
            (Decode.field "key" Decode.string
                |> Decode.andThen
                    (\key ->
                        if key == "Escape" then
                            Decode.succeed EscapePressed
                        else
                            Decode.fail "not handled"
                    )
            )
        ]
```

### Update cycle (Main.elm)
- **Msg**: `EscapePressed`
  - If `bookDetailOverlay` is `Just overlay`:
    - Set `bookDetailOverlay = Nothing`
    - Return focus: `Browser.Dom.focus spineId` (where `spineId = "spine-" ++ bookId`)
  - If `bookDetailOverlay` is `Nothing`:
    - Close user menu: `UserMenu.update UserMenu.Close model.userMenu`
- **Msg**: `FocusResult` — no-op (handles the `Result` from `Browser.Dom.focus`)

### Focus Management in `openOverlay`
```elm
openOverlay model bookId =
    ...
    overlay = { bookId = bookId, detail = detailModel, triggerSpineId = Just ("spine-" ++ bookId) }
    ...
    Cmd.batch
        [ Cmd.map OverlayBookDetailMsg detailCmd
        , Task.attempt (always FocusResult) (Browser.Dom.focus "book-overlay-close")
        ]
```

### CSS Focus Indicators
- All elements: `*:focus-visible { outline: 2px solid #d4a029; outline-offset: 2px; }`
- Books: `.book-pile__book:focus-visible .book { outline: 2px solid var(--accent); outline-offset: 2px; }`
- Skip link: `.skip-link:focus { top: 0; outline: 2px solid var(--text); }`
- Reduced motion: CSS includes `@media (prefers-reduced-motion)` considerations.

## 13. Operational Metrics

- **Keyboard-only session rate**: Percentage of sessions where no mouse/touch events are detected (proxy for keyboard-only users). Requires client-side interaction tracking.
- **Skip link usage rate**: Count of skip link activations (focus + Enter on `#main-content` anchor). Indicates screen reader and keyboard user activity.
- **Escape key event rate**: Count of `EscapePressed` Msg dispatches per session. Breakdown by context: overlay close vs user menu close.
- **Focus management success rate**: Percentage of overlay open/close cycles where `Browser.Dom.focus` succeeds (vs `FocusResult` returning an error).
- **Tab order completeness**: Automated test coverage verifying all interactive elements are reachable via Tab.

---

## 14. Performance & Usability Metrics

- **Keyboard navigation coverage**: Percentage of platform features accessible via keyboard alone. Target: 100%. Currently missing: arrow key navigation within bookshelves, focus trapping in overlays.
- **Tab stop count per page**: Number of Tab presses required to reach key actions on each page. Lower is better — skip links help reduce this for main content.
- **Focus trap completeness**: Whether overlays properly trap focus (currently not implemented — focus can Tab outside the overlay).
- **Focus indicator visibility score**: Manual assessment of whether focus outlines are visible on all interactive elements across all background colors.
- **Escape key discoverability**: Whether keyboard users discover that Escape closes overlays and menus (no visual hint currently provided).
- **Arrow key navigation gap**: The spec requires arrow keys for bookshelf grid navigation, which is not implemented. Track as an accessibility compliance gap.
- **Reduced motion compliance**: Whether `@media (prefers-reduced-motion)` correctly disables or reduces all animations.

---

## 15. Cost Tracking

- **No operational costs**: Keyboard navigation is purely frontend behaviour. No API calls, no database reads, no external services.
- **Focus management overhead**: `Browser.Dom.focus` calls are negligible runtime cost (<1ms per call).
- **Subscription cost**: Global `Browser.Events.onKeyDown` subscription runs on every keypress. Negligible CPU — the decoder fails fast for non-Escape keys.
- **Total runtime cost**: $0.00.

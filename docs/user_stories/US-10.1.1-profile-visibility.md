# US-10.1.1 — Set Profile Visibility

## 1. User Story

> **As a** user, **I want to** control who can see my profile **so that** I can choose whether to be discoverable on the platform or remain completely private.

The user navigates to Profile Settings > Privacy and chooses a profile visibility level:
- **Owner only** -- the profile is completely invisible to all other users. No one can find, follow, or see any trace of this account. Effectively a ghost mode.
- **Platform users** -- any logged-in user can find the profile and see whichever shelves, posts, and placements are set to platform-level visibility.

The change takes effect immediately.

**Ceiling rule:** all shelves, placements, and blog posts are subject to the profile visibility ceiling -- content cannot be more visible than the profile that contains it. The `looking_for_home` shelf is not exempt from this rule; it simply has a different *default* visibility that activates when the profile is discoverable.

---

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/settings/privacy`.
2. Page renders with "Profile Visibility" section showing a two-option selector: "Only me" and "Discoverable."
3. User selects desired visibility.
4. User clicks "Save Profile Visibility."
5. System sends `PUT /api/settings/profile_visibility`.
6. Backend updates the user record, emits `user.profile_visibility_changed` event, and enqueues a `VisibilityRecapJob`.
7. The recap job asynchronously caps all bookshelves, placements, and blog posts to the new ceiling.
8. UI shows "Saved!" confirmation.

### Sad Paths
- **Invalid visibility value**: `User.profile_visibility_changeset/2` rejects invalid values, returning changeset errors. HTTP 422.
- **Missing parameter**: Returns HTTP 422 with `{ error: "profile_visibility parameter is required" }`.
- **Save failure**: Elm model transitions to `Failure`, showing "Could not save. Please try again."

### Elm State Machine
- **Page module**: `Page.Settings.Privacy`
- **Model fields involved**: `profileVisibility : String`, `savingProfile : RemoteData Http.Error ()`
- **Msg flow**: `SetProfileVisibility String -> SaveProfileVisibility -> SaveProfileVisibilityCompleted (Ok/Err)`
- **RemoteData states**: NotAsked -> Loading -> Success / Failure

## 5. Database Interactions

### Write: Update profile visibility
- **Table(s)**: `op.users`
- **Operation**: UPDATE
- **Fields**: `profile_visibility` (valid values: `"owner"`, `"platform"`)
- **Changeset validations**: Via `User.profile_visibility_changeset/2` -- validates inclusion
- **Module**: `Stacks.Accounts.update_profile_visibility/2`

### Write: Visibility recap (async, via `VisibilityRecapJob`)
- **Table(s)**: `op.bookshelves`, `op.bookshelf_placements`, `op.blog_posts`
- **Operation**: UPDATE (batch)
- **Bookshelves**: `from b in Bookshelf, where: b.user_id == ^user_id and b.visibility in ^violating` -- set visibility to new ceiling
- **Placements**: `from p in Placement, join: b in Bookshelf, where: b.user_id == ^user_id and p.visibility in ^violating` -- set visibility to new ceiling
- **Blog posts**: `Blog.tighten_posts_to_ceiling(user_id, new_visibility)` -- updates posts whose visibility is less restrictive than the new ceiling

## 6. Event Flow & Lifecycle

### Events Emitted
- **Event type**: `user.profile_visibility_changed`
- **Aggregate**: type `"user"`, ID is the user UUID
- **Payload**: `%{visibility: "owner" | "platform"}`
- **Emitted by**: `Stacks.Accounts.update_profile_visibility/2`
- **Emission method**: `Events.emit_safe/1`

- **Event type**: `user.visibility_recap_completed` (from the background job)
- **Aggregate**: type `"user"`, ID is the user UUID
- **Payload**: `%{new_visibility: String, bookshelves_capped: integer, placements_capped: integer, posts_capped: integer}`
- **Emitted by**: `Stacks.Workers.VisibilityRecapJob.perform/1`
- **Emission method**: `Events.emit_safe/1`

### Event Handlers Triggered
No handlers are registered for `user.profile_visibility_changed` in the Events Registry. The recap job is enqueued directly by `Accounts.update_profile_visibility/2`, not via event handlers.

## 7. Background Jobs (Oban)

### `Stacks.Workers.VisibilityRecapJob`
- **Worker**: `Stacks.Workers.VisibilityRecapJob`
- **Queue**: `:default`
- **Args**: `%{ "user_id" => user_id, "new_visibility" => "owner" | "platform" }`
- **Max attempts**: 3
- **Uniqueness**: None configured
- **What it does**:
  1. Determines which visibility values violate the new ceiling:
     - If ceiling is `"owner"`: violating values are `["platform", "group"]`
     - If ceiling is `"platform"` or anything else: no violations (empty list, job exits early)
  2. Batch-updates all bookshelves with violating visibility to the new ceiling.
  3. Batch-updates all placements (joined through bookshelves) with violating visibility.
  4. Calls `Blog.tighten_posts_to_ceiling/2` to cap all posts in a transaction.
  5. Emits `user.visibility_recap_completed` event with counts.
- **On success**: Logs counts. Returns `:ok`.
- **On failure**: Logs exception with stacktrace. Returns `{:error, exception}` for retry.
- **Important note**: The visibility change is already enforced at read time by `Stacks.Visibility.resolve_visibility/2` regardless of stored values. The recap job brings stored values into sync -- this is a correctness-of-stored-state issue, not a security issue.

## 13. Operational Metrics

- **Visibility change event count**: Total `user.profile_visibility_changed` events, segmented by new visibility value (`"owner"` vs. `"platform"`). Tracks how often users tighten or loosen their profile visibility.
- **Visibility recap job outcome rate**: Success vs. failure counts for `VisibilityRecapJob`. Failures indicate cascading update issues across bookshelves, placements, or blog posts.
- **Recap cap counts**: From the `user.visibility_recap_completed` event payload: `bookshelves_capped`, `placements_capped`, `posts_capped`. Measures the blast radius of each profile visibility tightening.
- **Direction ratio**: Tightening (to "owner") vs. loosening (to "platform") changes. A spike in tightening may indicate a privacy concern or platform trust issue.

---

## 14. Performance & Usability Metrics

- **Visibility recap job duration**: Wall-clock time for `VisibilityRecapJob` to batch-update all violating bookshelves, placements, and blog posts. Scales with the user's content volume. Important because stored-state consistency depends on this job completing.
- **Recap batch sizes**: Number of rows updated per entity type (bookshelves, placements, posts). Large batches for power users may require monitoring.
- **Profile visibility save latency**: Round-trip time from `PUT /api/settings/profile_visibility` to HTTP 200. The synchronous part (user record UPDATE + event emit + job enqueue) should be fast; the async recap runs separately.
- **Time from save to recap completion**: Measures the window during which stored visibility values may be stale (read-time enforcement via `resolve_visibility/2` still protects during this window).

---

## 15. Cost Tracking

- **Neon**: Compute cost for the synchronous UPDATE on `op.users` (minimal) plus the async `VisibilityRecapJob` batch UPDATEs across `op.bookshelves`, `op.bookshelf_placements`, and `op.blog_posts`. Recap cost scales with user content volume.
- The recap job is the most expensive operation: it performs three separate batch UPDATEs plus a transactional `Blog.tighten_posts_to_ceiling/2` call. Users with hundreds of placements and posts will have higher per-change compute cost.
- No external service calls, no storage operations, no email notifications. Cost is purely Neon compute for DB writes.

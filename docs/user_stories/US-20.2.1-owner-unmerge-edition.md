# US-20.2.1 — Split a Wrongly Merged Edition Back Off Its Work (Owner Only)

## 1. User Story

> **As the** platform owner, **I want** a reviewed way to reverse a bad edition merge **so that** an ISBN stops resolving to the wrong book for every reader who scans it — without me opening a `psql` session against production.

**Owner ruling, 2026-07-30:** this is an **owner-side data correction, not public UI**. Built as Issue #376 on the #339/#340 data-correction mechanism. Written 2026-08-06 from the code; every claim cites the implementation.

**Family US-20.2.x** is *owner-side data correction*, within the new US-20.x (Platform Owner / Operations) family. Its sibling US-20.1.1 is the admin MFA gate that makes this reachable at all.

**What the owner wants to accomplish:** `Stacks.Books.merge_edition/2` is a one-way door. It writes a second `op.book_editions` row under an existing work, and nothing takes it back. When the merge was wrong — the ISBN names a genuinely different book, not another format of the same one — three things are true and stay true:

- the work permanently claims a book it is not;
- the ISBN permanently resolves to the wrong title for every reader who scans it, because `Books.find_existing/1` looks the edition up and returns its **parent**;
- the only recourse was a shell on production.

**How they accomplish it:**
1. Sign in through the admin gate (US-20.1.1) — owner role, second factor, 30-minute session.
2. `GET /api/admin/data_corrections` to see every registered correction, its scope, its reversibility, and the rows it *would* change right now. Writes nothing: **dry-run is what a GET means**.
3. `POST /api/admin/data_corrections/unmerge_edition/target` with `{argument: {edition_id, title}, reason: "…"}` and **no `apply`** — a dry run that reports the blast radius.
4. Read the plan. It names the work the edition is leaving, the title it will become, and **how many placements stay behind**.
5. Repeat with `apply: true`. One row moves, one work is minted, two audit-recorded column swaps, and the book detail cache is evicted for both works.

**What the owner sees:** JSON. There is no admin page for this — deliberately. The correction is three verbs and no more, and a form would invite a fourth.

**Acceptance Criteria:**
- Owner-only, behind MFA, with the role re-checked at the point of write.
- `reason` is mandatory and is recorded verbatim in the audit row, in the same transaction as the change.
- Dry-run is the default and reports the blast radius before anything is written.
- Only a *registered* correction name is reachable — no table, column, or predicate parameter.
- The new work inherits `visibility_tier` and nothing else.
- Placements are **not** moved, and the plan says how many stay.
- A row that moved between planning and applying is refused, not overwritten.

## 2. UI Interaction Flow

No user-facing UI, and no admin page either. The surface is three HTTP endpoints, reachable from a terminal against a running stack — *"where there is no shell and no `mix`"* (`data_correction_controller.ex:8-9`).

### Happy Path
1. `GET /api/admin/data_corrections` → every registered standing correction with its current blast radius.
2. `POST …/unmerge_edition/target` with `{"argument": {"edition_id": "<uuid>", "title": "The Book It Actually Is"}, "reason": "ISBN 978… is Eco's Postscript, not The Name of the Rose"}`.
3. Response: `mode: "dry_run"`, `count: 1`, and one change whose `because` reads:
   > *"ISBN 9788845292613 is not an edition of \"The Name of the Rose\"; splitting it onto its own work. 47 placement(s) stay on \"The Name of the Rose\" — no placement has ever named a merged edition, so which readers acquired this one is not recorded and may not be guessed."*
4. Same request with `"apply": true`. Response: `mode: "applied"`, `count: 1`, and `new_work_id` in the audit detail.
5. Reading the book back immediately shows the split — the cache was evicted in-band, not by event (§10).

### Sad Paths
| Situation | Result |
|-----------|--------|
| No `reason`, or blank after trim | `422 {error: "reason_required"}` |
| Unregistered correction name | `404 {error: "unknown_correction"}` — *"An unregistered name is a 404, not an error to work around"* |
| Name exists as a *standing* correction but not a targeted one | `404` — `target` resolves through `Registry.fetch_targeted/1` and **never** through `fetch/1`, because *"the two lists take different arguments, and a name that crossed between them would apply something other than what the operator asked for"* |
| `edition_id` absent or not a UUID | `422 {error: "invalid_argument", detail: ":edition_id_required"}` |
| `title` absent or blank | `422 … ":title_required"` |
| No `argument` object at all | `422 … ":argument_required"` |
| Edition id names no row | `422 {error: "correction_failed", detail: "{:unknown_edition, …}"}` |
| The edition is the work's **primary** | `422 … "{:primary_edition, …}"` — a merged edition is always `is_primary: false`, so a primary one was never merged, and splitting it would take the work's representative row away from it |
| It is the work's **only** edition | `422 … "{:only_edition_of_work, …}"` — a work with no edition is not reachable by ISBN and not describable on a detail page; *"'split the only edition out' is a rename asking to be a repair"* |
| The new work's changeset fails | `422 … "{:could_not_mint_work, …}"` |
| The row moved between plan and apply | `422 … "{:row_no_longer_matches, id, from}"` — `Column.swap/4`'s `WHERE id = $2 AND column IS NOT DISTINCT FROM $3` matched 0 rows |
| Run twice | The second run is refused by the same clause. **Idempotence is not claimed** — a targeted correction is aimed at a row a human picked, so running it twice means a human asked twice, and no predicate can tell the difference (`targeted.ex:39-49`) |
| Audit write fails | The **whole change is rolled back**. *"A correction that cannot be recorded is rolled back rather than applied silently. An unexplained mutation is worse than an unrepaired row — the row is at least still describable"* (`data_correction.ex:234-245`) |
| Admin token stale, MFA lapsed, IP changed, node redeployed | `401` / `403` from `pipeline :admin` — see US-20.1.1 |
| Admin token minted while owner, role since revoked | `403` from `:require_owner`, re-checked at the point of use |

## 3. API Calls

### `GET /api/admin/data_corrections`
- **Auth**: admin token, MFA-verified, owner role
- **Pipeline**: `:api` → `:admin` → `:require_owner` → `:rate_limit_admin` (`router.ex:395-402`)
- **Controller**: `StacksWeb.DataCorrectionController.index/2`
- **Response**: `{corrections: [{name, scope, reversibility, reversibility_note, mode, count, changes, report}]}`
- **Writes nothing.** `assign(:audit_row_count, …)` is set to the summed planned count so the admin-audit plug records what was *inspected*.
- ⚠️ **Lists only the standing (`Registry.all()`) corrections.** `unmerge_edition` is targeted, so it does **not** appear here — see the gap in §16.

### `POST /api/admin/data_corrections/:name/target`
- **Auth / Pipeline**: as above
- **Controller**: `DataCorrectionController.target/2`
- **Request body**: `{ argument: {edition_id: uuid, title: string}, reason: string, apply: boolean }`
- **`apply` defaults to `false`** — and this is a POST even to dry-run, *"because a correction that takes an argument has nothing to say without a body"*. The blast radius is in the response either way, and seeing it before writing is still the point.
- **Response (success)**: `{correction: {name, scope, reversibility, reversibility_note, mode: "dry_run" | "applied", count, changes: [{id, from, to, because}], report}}`
- **Response (error)**: `422 reason_required` · `404 unknown_correction` · `422 invalid_argument` + `detail` · `422 correction_failed` + `detail`
- **`audit_row_count`**: the outcome count when applying, **0 on a dry run** — *"a dry-run wrote nothing, so it audits nothing … claiming rows for a GET-shaped read would make the count meaningless for the writes it exists to track"*

### `POST /api/admin/data_corrections/:name/apply`
The parameter-free sibling, for standing corrections. Not this story's path, listed because it shares the audit and transaction machinery.

⛔ **What this surface cannot do.** `:name` resolves through the registry, so *"the only rows reachable over HTTP are the ones a reviewed, committed correction module already claims. There is no table parameter, no column parameter and no predicate parameter, and adding one would turn a repair tool into the arbitrary SQL endpoint `issues/138-prod-data-access-break-glass.md` rules out in as many words"* (`data_correction_controller.ex:36-42`).

## 4. Auth & Middleware Guards

- **Plugs fired**: `SecurityHeaders` → `AdminAuthPipeline` → `RequireMFA` → `AuditAdminCall` → `RequireRole role: "owner"` → `RateLimiter bucket: :admin`
- **Ownership checks**: none in the domain sense — there is no owner of a `book_edition` row. The authorisation *is* the pipeline.

⚠️ **`:require_owner` on top of `:admin` looks redundant and is not.** The admin login already refuses a non-owner. But *"an admin token outlives the role it was minted under: demote the account and the pipeline happily keeps loading the user for the remaining life of the session. For a read that is unfortunate; for a mutation that rewrites production rows it is the difference between a stale token and a stale token that can still write. Checking where the write happens, rather than only where the session began, is the lesson #332 recorded"* (`data_correction_controller.ex:44-53`).

### The argument is cast by the correction, not the controller
`correction.cast_argument(argument_params)` — so *"a targeted correction declares the keys it accepts, so no request params map reaches a write path"*. This mirrors the narrowness of `merge_edition/2`'s caller-supplied field set, for the stated reason that **the inverse of an operation must not be looser than the operation** (`targeted.ex:29-36`).

### `reason` is a guard, not a comment
Required, trimmed, non-empty, and written verbatim into the audit metadata **inside the change's transaction**. A repair with no stated reason cannot be applied.

## 5. Database Interactions

### What changes: exactly two columns of exactly one row, plus one new row
| Target | From | To |
|--------|------|----|
| `op.book_editions.book_id` | the work the edition was merged into | a newly minted work holding only this edition |
| `op.book_editions.is_primary` | `false` | `true` |
| `op.books` | — | one INSERT: the new work |

`is_primary` becomes `true` because *"the split-out edition is the only edition of its new work, and a work whose sole edition is non-primary is a shape nothing else in the system produces."* `op.book_editions_one_primary_per_book` accepts it because the new work has no other edition to conflict with.

### What the new work inherits: `visibility_tier`, and nothing else
⛔ **That single inheritance is a safety property, not a convenience.** *"Splitting an edition out of an `age_gated` work into a default-`public` one would silently un-gate content, and a repair may not widen an audience."*

- **Title** is stated by the operator — the judgement that the merge was wrong *is* the judgement about what the book actually is.
- **Author** is left null rather than inherited, *"because inheriting it would assert something the split has just decided is false"*. `Stacks.Workers.EnrichBookJob` is the path that fills it in.

### What follows the edition, and what stays
| Keyed on | Examples | Where it ends up |
|----------|----------|------------------|
| the **edition** | `op.price_history.book_edition_id`, partner inventory, uploaded images | follows the edition, for free |
| the **work** | `op.listings.book_id` | stays on the old work |

A listing for the split-out edition is left pointing at the old work. *"That is a live-listing decision for the operator and not something this correction should guess at."*

### Placements stay on the work they were made against

**This is the disposition decision #376 asks for, and the evidence is that the database does not record what the other choice would need.**

`Shelving.place_book/3` is one of only two writers of a placement's `book_edition_id`, and it always writes the work's **primary** edition (`primary_edition_id/1` orders `desc: is_primary`). The other, `do_reread_book/2`, carries an existing value forward. `merge_edition/2` inserts every merged edition with `is_primary: false`. So **no placement in the system has ever named a merged edition** — a reader who scans the merged ISBN gets `find_existing/1`'s *work*, and a placement pointing at that work's primary edition. **There is no row-level evidence of who acquired the edition being split out.**

Moving placements would therefore be guessing, and every available rule guesses badly:
- *"move them all"* relocates readers who own the original book and never touched this ISBN;
- *"move the ones created after the merge"* catches everyone who added the original in that window;
- *"move the ones whose upload named the ISBN"* reads evidence that **GDPR image retention deletes after 30 days**, and that the manual-ISBN path never writes at all.

*"A wrong reassignment is a second wrong merge, performed on user data, and it is not undoable by the same argument that makes the merge itself not undoable."*

So they stay — **and the correction is not thereby cosmetic.** The repair that matters is at the source: after the split the ISBN resolves to the right work for every future lookup, the wrong work stops advertising a book it does not contain, and the split-out book exists as itself. What is left is a bounded, countable set of readers whose shelf shows the old work — and the plan **states that count in its `:because`** before anything is written, so the operator sees the blast radius and can reach those readers as a human decision rather than having one made for them silently.

### Planning reads through Ecto; writes go through `Column.swap/4`
`Stacks.DataCorrection.Column`'s moduledoc argues for raw SQL because a correction usually runs where reality and the schema disagree. *"That argument does not apply to the reads here: the edition row is entirely valid, its wrongness is a relationship rather than a value, and no changeset can normalise a foreign key away."* This correction also never runs from the pre-migration deploy path, so `Column`'s `to_regclass` guard has nothing to protect.

The **writes** still go through `Column.swap/4`, for the one property that matters:

```sql
UPDATE #{table} SET #{column} = $1, updated_at = now()
WHERE id = $2 AND #{column} IS NOT DISTINCT FROM $3
```

0 rows updated → `{:error, {:row_no_longer_matches, id, from}}`. **A row that moved between planning and applying is refused.**

### Transaction shape
`run_targeted/3` plans first (outside any transaction — a refusal costs nothing), then hands the plan to the **same** private `apply_plan/4` the parameter-free path uses. So it is the same `Repo.transaction`, the same `audit.audit_log` row, and the same rollback when the audit cannot be written. *"There is one audit path, and this did not add a second."*

### Audit row
`Stacks.Audit.log(actor_id, "data.correction.applied", resource_type: "book_edition", resource_id: edition_id, metadata: %{correction: "unmerge_edition", scope:, reversibility:, from:, to:, because:, invoked_by: "admin api", reason:, new_work_id:})` — action from `DataCorrection.@audit_action` (`data_correction.ex:144`), `resource_type` from `UnmergeEdition.resource_type/0`, metadata encrypted through the Cloak vault.

⚠️ `apply_plan/4` calls `ensure_vault!/0` first, because *"a correction run from `mix` or from `bin/core eval` has a started repo but no application tree, and `Audit.log/3` rescues its own failures — so without this the audit trail would silently be empty in exactly the situation it exists for"* (`data_correction.ex:252-268`).

## 6. Event Flow & Lifecycle

### Events Emitted
**None.** A data correction is not a domain event. `books.edition_merged` announced the merge; nothing announces the un-merge.

That is a real consequence, not a neutral choice: any handler that acted on the merge is not told the merge was wrong. Today the only subscriber is `CacheInvalidationHandler`, and this correction does its job directly (§10), so nothing is currently missed. If a future subscriber appears — a search-index writer, a recommendation refresh — it will need telling. Recorded in §16.

### Reversibility, as declared
`reversibility/0` returns `{:reversible, "…"}` with an honest note rather than a bare atom:

> *"the audit row keeps the work the edition left, and putting it back is the same one-column write — but the work minted to hold it would be orphaned rather than removed, and any placement, listing or price made against the new work after the split would have to be moved by hand"*

That text is quoted in the dry-run report and in the audit row, so the operator reads the caveat at the moment of deciding rather than afterwards.

## 7. Background Jobs (Oban)

None. This runs synchronously in the request, because the operator reads the result back immediately. That is also why the cache eviction is in-band rather than event-driven (§10) — Oban dispatch is asynchronous.

**Follow-on work the operator may want to enqueue by hand:** `Stacks.Workers.EnrichBookJob` for the new work, since its author is deliberately null (§5).

## 8. External Service Calls

None. `mint_work/1` writes a title and a visibility tier — it does not resolve the new work's ISBN against Open Library, because the ISBN is already verified: it is on the edition being moved, and `merge_edition/2` passed it through the hard gate when it was created.

## 9. Storage (R2 / Local)

N/A. Uploaded images are keyed on the **edition**, so they follow it (§5). Nothing is copied or deleted.

## 10. Cache Interactions

- **Cache**: `Stacks.Books.BookDetailCache` (ETS, keyed by **work** id, 5-minute TTL)
- **Operation**: `invalidate` — **twice**: the old work and the newly minted one
- **When**: inside `apply_change/1`, after both column swaps succeed
- **Why in-band**: *"The book detail page is served from a 5-minute ETS cache keyed by work id, so without this both works keep describing the pre-split shape for up to five minutes — the same eviction-under-the-wrong-key defect #355 found. Evicted in-band rather than by event, because the operator reads the result back immediately and Oban dispatch is asynchronous"* (`unmerge_edition.ex:153-159`).

⚠️ **Both keys, not one.** Evicting only the work the edition left would leave the new work's entry — which does not exist yet — fine, but evicting only the new work would leave the old one still listing an edition it no longer has. The pair is the fix.

---

## 11. dbt Model Dependencies

No refresh is triggered. `stg_book_editions` → `int_book_detail_view` will reflect the split at the next nightly `{"0 5 * * *", DbtRefreshJob, args: %{full: true}}` run.

Acceptable for the same reason as US-2.6.1 §11: the reader-facing book detail is served from Postgres via `BookDetailCache`, not from the warehouse. But an operator who repairs data and then checks a Grafana panel will see the pre-split shape until the nightly run, and nothing tells them so.

## 12. Elm Frontend State Machine (Detail)

**N/A — there is no frontend, by owner ruling.**

Worth stating positively rather than as an omission. A public "this ISBN is the wrong book" affordance would be a reader-facing button that rewrites the book graph. The four registered corrections and this targeted one are *reviewed, committed modules*; a form would be a fifth kind of thing — a caller-supplied predicate — which is exactly what §3's "what this surface cannot do" refuses.

The nearest reader-facing surface is `POST /api/books/:id/merge-format` (US-1.1.8), which creates merges. That asymmetry is deliberate: creating a merge is a reader judgement about their own book; reversing one is a judgement about the shared catalogue.

## 16. Known Gaps

1. **`unmerge_edition` is invisible from `GET /api/admin/data_corrections`.** `index/2` runs `Registry.all()`, which is the *standing* list — deliberately separate, because *"the deploy path and the mix task sweep `all/0`, and a correction that needs an argument has none to sweep with"* (`registry.ex:80-87`). But `Registry.all_targeted/0` **exists and is exposed nowhere over HTTP**, so an operator who does not already know the name cannot discover it from the API — which undercuts the "reachable on a running stack" purpose this surface was built for. A `targeted:` key in the index response, listing name + `resource_type` + the argument keys and nothing else, would fix it without weakening anything: enumerating names is not the same as accepting one.
2. **No follow-on enrichment is enqueued.** The new work has a null author by design (§5), and nothing schedules `EnrichBookJob` for it. The operator must know to do this, and nothing tells them.
3. **The orphaned work on reversal.** `reversibility/0` says so honestly, but there is no correction that removes a work minted by a reverted split — so reversing leaves a titled, editionless `op.books` row, which is exactly the shape `refuse_last_edition/1` refuses to create on the way in.
4. **Listings are left pointing at the old work** (§5). Correct — it is an operator decision — but nothing surfaces *whether there are any*. The plan counts placements and not listings, so the operator is told about one silent consequence and not the other.
5. **No dbt refresh** (§11), so warehouse-backed views show the pre-split shape until the nightly run.
6. **No event is emitted** (§6), so a future subscriber to `books.edition_merged` will silently miss the reversal.
7. **The placement-disposition argument is load-bearing and time-sensitive.** It holds because no placement has ever named a merged edition. §13's last metric is the check; nothing currently runs it, and if a new write path ever sets `book_edition_id` to a non-primary edition, this story's central decision becomes wrong without anything failing.

# US-12.1.2 — LLM Book Associations on a Post

## 1. User Story

> **As a** user, **I want** the platform to surface connections between my writing and my reading history **so that** readers can explore the books that informed a post, and I can discover patterns in my own reading and thinking.

After a post is published, an Oban job runs the post body through an LLM. The LLM is given the post content and the user's full book catalogue (title, author, description, subjects). It returns a ranked list of books from the catalogue that relate to the post, with a one-sentence reasoning for each association. Associations are stored in `post_book_associations` with a confidence score. The top three are surfaced on the post by default. The user can review, accept, dismiss, or manually add associations.

**Note — distinction from the Writing Assistant (US-12.2.1):** This is a *post-publish, asynchronous, non-interactive* flow using a small fast model (`Meta-Llama-3-8b-chat-hf`). The Writing Assistant is a *real-time, interactive, RAG-powered Socratic dialogue* using a larger model (`Llama-3.3-70B-Instruct-Turbo`). Both use Together AI but serve different purposes and must not be conflated in architecture or cost tracking.

## 2. UI Interaction Flow

### Happy Path (Automated Association)
1. User publishes a blog post (see US-12.1.1).
2. `blog.post_published` event fires.
3. `BlogAssociationHandler` enqueues `PostBookAssociationWorker`.
4. Worker fetches the post content and up to 200 books from the catalogue.
5. Worker sends a prompt to Together AI LLM with post body and book list.
6. LLM returns a JSON array of `{ book_id, confidence, reasoning }`.
7. Worker persists each association via `Blog.associate_book/3` with `source: "llm"`.
8. `blog.associations_suggested` event is emitted.
9. On the post page, "Books from my shelves" section shows associated books.

### Happy Path (User Confirm/Dismiss)
1. User views their post on `Page.Blog.Post`.
2. The owner sees all associations (including hidden ones) with Confirm/Dismiss buttons.
3. User clicks "Confirm" on an association.
4. System sends `PUT /api/blog/posts/:post_id/associations/:id/confirm`.
5. Backend sets `visible: true` on the association.
6. `blog.association_confirmed` event is emitted.
7. Page reloads post data to reflect the change.

### Happy Path (Dismiss)
1. User clicks "Dismiss" on an association.
2. System sends `PUT /api/blog/posts/:post_id/associations/:id/dismiss`.
3. Backend sets `visible: false`.
4. `blog.association_dismissed` event is emitted.
5. Association disappears from public view but remains visible to owner.

### Sad Paths
- **LLM circuit breaker open**: `TogetherClient.complete/2` returns `{:error, :circuit_open}`. Worker returns error for Oban retry.
- **API key missing**: Returns `{:error, :api_key_missing}`. Worker fails.
- **LLM response not valid JSON**: Worker logs warning, returns `:ok` (no retry -- malformed output won't improve).
- **No books in catalogue**: Worker skips LLM call, logs info, returns `:ok`.
- **Association not found**: Confirm/dismiss returns `{:error, :not_found}`.

### Elm State Machine
- **Page module**: `Page.Blog.Post` (viewer) + `Components.BookAssociations` (display)
- **Model fields involved**: `post : RemoteData Http.Error BlogPost`, `actionResult : RemoteData Http.Error ()`
- **Msg flow**: `ConfirmAssociation id -> AssociationActionCompleted -> PostLoaded (reload)`
- **RemoteData states**: actionResult: NotAsked -> Loading -> Success (triggers reload) / Failure

## 3. API Calls

### `PUT /api/blog/posts/:post_id/associations/:id/confirm`
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.BlogController.confirm_association/2`
- **Request body**: None
- **Response (success)**: `{ association: { id, book_id, visible: true } }` -- HTTP 200
- **Response (error)**: `:not_found` (404), `:unauthorized` (403)

### `PUT /api/blog/posts/:post_id/associations/:id/dismiss`
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.BlogController.dismiss_association/2`
- **Request body**: None
- **Response (success)**: `{ association: { id, book_id, visible: false } }` -- HTTP 200
- **Response (error)**: `:not_found` (404), `:unauthorized` (403)

### `GET /api/blog/posts/:id` (shows associations)
- **Auth**: Optional (JWT Bearer token)
- **Pipeline**: `:api` (with optional auth for public posts)
- **Controller**: `StacksWeb.BlogController.show/2`
- **Response (success)**: `{ post: {...}, associations: [{ id, book_id, confidence, source, visible, reasoning? }] }` -- HTTP 200
- **Notes**: `reasoning` field is only included when the viewer is the post owner (`is_owner`). Non-owners only see associations where `visible == true`.

## 7. Background Jobs (Oban)

### `Stacks.Workers.PostBookAssociationWorker`
- **Worker**: `Stacks.Workers.PostBookAssociationWorker`
- **Queue**: `:default`
- **Args**: `%{ "post_id" => post_id }`
- **Max attempts**: 3
- **Uniqueness**: None configured
- **What it does**:
  1. Fetches the post by ID. If not found, logs warning and returns `:ok`.
  2. Fetches up to 200 books from the catalogue, preloading authors.
  3. If no books exist, skips and returns `:ok`.
  4. Builds an LLM prompt containing the post body (truncated to 4000 chars) and a formatted book list (`id: "title" by author`).
  5. Calls `together_client().complete(prompt, max_tokens: 1024, temperature: 0.2)`.
  6. Parses the JSON response as a list of `{ book_id, confidence, reasoning }` objects.
  7. For each valid association, calls `Blog.associate_book(post, book_id, attrs)` with `source: "llm"`.
  8. Emits `blog.associations_suggested` event with the list of associated book IDs.
- **On success**: Returns `:ok`.
- **On failure**: LLM errors return `{:error, reason}` for Oban retry. Parse errors log a warning and return `:ok` (no retry).

### Trigger chain
`Blog.publish_post/2` -> emit `blog.post_published` -> `Events.Dispatcher` -> `BlogAssociationHandler.handle_event/1` -> `PostBookAssociationWorker.new(%{post_id: post_id})` -> `Oban.insert/1`

## 8. External Service Calls

### Together AI (LLM)
- **Service**: Together AI (LLM inference)
- **Endpoint**: `POST https://api.together.xyz/v1/chat/completions`
- **Client module**: `Stacks.AI.TogetherClient`
- **Auth**: Bearer token (`VISION_TOGETHER_API_KEY`)
- **Model**: `meta-llama/Llama-3-8b-chat-hf` — small, fast, post-publish batch use
- **Parameters**: `max_tokens: 1024`, `temperature: 0.2`
- **Circuit breaker**: `:together_ai_fuse` -- 3 failures in 2 minutes blows the circuit
- **Fallback**: When circuit is blown, returns `{:error, :circuit_open}`. Worker retries.
- **Mock in test**: Configurable via `Application.get_env(:core, :together_client)` -- uses `Stacks.AI.MockTogetherClient` in test.
- **Not to be confused with**: The Writing Assistant (`US-12.2.1`) which uses `Llama-3.3-70B-Instruct-Turbo` via `Stacks.AI.WritingAssistantClient` for real-time interactive dialogue. These are separate clients, separate circuit breakers, and tracked separately in cost reporting.

## 13. Operational Metrics

- **LLM association worker success/failure rates**: `PostBookAssociationWorker` outcome counts -- success, LLM error (retried), parse error (not retried), circuit breaker open, API key missing. Critical for monitoring Together AI reliability.
- **Circuit breaker state**: `:together_ai_fuse` state transitions (closed -> open -> half-open). 3 failures in 2 minutes blows the circuit. Track open-circuit duration and recovery frequency.
- **Association creation count**: Total `Blog.associate_book/3` calls per worker run. The `blog.associations_suggested` event payload contains `count` for this.
- **Association confirm/dismiss counts**: `blog.association_confirmed` and `blog.association_dismissed` event counts. Tracks user engagement with LLM suggestions.
- **LLM skip rate**: Count of worker runs that skip the LLM call because the user has no books in their catalogue. Indicates users who publish before building a library.

---

## 14. Performance & Usability Metrics

- **Blog publish to LLM association time**: End-to-end latency from `blog.post_published` event emission to `blog.associations_suggested` event. Includes: event dispatch, Oban job enqueue + scheduling, post fetch, book catalogue fetch (up to 200 books with author preload), LLM API call, JSON parse, and batch association INSERT.
- **LLM API call latency**: Time for `together_client().complete/2` -- the Together AI inference call with `max_tokens: 1024, temperature: 0.2`. The dominant cost in the pipeline.
- **Association confirm/dismiss rates**: Ratio of confirmed vs. dismissed associations. Indicates LLM suggestion quality. A high dismiss rate suggests the prompt or model needs tuning.
- **Association visibility on post pages**: Percentage of associations that are visible to non-owner readers (i.e., confirmed by the author). Tracks how many LLM suggestions users actually endorse.

## 15. Cost Tracking

- **Together AI**: Per-token cost for the LLM inference call. Input tokens: post body (truncated to 4000 chars) + formatted book list (up to 200 books with `id: "title" by author`). Output tokens: JSON array of `{ book_id, confidence, reasoning }` objects (max 1024 tokens). Cost scales with post length and catalogue size. Model: `meta-llama/Llama-3-8b-chat-hf`.
- **Neon**: Compute cost for the book catalogue query (`op.books` + `op.authors` JOIN, LIMIT 200), post fetch, and batch INSERT into `op.post_book_associations`. The catalogue query is the most expensive DB operation in this flow.
- **Neon** (cache invalidation): `blog.associations_suggested` triggers `CacheInvalidationHandler`, which may incur additional cache-related DB operations.
- Confirm/dismiss operations are low-cost single-row UPDATEs on `op.post_book_associations`. No external service calls for user-facing association management.

# US-17.2.1 — View and Edit Profile

## 1. User Story

> **As a** user, **I want to** manage my display name, email, and personal website **so that** my public identity on the platform is accurate.

**Acceptance criteria:**
- `/settings/profile` renders the profile editing form
- Display name changes are reflected in the navigation bar immediately
- Email changes require the current password for confirmation
- All fields validate before saving (email format, URL format)

---

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/settings/profile` (via Settings sidebar or user menu dropdown).
2. `Profile.init auth.user` populates the model with current user data.
3. Form shows two sections: "Personal Information" (Display Name, Email, Website URL) and "Location" (Country Code, City).
4. User edits fields and clicks "Save Profile" or "Save Location".
5. API call fires. Button shows "Saving..." while loading.
6. On success: "Profile saved." or "Location saved." confirmation.

### Sad Paths
- **Save fails**: "Could not save profile. Please try again." / "Could not save location. Please try again."
- **Email change without password**: The API returns `{ "error": "invalid_current_password" }` — HTTP 422. Currently the frontend does not send `current_password`, so email changes that require password confirmation will fail.

### Elm State Machine
- **Page module**: `Page.Settings.Profile`
- **Model fields**: `displayName`, `email`, `websiteUrl`, `countryCode`, `city`, `savingProfile : RemoteData Http.Error ()`, `savingLocation : RemoteData Http.Error ()`
- **Msg flow**: `SetDisplayName`/`SetEmail`/`SetWebsiteUrl` -> update fields, reset `savingProfile`; `SaveProfile` -> `Api.updateProfile` -> `SaveProfileCompleted`; `SetCountryCode`/`SetCity` -> update fields, reset `savingLocation`; `SaveLocation` -> `Api.updateLocation` -> `SaveLocationCompleted`

---

## 3. API Calls

### `PUT /api/settings/profile`
- **Auth**: Required (Bearer JWT)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.UserSettingsController.update_profile/2`
- **Request body**: `{ "display_name": string, "email": string, "website_url": string }`
- **Response (success)**: `{ "display_name": string, "website_url": string, "email": string }` — HTTP 200
- **Response (error)**:
  - `{ "error": "invalid_current_password" }` — HTTP 422 (when changing email without valid `current_password`)
  - `{ "errors": { ... } }` — HTTP 422 (changeset validation errors)
- **Context function**: `Accounts.update_profile/2` — if `email` is present in attrs, calls `update_profile_with_email` which verifies `current_password` with Argon2 first, then uses `Ecto.Multi` to update profile and email atomically.

### `PUT /api/settings/location`
- **Auth**: Required (Bearer JWT)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.UserSettingsController.update_location/2`
- **Request body**: `{ "country_code": string, "city": string }`
- **Response (success)**: `{ "country_code": string, "city": string }` — HTTP 200
- **Response (error)**: `{ "errors": { ... } }` — HTTP 422
- **Context function**: `Accounts.update_location/2` — applies `User.location_changeset`, emits `user.location_updated` event.

---

## 4. Auth & Middleware Guards

- **Plugs fired**: `SecurityHeaders` -> `AuthPipeline` (VerifyHeader, EnsureAuthenticated, LoadResource, RequireConfirmedEmail)
- **Ownership**: The controller reads the current user from `Guardian.Plug.current_resource(conn)` — users can only update their own profile.

---

## 5. Database Interactions

### Write: Update profile
- **Table(s)**: `op.users`
- **Operation**: UPDATE
- **Changeset**: `User.profile_changeset/2` — casts `display_name`, `website_url`
- **Transaction**: Simple update if no email change. `Ecto.Multi` with `:profile` and `:email` steps if email is being changed.
- **Email changeset**: `User.email_changeset/2` — validates email format, unique constraint.

### Write: Update location
- **Table(s)**: `op.users`
- **Operation**: UPDATE
- **Changeset**: `User.location_changeset/2` — casts `country_code`, `city`

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.SettingsProfile`
- **URL**: `/settings/profile`
- **Public or authenticated**: Authenticated only

### Init
- **`Profile.init user`**: Populates model from the user record: `displayName = user.displayName`, `email = user.email`, `websiteUrl = ""` (not currently stored in auth flags), `countryCode = Maybe.withDefault "" user.countryCode`, `city = Maybe.withDefault "" user.city`. Both `savingProfile` and `savingLocation` start as `NotAsked`.

### Update cycle
- **Msg**: `SetDisplayName val` / `SetEmail val` / `SetWebsiteUrl val` — update field, reset `savingProfile` to `NotAsked`
- **Msg**: `SetCountryCode val` / `SetCity val` — update field, reset `savingLocation` to `NotAsked`
- **Msg**: `SaveProfile` — if token present, call `Api.updateProfile`, set `savingProfile = Loading`
- **Msg**: `SaveProfileCompleted (Ok _)` -> `savingProfile = Success ()`
- **Msg**: `SaveProfileCompleted (Err err)` -> `savingProfile = Failure err`
- **Msg**: `SaveLocation` — if token present, call `Api.updateLocation`, set `savingLocation = Loading`
- **Msg**: `SaveLocationCompleted (Ok _)` -> `savingLocation = Success ()`
- **Msg**: `SaveLocationCompleted (Err err)` -> `savingLocation = Failure err`

### View
- Two sections: "Personal Information" and "Location", each with their own save button and feedback.
- **CSS classes**: `page--settings`, `settings-section`, `settings-section__title`, `form-field`, `form-field__label`, `form-field__input`, `settings-actions`, `btn--primary`, `btn--disabled`, `success`, `error`

## 13. Operational Metrics

- **Profile update success rate**: Ratio of HTTP 200 responses to total `PUT /api/settings/profile` requests.
- **Profile update failure rate**: Count of HTTP 422 responses, split by error type (invalid_current_password, changeset validation errors).
- **Location update success rate**: Ratio of HTTP 200 responses to total `PUT /api/settings/location` requests.
- **Location update failure rate**: Count of HTTP 422 responses from location updates.
- **Email change attempt rate**: How often users attempt to change their email address (tracked by presence of `email` in request body).
- **Email change success vs failure**: Email changes require `current_password` verification — track success rate and `invalid_current_password` rejection rate.
- **Event emission reliability**: Count of `user.profile_updated` and `user.location_updated` events successfully written to `event_log`.

---

## 14. Performance & Usability Metrics

- **Profile save latency**: p50/p95 for `PUT /api/settings/profile` round-trip. Should be <200ms (simple DB UPDATE).
- **Location save latency**: p50/p95 for `PUT /api/settings/location` round-trip. Should be <200ms.
- **Display name update-to-nav-reflection time**: Time from successful profile save to navigation bar showing the updated display name. Requires page-level auth refresh.
- **Profile page load time**: Time from navigation to form render. Should be <50ms (init from in-memory auth data, no API call on load).
- **Form abandonment rate**: Percentage of profile page visits where the user edits fields but does not click save.
- **Password prompt confusion rate**: How often email changes fail due to missing `current_password` (known frontend gap).

---

## 15. Cost Tracking

- **Database writes**: One UPDATE to `op.users` per save (profile or location). Negligible Neon cost.
- **Ecto.Multi (email changes)**: Two-step transaction (profile + email) when email is changed. Marginally more DB work, still negligible.
- **Argon2 (email changes only)**: If email is changed, `Argon2.verify_pass` is called to verify current password. ~200-400ms CPU on Fly.io shared-cpu-1x. Cost: ~$0.0000005.
- **Event writes**: One INSERT to `event_log` per update. Negligible.
- **No external service calls**: Profile/location updates do not trigger email delivery or external APIs.
- **Total per-save cost**: ~$0.00 (negligible DB writes; Argon2 only on email changes).

# US-14.1.1 — Register a New Account

## 1. User Story

> **As a** new user, **I want to** create an account on The Stacks **so that** I can start building my personal book collection.

Set up their identity on the platform so they can begin adding books, organising shelves, and accessing all features that require authentication.

**How they accomplish it:**
1. The user navigates to The Stacks and clicks "Sign In" in the top navigation.
2. The authentication page loads with two tabs: "Sign In" and "Register". The user clicks the "Register" tab.
3. The registration form appears with four fields: Display Name, Email, Password, and Confirm Password.
4. The user enters their chosen display name, their email address, a password, and repeats the password in the confirmation field.
5. The user clicks "Request Entry".
6. The system validates the input, creates the account, and sends a confirmation email.
7. The user sees a "Registration Pending" state: "Check your inbox! A confirmation email has been sent to [email]. Click the link in the email to confirm your address and activate your account."
8. The user must confirm their email by clicking the link in the email before they can log in.

**Acceptance criteria:**
- Registration form collects display name, email, password, and password confirmation
- Password confirmation must match the password field; mismatched passwords prevent submission
- Switching between Sign In and Register tabs preserves entered email and password
- Successful registration shows a "check your inbox" pending state — the user is NOT navigated to antilibrary
- First-time registration triggers the onboarding flow after email confirmation and first login (US-14.1.2)
- Subsequent logins redirect to the AntiLibrary (`/antilibrary`)
- Duplicate email addresses produce a clear, non-technical error message
- The submit button is disabled during the API request to prevent double submission
- Rate limiting is applied to the registration endpoint to prevent abuse

**Technical note:** In the single-user (self-hosted) phase, the first user to register becomes the platform owner (`role: "owner"`). No public registration beyond the owner is available until the multi-user phase.

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/login` (or clicks "Sign In" in the nav bar).
2. User sees the login card with two tabs: "Sign In" (active by default) and "Register".
3. User clicks "Register" tab. The form updates to show Display Name, Email, Password, and Confirm Password fields.
4. User fills in all four fields. Real-time validation runs: email must contain `@` and `.`, password must be >= 8 characters, display name must be non-empty, password confirmation must match the password field.
5. Fields show green border (`login-card__field--valid`) or red border with hint (`login-card__field--error`).
6. User clicks "Request Entry" button (disabled until all fields validate, including matching passwords).
7. Button shows a spinner (`spinner spinner--small`) while the API call is in flight.
8. On success (HTTP 201), the backend returns `{"message": "confirmation_email_sent"}`.
9. The frontend transitions to a **Registration Pending** state. The login card is replaced by a confirmation notice:
   > "Check your inbox! A confirmation email has been sent to [email]. Click the link in the email to confirm your address and activate your account."
10. The user is NOT navigated to antilibrary. No JWT is stored. No door animation plays.

### Email Confirmation Sub-flow
1. User receives a confirmation email with a link to `/api/auth/confirm/:token`.
2. The backend verifies the token (Phoenix.Token, salt: `"email_confirm"`, max_age: 172800 / 48 hours).
3. If valid: the user's `email_confirmed` flag is set to `true`, and the browser is redirected to `/confirm-email/success`.
4. If invalid or expired: the browser is redirected to `/confirm-email/error`.
5. The `/confirm-email/success` page shows "Email confirmed" and a "Sign in" link to `/login`.
6. The `/confirm-email/error` page shows "Confirmation failed" and guidance to contact support or retry.

### Sad Paths
- **Duplicate email**: API returns 422 with changeset errors. User sees: "Registration could not be completed. The email may already be in use."
- **Invalid fields**: Client-side validation prevents submission. Red border and hint text on invalid fields.
- **Passwords don't match**: Submit button remains disabled. Confirm Password field shows: "Passwords do not match."
- **Network error**: User sees: "The library is unreachable. Please try again."
- **Rate limited**: API returns 429. User sees a generic error message.

### Elm State Machine
- **Page module**: `Page.Login`
- **Model fields involved**: `email`, `password`, `passwordConfirm`, `displayName`, `mode` (set to `RegisterMode`), `submitState`, `emailValidation`, `passwordValidation`, `passwordConfirmValidation`, `displayNameValidation`
- **Msg flow**: `DisplayNameChanged`/`EmailChanged`/`PasswordChanged`/`PasswordConfirmChanged` -> field validation -> `FormSubmitted` -> `Api.register` call -> `GotRegisterResponse (Ok|Err)` -> update model to `RegistrationPending` or `Failure`
- **RemoteData states**: `NotAsked` -> `Loading` -> `RegistrationPending` / `Failure Http.Error`
- **OutMsg pattern**: `NoOut` during form interaction; `RegistrationSucceeded email` on success (shows pending confirmation state); no door animation, no JWT, no navigation to antilibrary.

## 3. API Calls

### `POST /api/auth/register`
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.AuthController.register/2`
- **Request body**: `{ "email": string, "password": string, "display_name": string }`
- **Response (success)**: `{ "message": "confirmation_email_sent" }` — HTTP 201
- **Response (error)**: `{ "errors": { "email": ["has already been taken"], ... } }` — HTTP 422
- **Note**: The first user registered gets `role: "owner"` automatically via `maybe_assign_owner_role/1`.

### `GET /api/auth/confirm/:token`
- **Auth**: None
- **Pipeline**: `:api`
- **Controller**: `StacksWeb.EmailVerificationController.confirm/2`
- **Response (success)**: 302 redirect to `/confirm-email/success`
- **Response (error)**: 302 redirect to `/confirm-email/error`

## 5. Database Interactions

### Write: Create user
- **Table(s)**: `op.users`
- **Operation**: INSERT (via `Ecto.Multi`)
- **Changeset validations**: `User.registration_changeset/2` — required: `email`, `password`; validates email format (`~r/^[^\s]+@[^\s]+$/`), password length (min 8), role inclusion (`owner`/`user`), profile_visibility inclusion; unique constraint on email; password hashed with Argon2.
- **Transaction**: Wrapped in `Ecto.Multi` with three steps:
  1. `:user` — INSERT the user record
  2. `:set_confirmation` — UPDATE with `email_confirmed: false` and a random `email_confirmation_token` (32-byte url-encoded random; this is later overwritten with a signed Phoenix.Token by `EmailConfirmationHandler`)
  3. `:emit_event` — emit `user.registered` event via `Events.emit_safe/1`
- **Password hashing**: `Argon2.hash_pwd_salt/1` runs synchronously inside the registration changeset. (Unlike login, registration does NOT route through `Stacks.Accounts.ArgonPool` — see Issue #166.)
- **Audit log**: `AuthController.register/2` calls `Audit.log(user.id, "user.registered", ...)` after the Multi succeeds (separate from the event-bus emission inside `Accounts.register/1`).
- **Schema module**: `Stacks.Accounts.User`

### Read: Check if first user
- **Table(s)**: `op.users`
- **Query**: `Repo.aggregate(User, :count, :id)` — if 0, assign `role: "owner"`

## 6. Event Flow & Lifecycle

### Events Emitted
- **Event type**: `user.registered`
- **Aggregate**: `user` + user ID
- **Payload**: `%{role: user.role}`
- **Emitted by**: `Stacks.Accounts.register/1` (within the Multi transaction)
- **Emission method**: `Events.emit_safe/1`

### Event Handlers Triggered
- **Handler**: `Stacks.Notifications.EmailConfirmationHandler`
- **Action**: Looks up user by `aggregate_id`, calls `Email.send_registration_confirmation/1`
- **Downstream effects**: Generates a signed Phoenix.Token (`Phoenix.Token.sign(CoreWeb.Endpoint, "email_confirm", user.id)`; verified with `max_age: 172_800` / 48h), overwrites the random `email_confirmation_token` set during registration with this signed token, and enqueues an `EmailDeliveryJob` with template `registration_confirmation`.

## 13. Known Bugs / Implementation Gaps

The following bugs exist in the current frontend implementation and must be fixed before this story can be considered done. Tests for the desired behavior are in `frontend/tests/LoginTest.elm` and `frontend/tests/Page/LoginProgramTest.elm`.

### Bug 1: No password confirmation field
`Page.Login.elm` has no `passwordConfirm` field in the `Model`, no `PasswordConfirmChanged` `Msg`, no `passwordConfirmValidation`, and no confirm password input in the view. The registration form should require the password to be entered twice. Without this, users who mistype their password during registration cannot know until they try to log in.

### Bug 2: Frontend/backend decoder mismatch on registration
`Api.register` uses `authResponseDecoder` (which expects `{ token, user: {...} }` — the login response shape). The backend correctly returns `{"message": "confirmation_email_sent"}` on HTTP 201. Because the proto-generated decoder always returns a default-value `AuthResponse` on any JSON (defaulting `token = ""`), decoding succeeds with an empty struct. This causes `GotAuthResponse (Ok { token = "", ... })` to fire, which triggers the door animation and navigates the user to `/antilibrary` with a blank JWT. The fix is to introduce a dedicated `GotRegisterResponse (Result Http.Error ())` Msg and a registration-specific decoder that only checks for the `"message"` key.

### Bug 3: No RegistrationPending state
`Page.Login.elm` has no `RegistrationPending` mode or state. After a successful registration API call, the user should see a "check your inbox" message — not be navigated anywhere. Currently, due to Bug 2, the user is incorrectly taken to antilibrary. Once Bug 2 is fixed, this state must be implemented to provide the correct post-registration UX.

### Bug 4: HTTP 403 not handled in errorMessage
The `errorMessage` function in `Page.Login.elm` handles `Http.BadStatus 401`, `Http.BadStatus 409`, and `Http.BadStatus 422` explicitly. `Http.BadStatus 403` falls through to the generic message: "The door remains shut. Invalid email or password." When a user with an unconfirmed email attempts to log in, the backend returns 403 with `{"error": "email_unconfirmed"}`. The user should instead see: "Please confirm your email address before signing in. Check your inbox for the confirmation email." with a "Resend confirmation email" link.

## 14. Operational Metrics

- **Registration success rate**: Ratio of HTTP 201 responses to total `POST /api/auth/register` requests. Track by day/week.
- **Registration failure rate**: Count of HTTP 422 (duplicate email, validation errors) and HTTP 429 (rate limited) responses.
- **Rate limiter trigger count**: Number of times the `:auth` bucket (5/min per IP) rejects registration attempts.
- **Email confirmation delivery rate**: Ratio of successfully delivered confirmation emails (via Resend) to total `registration_confirmation` jobs enqueued in the `:notifications` Oban queue.
- **Email confirmation success rate**: Ratio of `GET /api/auth/confirm/:token` requests returning 302 to `/confirm-email/success` vs `/confirm-email/error`.
- **Argon2 hash computation time**: p50/p95/p99 latency for `Argon2.hash_pwd_salt/1` during `User.registration_changeset/2`. Directly impacts registration endpoint response time.
- **Guardian token issuance count**: Number of JWTs issued post-confirmation (tracked via `user.login` audit log entries from first-time logins).
- **Event emission reliability**: Count of `user.registered` events successfully written to `event_log` vs Multi transaction failures.

## 15. Performance & Usability Metrics

- **Registration-to-confirmation-to-first-login conversion rate**: Funnel from `user.registered` event to email confirmation to first `user.login` audit entry. Drop-off indicates email delivery or UX friction.
- **Registration form time-to-submit**: Client-side measurement from page load to `FormSubmitted` Msg dispatch.
- **Registration endpoint latency**: p50/p95 for `POST /api/auth/register` (includes Argon2 hashing, Multi transaction, event emission).
- **Confirmation email click-through time**: Time between `EmailDeliveryJob` completion and `GET /api/auth/confirm/:token` request.
- **Client-side validation feedback latency**: Time from keypress to validation state change (should be <16ms, synchronous in Elm).
- **Error message clarity**: Track support requests related to registration errors (duplicate email, unconfirmed email) to measure message effectiveness.
- **Tab switching retention**: Rate at which users who land on Sign In tab switch to Register tab and complete registration.

## 16. Cost Tracking

- **Resend**: Confirmation email delivery at ~$0.001/email. Volume is bounded by registration rate (single-user phase: effectively one email total; multi-user phase: scales with new signups).
- **Argon2 (Fly.io compute)**: Password hashing is CPU-intensive. Each registration triggers one Argon2 hash. On Fly.io shared-cpu-1x, expect ~200-400ms per hash. Cost is absorbed into the Fly.io machine billing (~$0.0000025/second of CPU).
- **Guardian JWT**: Token encoding uses HMAC-SHA512 — negligible CPU cost (<1ms).
- **Oban job processing**: EmailDeliveryJob runs on the `:notifications` queue. Minimal compute — the cost is in the Resend API call, not the job execution.
- **Database writes**: One INSERT (user) + one UPDATE (confirmation token) + one INSERT (event_log) per registration. Negligible Neon cost at single-user scale.
- **Total per-registration cost**: ~$0.001 (dominated by Resend email delivery).

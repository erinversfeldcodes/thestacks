# US-10.2.3 — Set Blog Post Visibility

## 1. User Story

> **As a** user, **I want to** control who can read each of my blog posts **so that** I can publish some posts widely and keep others within a trusted group.

When writing or editing a post, the user sets the visibility before publishing (or can change it at any time). Visibility options: Only me / Platform users / Group -- subject to the profile visibility ceiling. A post set to "Only me" is saved as a draft-like private post. It does not appear in the user's public blog listing.

---

## 2. UI Interaction Flow

### Happy Path
1. User opens the blog editor (`Page.Blog.Editor`).
2. In the editor, a "Visibility" dropdown shows three options: "Only me" (owner), "Group", "Platform."
3. User selects desired visibility.
4. User clicks "Save Draft" or "Publish."
5. System sends `POST /api/blog/posts` (new) or `PUT /api/blog/posts/:id` (edit) with visibility in the payload.
6. Backend validates the visibility against the profile ceiling via `Visibility.validate_visibility_ceiling/3`.
7. If valid, post is saved. If visibility exceeds ceiling, returns `{:error, :visibility_ceiling}`.

### Sad Paths
- **Visibility exceeds profile ceiling**: `Blog.create_post/2` or `Blog.update_post/3` returns `{:error, :visibility_ceiling}`. The user must choose a more restrictive visibility.
- **Save failure**: Elm shows "Could not save post. Please try again."
- **Publish failure**: Elm shows "Could not publish post. Please try again."

### Elm State Machine
- **Page module**: `Page.Blog.Editor`
- **Model fields involved**: `visibility : Visibility` (from `Types.BlogPost`), `saving : RemoteData`, `publishing : RemoteData`
- **Msg flow**: `SetVisibility String -> SaveDraft/Publish -> SaveCompleted/PublishCompleted`
- **RemoteData states**: NotAsked -> Loading -> Success / Failure

---

## 3. API Calls

### `POST /api/blog/posts`
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.BlogController.create/2`
- **Request body**: `{ title: string, body: string, visibility: "owner" | "group" | "platform" }`
- **Response (success)**: `{ post: { id, user_id, title, body, visibility, published_at, created_at, updated_at } }` -- HTTP 201
- **Response (error)**: Changeset errors or visibility_ceiling error -- HTTP 422

### `PUT /api/blog/posts/:id`
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.BlogController.update/2`
- **Request body**: `{ title?, body?, visibility? }`
- **Response (success)**: `{ post: {...} }` -- HTTP 200
- **Response (error)**: `:not_found` (404), `:unauthorized` (403), `:visibility_ceiling` (422)

---

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` -> `AuthPipeline` (`:authenticated` scope) -> controller action
- **Visibility checks**: `Blog.create_post/2` and `Blog.update_post/3` both call `validate_ceiling/2` which delegates to `Visibility.validate_visibility_ceiling/3`. This ensures the post visibility rank >= the user's `profile_visibility` rank.
- **Age gate**: N/A
- **Ownership checks**: `Blog.update_post/3` calls `check_ownership/2` which pattern-matches `post.user_id == user.id`. Returns `{:error, :unauthorized}` on mismatch.

## 5. Database Interactions

### Write: Create post with visibility
- **Table(s)**: `op.blog_posts`
- **Operation**: INSERT
- **Fields**: `user_id`, `title`, `body`, `visibility` (default "owner"), `visibility_group_id` (optional), `published_at` (nil for drafts)
- **Changeset validations**: `validate_required([:user_id, :title, :body])`, `validate_inclusion(:visibility, ~w(owner group platform))`
- **Schema module**: `Stacks.Blog.Post`

### Write: Update post visibility
- **Table(s)**: `op.blog_posts`
- **Operation**: UPDATE
- **Fields**: Any of `title`, `body`, `visibility`, `visibility_group_id`, `published_at`
- **Module**: `Stacks.Blog.update_post/3`

### Write: Tighten posts to ceiling (from `VisibilityRecapJob`)
- **Table(s)**: `op.blog_posts`
- **Operation**: UPDATE (batch in transaction)
- **Query**: `from p in Post, where: p.user_id == ^user_id` then filtered for violations
- **Module**: `Stacks.Blog.tighten_posts_to_ceiling/2`

### Read: Posts visible to viewer
- **Table(s)**: `op.blog_posts`
- **Query**:
  - Owner sees all: `from p in Post, where: p.user_id == ^user_id, order_by: [desc: p.created_at]`
  - Non-owner sees published only: `from p in Post, where: p.user_id == ^user_id and not is_nil(p.published_at), order_by: [desc: p.published_at]`
  - Then filtered by `Visibility.can_view?/2`
- **Module**: `Stacks.Blog.list_user_posts/2`

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.BlogNew` (new post), `Route.BlogEdit postId` (edit)
- **URL**: `/blog/new`, `/blog/posts/:id/edit`
- **Public or authenticated**: Authenticated

### Init
- **New mode**: `{ mode = New, title = "", body = "", visibility = Owner, saving = NotAsked, publishing = NotAsked, loading = NotAsked }`
- **Edit mode**: Sets `loading = Loading`, fires `Api.getBlogPost postId maybeToken PostLoaded`

### Update cycle
- **Msg**: `SetVisibility String` -- parses string to `Visibility` union type (`Owner` / `Group` / `Platform`), resets save state.
- **Model change**: `visibility = parsed_value, saving = NotAsked`
- **Cmd**: None

- **Msg**: `SaveDraft` -- sends create or update API call depending on mode.
- **Model change**: `saving = Loading`
- **Cmd**: `Api.createBlogPost` or `Api.updateBlogPost`

- **Msg**: `Publish` -- saves first, then publishes on `SaveCompleted`.
- **Model change**: `publishing = Loading, saving = Loading`
- **Cmd**: Create/update API call, then on success fires `Api.publishBlogPost`

### View
- **Key elements**:
  - Visibility dropdown with three options: "Only me" (owner), "Group", "Platform"
  - Save Draft button, Publish button
  - Feedback messages for save/publish success/failure
- **ARIA attributes**: N/A
- **CSS classes**: `page--blog-editor`, `blog-editor__form`, `form-field`, `form-field__select`, `blog-editor__actions`, `btn--secondary` (Save Draft), `btn--primary` (Publish)

## 13. Operational Metrics

- **Blog visibility change count**: Total post visibility updates (via create or update), segmented by visibility level (owner, group, platform). Tracks post visibility distribution across the platform.
- **Ceiling violation rejection count**: Number of times `validate_ceiling/2` rejects a post visibility for exceeding the profile ceiling. Indicates users attempting to publish more broadly than their profile allows.
- **Blog CRUD operation counts**: `blog.post_created`, `blog.post_updated` events provide create and update throughput. Post deletion is tracked via `blog.post_deleted`.
- **Visibility recap tightening**: Count of posts capped by `Blog.tighten_posts_to_ceiling/2` during `VisibilityRecapJob` runs. Tracked in the `user.visibility_recap_completed` event payload (`posts_capped`).

---

## 14. Performance & Usability Metrics

- **Blog post save/publish latency**: Round-trip time for `POST /api/blog/posts` (create), `PUT /api/blog/posts/:id` (update), and `POST /api/blog/posts/:id/publish`. All are single-row INSERT/UPDATE operations on `op.blog_posts`.
- **Blog post read counts per visibility level**: Distribution of `GET /api/blog/posts/:id` requests segmented by the post's visibility level. Indicates which visibility tiers generate the most read traffic.
- **Visibility resolution latency for posts**: Time for `Visibility.can_view?/2` on post resources. Includes profile ceiling, block check, and resource visibility -- runs on every post read.

---

## 15. Cost Tracking

- All blog visibility operations are low-cost DB reads and writes only -- single-row INSERT/UPDATE on `op.blog_posts`.
- **Neon**: Minimal compute cost per individual visibility change. The `tighten_posts_to_ceiling/2` batch operation during recap is the most expensive path, running a transactional UPDATE across all of a user's posts.
- **dbt**: `blog.post_updated` triggers `DbtRefreshHandler`, which incurs Neon compute cost for the affected dbt model refresh.
- No external service calls, no storage operations, no email notifications for visibility changes specifically.

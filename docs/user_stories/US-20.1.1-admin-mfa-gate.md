# US-20.1.1 — Reach the Admin Surfaces Behind a Second Factor

## 1. User Story

> **As the** platform owner, **I want** every admin surface to require a second factor and a session of its own **so that** a stolen password — or my own ordinary browser session — cannot reach the data and controls that only I should touch.

**Retro-story (spec-of-record).** The admin MFA gate shipped in Issues #237 / #303 / #332 and had no story file. Written 2026-08-06 from the code; every claim cites the implementation.

**Family US-20.x** is new: *Platform Owner / Operations* — the owner-facing surfaces that are not product features and have no reader in them. `US-20.1.x` is the admin gate; `US-20.2.x` is owner-side data correction (see US-20.2.1).

**What the owner wants to accomplish:** Open `/admin/sources`, `/admin/scrapers`, `/admin/book-moderation`, or `/admin/removal-requests` — surfaces that read other people's data and act on it — and be certain that reaching them took a second factor, that the session ends quickly, and that every call was recorded.

**How they accomplish it:**
1. The owner navigates to any `/admin/*` route.
2. Because no admin token is held, the route resolves to the **admin sign-in gate** rather than to the page (`Main.elm:999-1005`). A page is never allowed to render holding a credential it cannot use.
3. The gate asks for owner email + password → an *unverified* admin session id.
4. The gate asks for the current TOTP code → the **admin token**.
5. The route the owner originally asked for is re-resolved and loads (`Main.elm:2788-2808`).
6. Thirty minutes later the token and the MFA window are both dead, and the flow starts again.

If the account has no second factor yet, step 3 does not dead-end: the gate starts enrolment inline, shows the provisioning URI and ten recovery codes, and confirms with a TOTP code.

**What they see on the page:**
- Title "Admin sign-in" and the subtitle *"Admin surfaces need a second factor and a session of their own. Your ordinary session is untouched, and this one ends after 30 minutes."* (`Page/Admin/Session.elm:322-327`)
- Owner email + password fields, a "Continue" button, and a secondary "Set up a second factor" button — reachable *without* failing a sign-in first.
- Then a single code field with "Enter the current code from your authenticator."
- On failure, a message that names the remedy rather than "something went wrong".

**Acceptance Criteria:**
- Non-owners are refused, with a distinct error from a wrong password.
- An owner with no enrolled factor cannot obtain an admin session — but can enrol from the same screen.
- The admin token is `typ: "admin_session"`, bound to the client IP and the node's boot id, and expires in 30 minutes.
- MFA counts as verified only within a 30-minute window.
- Every admin API call is audited, including its latency and the rows it touched.
- The admin token is never persisted client-side.

## 2. UI Interaction Flow

### Happy Path
1. Owner (already signed in ordinarily) navigates to `/admin/sources`.
2. `initPage` sees `isAdminRoute route && adminToken == Nothing` → `PageAdminGate Route.AdminSourceApproval AdminSession.init`.
3. Owner types email + password, submits → `SubmitCredentials` → `Api.adminLogin`.
4. `POST /api/admin/auth/login` returns `{session_id}` → `LoggedIn (Ok session)` → `step = AwaitingCode sessionId`, and **the password field is cleared in the same update** (`Session.elm:152-157`).
5. Owner types the TOTP code, submits → `SubmitCode` (refused client-side below 6 characters) → `Api.adminVerifyMfa`.
6. `POST /api/admin/auth/verify_mfa` returns `{token}` → `Verified (Ok token)` → `OutMsg Authenticated token`.
7. `Main` stores it in `model.adminAuth` and re-runs `initPage` for `gatedRoute`, so the owner lands on the page they asked for.

### Enrolment path
1. Either `LoggedIn (Err MfaNotEnrolled)` or an explicit click on "Set up a second factor" calls `startEnrolmentIfPossible`.
2. That needs the **ordinary owner token** (`Maybe.map .token (currentAuth model.auth)`) — necessarily, since you cannot hold an admin session before enrolling the factor it requires.
3. `POST /api/admin/auth/mfa/setup` returns `{provisioning_uri, recovery_codes}` → `step = Enrolling enrolment`.
4. The owner scans the URI, types a code → `ConfirmEnrolment` extracts the **base32** `secret=` parameter via `enrolmentSecret` → `POST /api/admin/auth/mfa/confirm`.
5. On success the gate returns to the **credentials step** with the notice "Your second factor is set up. Sign in to open an admin session."

### Sad Paths
| Situation | HTTP / result | What the operator is told |
|-----------|---------------|---------------------------|
| Wrong email or password | `401 invalid_credentials` | "That email and password did not match." |
| Email never confirmed | `403 email_unconfirmed` | (falls through to the transport message — see the gap in §16) |
| Account is not `role: "owner"` | `403 insufficient_role` | "That account is not an owner, so it cannot hold an admin session." |
| Owner has no MFA enrolled | `403 mfa_not_enrolled` | Not shown as an error — enrolment starts inline |
| Wrong / stale TOTP code | `401 invalid_code` | "That code was not accepted. Codes expire every 30 seconds — try the current one." |
| Session revoked, expired, or from another boot | `401 invalid_session` | "That admin session is no longer valid — a network change or a deploy ends it. Start again." |
| MFA already verified on that session | `409 already_verified` | "That session is already verified. Reload the page." |
| Enrolment secret malformed | `422 invalid_secret` | "That enrolment link looks malformed." |
| Not signed in ordinarily, and enrolment attempted | — | "Sign in to The Stacks first, then return here." |
| Admin token present but MFA window lapsed | `403 mfa_required` from `RequireMFA` | Handled per admin page |
| Page reloaded | admin token lost (memory only) | Sign in again — the honest consequence of a short-lived credential |

⚠️ **"That admin session is no longer valid" deliberately does not say "expired."** The session is bound to both the client IP hash and the node's `boot_id`, so a network switch or a deploy ends it. An operator told only "signed out" goes looking for the wrong problem (`Session.elm:301-306`).

### Elm State Machine
- **Page module**: `Page.Admin.Session`
- **Step type**: `Credentials | AwaitingCode String | Enrolling AdminMfaEnrolment` — a union rather than a bag of `Maybe`s, so "awaiting a code with no session id" is unrepresentable (`Session.elm:46-53`)
- **Model fields involved**: `step`, `email`, `password`, `code`, `error : Maybe String`, `notice : Maybe String`, `busy : Bool`
- **Msg flow**: `SubmitCredentials → LoggedIn → SubmitCode → Verified → OutMsg Authenticated`; enrolment branch `StartEnrolment → EnrolmentStarted → ConfirmEnrolment → EnrolmentConfirmed`
- **OutMsg pattern**: `NoOut | Authenticated String` — the module never stores the token; `Main` holds it
- **`notice` is separate from `error`** so a success and a failure cannot be rendered as each other (`Session.elm:63-65`)

## 3. API Calls

### `POST /api/admin/auth/login`
- **Auth**: None (credentials are the payload)
- **Pipeline**: `:api`, `:rate_limit_auth` (`router.ex:363`)
- **Controller**: `StacksWeb.AdminAuthController.login/2`
- **Request body**: `{ email: string, password: string }`
- **Response (success)**: `{ session_id: uuid }` — HTTP 200. The session exists but is **unverified**.
- **Response (error)**: `401 {error: "invalid_credentials"}` · `403 {error: "email_unconfirmed"}` · `403 {error: "insufficient_role"}` · `403 {error: "mfa_not_enrolled"}`
- **Side effect**: `Audit.log(user.id, "admin.login", …, operator_session_id: session.id)`

### `POST /api/admin/auth/verify_mfa`
- **Auth**: None beyond possession of the `session_id`
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `AdminAuthController.verify_mfa/2`
- **Request body**: `{ session_id: uuid, totp_code: string }` **or** `{ session_id: uuid, recovery_code: string }`
- **Response (success)**: `{ token: jwt }` — HTTP 200, `token_type: "admin"`, `session_id` and `boot_id` in the claims, `ttl: {30, :minute}`
- **Response (error)**: `409 already_verified` · `401 invalid_session` · `401 invalid_code`
- **Side effect**: `SessionContext.mark_mfa_verified/1` + `Audit.log(user.id, "admin.mfa_verified", …)`

### `POST /api/admin/auth/mfa/setup`
- **Auth**: Required — the **ordinary** Guardian token
- **Pipeline**: `:api`, `:authenticated`, `:require_owner`, `:rate_limit_auth` (`router.ex:374-377`)
- **Response**: `{ provisioning_uri: "otpauth://totp/The%20Stacks:…?secret=<BASE32>&issuer=The%20Stacks", recovery_codes: [10 strings] }`
- ⚠️ The secret is **not persisted** at this point. `begin_enrollment/1` returns it and the client must hand it back to `confirm`.

### `POST /api/admin/auth/mfa/confirm`
- **Auth**: Required — the ordinary owner token, same pipeline as setup
- **Request body**: `{ totp_code: string, secret: <BASE32, exactly as published>, recovery_codes: [string] }`
- **Response**: `{ ok: true }` — HTTP 200 · `422 invalid_code` · `422 invalid_secret`
- ⚠️ **base32, because that is what `mfa_setup` publishes.** This endpoint decoded *base64* until 2026-07-29, and nothing a client can reach ever holds base64 — the provisioning URI's `secret=` is base32 (the TOTP standard). Every client had to base32-decode and re-base64-encode, and getting it wrong returns `422 invalid_code`, which reads as clock skew. The tests missed it because they called `MFA.begin_enrollment/1` directly for the raw bytes, **bypassing the contract a client must use** (`admin_auth_controller.ex:116-126`).

### `DELETE /api/admin/auth/logout`
- **Auth**: Required — admin token
- **Pipeline**: `:api`, `:admin` (`router.ex:368-371`)
- **Response**: `{ ok: true }`; `SessionContext.revoke/1` stamps `revoked_at`

### What the gate protects
Every route under `pipe_through [:api, :admin, …]`: `GET /api/admin/users/by_email`, `by_id`, `audit_log`, `platform_stats`, `gdpr_export`, `POST /api/admin/gdpr_erase` (`router.ex:381-389`), the source/scraper/moderation/removal-request surfaces, and — with `:require_owner` stacked on top — the data-correction routes (`router.ex:395-402`, see US-20.2.1).

## 4. Auth & Middleware Guards

**`pipeline :admin`** is three plugs, in this order (`router.ex:73-77`):

1. **`StacksWeb.Plugs.AdminAuthPipeline`** — extracts the Bearer token, `Guardian.decode_and_verify`, requires `claims["typ"] == "admin_session"`, then `SessionContext.get_valid(claims["sid"], client_ip)`, then loads the user. Assigns `:current_user` and `:admin_session`. Any failure → `401 {error: "unauthorized"}` and halt.
2. **`StacksWeb.Plugs.RequireMFA`** — reads `conn.assigns.admin_session` and requires `mfa_verified_at` within the last **30 minutes**. Otherwise `403 {error: "mfa_required"}` and halt.
3. **`StacksWeb.Plugs.AuditAdminCall`** — registers a `before_send` callback that writes `Audit.log(user_id, "admin.call", …)` with `endpoint`, `latency_ms`, `success`, `row_count` (whatever the controller assigned to `:audit_row_count`), `operator_session_id`, and `metadata: %{reason:, method:}`. **Audit failures are swallowed** — a failing audit write must never fail the admin request, but it *is* logged at error level.

**`SessionContext.get_valid/2` refuses on five distinct grounds** (`session_context.ex:61-84`), each a separate error atom: `:not_found`, `:revoked`, `:expired`, `:boot_id_mismatch`, `:ip_mismatch`.

- **IP binding**: the raw IP is SHA-256 hashed before storage — same convention as `audit_log` — and compared as a hash. The IP itself is never stored.
- **Boot binding**: sessions are bound to `Core.Application.boot_id()`, so a process restart invalidates every session from the previous boot. A deploy is a logout.
- **Two clocks, deliberately**: the admin *session* expires 30 minutes after creation (`@session_ttl_minutes 30`), the *token* carries `ttl: {30, :minute}`, and MFA verification is separately valid for 30 minutes (`RequireMFA.@mfa_window_minutes`). They are all 30, and they are all checked.
- **Ordinary session untouched**: nothing here revokes or extends the reader's normal Guardian token. The subtitle says so because it is true.

⚠️ **`:require_owner` on top of `:admin` is not redundant** where writes happen. `login/2` already refuses a non-owner, but an admin token outlives the role it was minted under: demote the account and the pipeline keeps loading the user for the rest of the session. For a read that is unfortunate; for a mutation it is a stale token that can still write. That is #332's lesson, and it is why the data-correction routes re-check the role at the point of use (`data_correction_controller.ex:44-53`).

## 5. Database Interactions

### Write: create an unverified admin session
- **Table**: `op.admin_sessions`
- **Operation**: INSERT
- **Fields**: `user_id`, `ip_hash` (SHA-256 hex), `boot_id`, `expires_at = now + 30min`
- **Validations**: all four required
- **Schema module**: `Stacks.AdminSession`

### Write: mark MFA verified
- **Table**: `op.admin_sessions`
- **Operation**: UPDATE `mfa_verified_at = now()`

### Write: revoke
- **Table**: `op.admin_sessions`
- **Operation**: UPDATE `revoked_at = now()`

### Read: validate a session on every admin call
- **Table**: `op.admin_sessions`
- **Query**: `Repo.get(AdminSession, session_id, prefix: "op")` then the five-way `cond`

### Write: enrol a second factor
- **Table**: `op.user_mfa`
- **Operation**: INSERT with `on_conflict: {:replace_all_except, [:id, :created_at]}, conflict_target: :user_id` — so re-enrolment replaces rather than duplicating
- **Fields**: `user_id`, `totp_secret` (**encrypted at rest** via `Stacks.EncryptedBinary`), `recovery_codes` (SHA-256 hex hashes, never plaintext), `enabled_at`
- **Schema module**: `Stacks.MFA.UserMFA`

### Write: consume a recovery code
- **Table**: `op.user_mfa`
- **Operation**: UPDATE `recovery_codes` with the used hash removed — so a code cannot be replayed (`mfa.ex:177-184`)

### Write: audit rows
- **Table**: `audit.audit_log`
- **Rows per successful sign-in**: `admin.login`, `admin.mfa_verified`, then one `admin.call` per admin request thereafter

## 6. Event Flow & Lifecycle

### Events Emitted
**None on the `event_log`.** Admin authentication is recorded in `audit.audit_log`, not the domain event bus. The distinction is deliberate: `event_log` is the domain's immutable history and is warehouse-adjacent; operator authentication is an audit fact about a human, and the audit schema is where GDPR expects to find it.

### Telemetry
- `[:stacks, :auth, :mfa, :verify]` with `%{count: 1}` and `%{outcome: :success | :failure}`, fired on **both** the TOTP and recovery-code paths — so every code-checking route an attacker brute-forces is observable (Issue #237).
- ⚠️ `outcome` is a bounded whitelisted atom. Never the code, the secret, or the user id — telemetry is warehouse-adjacent (`mfa.ex:168-175`).

### Event Handlers Triggered
None.

## 7. Background Jobs (Oban)

None enqueued by this story. Adjacent: `Stacks.Workers.GuardianTokenSweepJob` reaps expired `op.guardian_tokens` rows, which includes dead admin tokens — see US-14.5.1.

**Not swept:** `op.admin_sessions`. Expired and revoked rows accumulate. They are inert (every one of the five `get_valid/2` grounds rejects them) so this is a table-size question, not a security one — but it is an unswept table, and worth a follow-up alongside the family-pruning `GuardianTokenSweepJob` already does.

None. TOTP is computed locally by `NimbleTOTP`; the authenticator app is the operator's own. There is no SMS, no push, no third-party MFA provider — and therefore no MFA vendor to trust, and no phone number to hold.

## 10. Cache Interactions

None server-side. Client-side, the admin token is held **in memory only** — `Main.adminAuth`, no port, no `localStorage` (`Page/Admin/Session.elm:20-23`). It needs no persistence machinery, it is the highest-value credential in the system, and MFA expires in 30 minutes anyway. A reload means signing in again.

## 11. dbt Model Dependencies

None. Admin sessions and MFA records are deliberately **outside** the warehouse: `op.user_mfa` holds an encrypted TOTP secret and recovery-code hashes, and `op.admin_sessions` holds an IP hash. Neither has a staging model, and neither should acquire one.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: none of its own. The gate is not routable — it is what an `/admin/*` route resolves to while `adminTokenFor model == Nothing`.
- **Page constructor**: `PageAdminGate Route AdminSession.Model` — it carries the route the operator was going to, so signing in lands them there rather than on a "now navigate again" screen.
- **Gated routes**: `Route.AdminSourceApproval` (`/admin/sources`), `AdminScraperConfig` (`/admin/scrapers`), `AdminBookModeration` (`/admin/book-moderation`), `AdminRemovalRequests` (`/admin/removal-requests`)

### Init
- `AdminSession.init` — `step = Credentials`, everything else empty. No API call on mount.

### Update cycle
| Msg | Model change | Cmd / OutMsg |
|-----|--------------|--------------|
| `SubmitCredentials` | `busy = True`, `error = Nothing`; no-op if either field is empty | `Api.adminLogin` |
| `LoggedIn (Ok s)` | `step = AwaitingCode s.sessionId`, `busy = False`, **`password = ""`** | — |
| `LoggedIn (Err MfaNotEnrolled)` | `step = Credentials`, `error = Nothing` | → `startEnrolmentIfPossible` |
| `LoggedIn (Err e)` | `error = Just (authErrorMessage e)` | — |
| `SubmitCode` | `busy = True`; no-op below 6 trimmed characters | `Api.adminVerifyMfa` |
| `Verified (Ok t)` | `busy = False`, `code = ""` | **`OutMsg Authenticated t`** |
| `Verified (Err e)` | `code = ""`, `error = Just …` | — |
| `EnrolmentStarted (Ok e)` | `step = Enrolling e` | — |
| `ConfirmEnrolment` | `busy = True` | `Api.adminMfaConfirm token {code, secret, recoveryCodes}` |
| `EnrolmentConfirmed (Ok ())` | `step = Credentials`, `notice = Just "Your second factor is set up. Sign in to open an admin session."` | — |

⚠️ `EnrolmentConfirmed (Ok ())` **returns to the credentials step rather than a terminal panel.** It used to render a panel reading "Sign in above to open an admin session" — while being the only thing on the page, having replaced the form. The operator finished enrolling and had nowhere to go but a manual reload, and the copy actively misdirected them. Found by driving the flow rather than reading it (`Session.elm:234-240`).

### `enrolmentSecret` — why it hand-parses
`Url.fromString` rejects the `otpauth:` scheme, so the query is split manually and the `secret=` value taken **base32, unmodified**. Exposed from the module so a test can assert the extraction without driving the whole flow (`Session.elm:102-127`).

### View
- **Key elements**: `h1` "Admin sign-in"; subtitle naming the 30-minute lifetime; `notice` and `error` rendered as separate paragraphs; then one of the three step views
- **Enrolment step**: an ordered list of the ten recovery codes (one-time display) plus the provisioning URI
- **ARIA attributes**: `label`/`for` pairs on every field; buttons carry real `type_`. **Gap:** neither `admin-gate-error` nor `admin-gate-notice` has `role="alert"` / `aria-live`, so a failure is silent to a screen reader.
- **CSS classes**: `page--admin`, `admin-gate`, `admin__title`, `admin__subtitle`, `admin__error`, `admin-gate__notice`, `admin-gate__field`, `admin-gate__input`, `admin-gate__submit`, `admin-gate__secondary`, `admin-gate__hint`
- **Test ids**: `admin-gate`, `admin-gate-notice`, `admin-gate-error`, `admin-email`, `admin-password`, `admin-continue`, `admin-enrol-start`

### The build-time guard
`scripts/check-admin-token-routing.sh` fails the build if any admin call site passes anything other than `adminTokenFor` (`Main.elm:879-886`). That exists because the original defect was exactly this: four admin pages passing the **ordinary** Guardian token, which `pipeline :admin` rejects with 401 — so source approval, scraper health, book moderation and the removal queue **had never loaded for anyone**, and every one of them looked finished from the code and its tests (#303, found by #309). `adminTokenFor` takes the whole `Model` precisely so it is impossible to hand it the ordinary session by mistake.

## 16. Known Gaps

Recorded here rather than quietly omitted, because a spec-of-record that hides its edges is the thing this wave exists to fix.

1. **`email_unconfirmed` has no operator-facing message.** `Api.adminErrorFromBody` maps `invalid_credentials`, `insufficient_role`, `mfa_not_enrolled`, `invalid_code`, `invalid_session`, `already_verified` — but not `email_unconfirmed`, which the login endpoint can return (`admin_auth_controller.ex:43-44`). It falls through to `AdminAuthTransport (Http.BadBody body)` → "Could not reach the server. Please try again." — which is wrong, and sends the operator after a network problem that does not exist.
2. **No `aria-live` on the gate's error or notice**, so a screen-reader operator gets no announcement of a failed sign-in.
3. **`op.admin_sessions` is never swept** (§7).
4. **`MFA.disable/2` is unreachable over HTTP.** The context function exists and is tested, but no route calls it — an owner cannot turn off or rotate their second factor except by re-enrolling (which the `on_conflict` upsert does support).
5. **Recovery-code exhaustion is silent.** `consume_recovery_code/2` removes the used hash; nothing warns when the list runs low or empty, and nothing reissues.
6. **Rate limiting is the shared `:auth` bucket**, not an admin-specific one. `pipeline :rate_limit_admin` exists and guards the admin *data* routes, but the login/verify pair sits behind `:rate_limit_auth` alongside ordinary sign-in.

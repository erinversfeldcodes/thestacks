# US-10.2.2 — Override Placement Visibility

## 1. User Story

> **As a** user, **I want to** make an individual book on a shelf less visible than the shelf itself **so that** I can hide specific books from people who can otherwise see the shelf.

The shelf is visible to close friends, but one book on it is too personal to share -- hide just that book without hiding the whole shelf.

**Ceiling rule:** a placement cannot be made *more* visible than its shelf. The options shown are always a subset of or equal to the shelf's current visibility.

---

## 2. UI Interaction Flow

### Happy Path
1. User opens a book's context menu on a shelf or detail overlay.
2. Selects "Visibility for this copy."
3. Modal shows visibility options, with options greyed out that exceed the shelf's ceiling.
4. User selects a visibility level equal to or more restrictive than the shelf.
5. System updates the placement's visibility.
6. On the shelf view, the book shows as a faint outline spine to the owner only.

### Sad Paths
- **Exceeds shelf ceiling**: The `Visibility.validate_visibility_ceiling/3` function prevents setting a placement visibility less restrictive than the shelf. Options are greyed out with tooltip: "This shelf is set to [level] -- placements can't be more visible than their shelf."
- **Not placement owner**: Ownership check fails, returns `{:error, :unauthorized}`.

### Elm State Machine
- **Page module**: Bookshelf page or book detail overlay.
- **Model fields involved**: Placement visibility state, shelf ceiling value.
- **Msg flow**: `UserSelectsPlacementVisibility -> UpdatePlacementVisibility -> GotUpdateResponse`
- **RemoteData states**: NotAsked -> Loading -> Success / Failure

---

## 3. API Calls

### Placement visibility update
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: Placement controller
- **Request body**: `{ visibility: "owner" | "group" | "platform" }`
- **Response (success)**: Updated placement with new visibility -- HTTP 200
- **Response (error)**: 422 if visibility exceeds shelf ceiling, 401/403 if unauthorized

---

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` -> `AuthPipeline` (`:authenticated` scope) -> controller action
- **Visibility checks**: `Stacks.Visibility.resolve_visibility/2` for placements:
  1. Preloads the bookshelf via `maybe_preload_bookshelf/1`.
  2. Checks marketplace exception: if the placement is on `looking_for_home` with `listing_status: "active"`, it is always visible (marketplace items must be discoverable).
  3. Runs `do_resolve/3`: profile ceiling -> block check -> age gate -> resource visibility.
  4. Owner ID is extracted from the placement's bookshelf's `user_id`.
- **Ceiling enforcement**: `Visibility.validate_visibility_ceiling/3` ranks visibility: `"public"` (0) < `"platform"` (1) < `"owner"` (2). A child (placement) must have a rank >= its parent (shelf).
- **Ownership checks**: Controller verifies placement belongs to a bookshelf owned by the authenticated user.

---

## 5. Database Interactions

### Write: Update placement visibility
- **Table(s)**: `op.bookshelf_placements`
- **Operation**: UPDATE
- **Fields**: `visibility` (valid values: `"owner"`, `"group"`, `"platform"`)
- **Schema module**: `Stacks.Shelving.Placement`

### Read: Viewable placements for a shelf
- **Table(s)**: `op.bookshelf_placements`
- **Query**: `from p in Placement, where: p.bookshelf_id == ^shelf_id` then filtered by `Visibility.can_view?/2`
- **Module**: `Stacks.Visibility.viewable_placements/2`

### Read: Resolve placement visibility
- **Table(s)**: `op.bookshelf_placements`, `op.bookshelves`, `op.users`, `op.user_blocks`
- **Preloads**: Bookshelf (for owner ID and shelf visibility)
- **Module**: `Stacks.Visibility.resolve_visibility/2`

## 13. Operational Metrics

- **Placement visibility change count**: Total placement visibility updates, segmented by target visibility level (owner, group, platform). Tracks how often users hide individual books on otherwise-visible shelves.
- **Ceiling violation rejection count**: Number of times `Visibility.validate_visibility_ceiling/3` rejects a placement visibility change for exceeding the shelf ceiling. Indicates attempts to make a placement more visible than its parent shelf.
- **Visibility change events**: No dedicated event is emitted for individual placement visibility changes. Bulk changes during profile ceiling tightening are tracked via `VisibilityRecapJob` (see US-10.1.1).

---

## 14. Performance & Usability Metrics

- **Placement visibility save latency**: Round-trip time for the placement visibility update API call. Single-row UPDATE on `op.bookshelf_placements` -- expected sub-10ms at the database level.
- **Visibility resolution latency for placements**: Time for `Visibility.resolve_visibility/2` on placement resources. Includes `maybe_preload_bookshelf/1`, marketplace exception check, profile ceiling, block check, age gate, and resource visibility. More complex than shelf-level resolution due to the preload and marketplace logic.
- **Placement visibility modal load time**: Time to render the visibility options modal with shelf ceiling information and greyed-out options.

---

## 15. Cost Tracking

- All placement visibility operations are low-cost DB reads and writes only -- single-row UPDATE on `op.bookshelf_placements`.
- **Neon**: Minimal compute cost per change. The `resolve_visibility/2` check for placements is slightly more expensive than for shelves due to the bookshelf preload (JOIN to get owner ID and shelf visibility), but still a single query per access.
- No external service calls, no storage operations, no email notifications.

# US-17.3.1 — Email Notification Preferences

## 1. User Story

> **As a** user, **I want to** control which emails The Stacks sends me **so that** I only receive messages I care about — the platform should be quiet by default.

**Acceptance criteria:**
- `/settings/notifications` renders the notification preferences page
- Terms of service notifications cannot be disabled (not yet implemented in UI — spec only)
- All other categories are toggleable
- Changes save automatically without a submit button
- Default states match the specification (most off by default)

---

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/settings/notifications` via the settings sidebar.
2. Page shows "Notification Preferences" with four toggle rows.
3. User clicks a toggle. The toggle state flips immediately in the UI.
4. An API call fires automatically (no save button needed).
5. On success: "Preferences saved." confirmation.

### Current Toggle Categories
As implemented in `Page.Settings.Notifications`:
1. **Price Drops** — default: off
2. **New Reviews** — default: off
3. **Author Updates** — default: off
4. **Event Alerts** — default: off

**Note**: The spec defines different categories (WishList availability, Marketplace activity, Group invitations, Event matches) and a locked "Terms of service" toggle. The backend `User` schema has `notify_wishlist_availability`, `notify_marketplace`, `notify_group_invitations`, `notify_event_matches` fields. The frontend toggle labels do not match the backend fields — `Api.updateNotifications` in `frontend/src/Api.elm` maps `priceDrops -> notify_wishlist_availability`, `newReviews -> notify_marketplace`, `authorUpdates -> notify_group_invitations`, `eventAlerts -> notify_event_matches` before sending the request. The downstream wiring that consumes these flags (e.g. `WishlistAvailabilityHandler`, `EmailDeliveryJob`) was completed in Issue #152.

### Sad Paths
- **Save fails**: "Could not save notification preferences. Please try again."

### Elm State Machine
- **Page module**: `Page.Settings.Notifications`
- **Model fields**: `priceDrops`, `newReviews`, `authorUpdates`, `eventAlerts` (all Bool), `saving : RemoteData Http.Error ()`
- **Msg flow**: `TogglePriceDrops`/`ToggleNewReviews`/`ToggleAuthorUpdates`/`ToggleEventAlerts` -> flip boolean, immediately call `savePreferences` -> `SaveCompleted`
- **Auto-save**: Each toggle fires an API call immediately, no explicit save step.

## 3. API Calls

### `PUT /api/settings/notifications`
- **Auth**: Required (Bearer JWT)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.UserSettingsController.update_notifications/2`
- **Request body**: `{ "notify_wishlist_availability": bool, "notify_marketplace": bool, "notify_group_invitations": bool, "notify_event_matches": bool }` — the frontend translates its UI-facing names (`priceDrops`, `newReviews`, `authorUpdates`, `eventAlerts`) to these backend field names in `Api.updateNotifications`.
- **Response (success)**: `{ "notify_wishlist_availability": bool, "notify_marketplace": bool, "notify_group_invitations": bool, "notify_event_matches": bool }` — HTTP 200
- **Response (error)**: `{ "errors": { ... } }` — HTTP 422
- **Context function**: `Accounts.update_notifications/2` — applies `User.notifications_changeset/2`

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.SettingsNotifications`
- **URL**: `/settings/notifications`
- **Public or authenticated**: Authenticated only
- **Browser tab title**: "Notifications — The Stacks"

### Init
- **`Notifications.init`**: `{ priceDrops = False, newReviews = False, authorUpdates = False, eventAlerts = False, saving = NotAsked }`
- **Note**: Preferences are not loaded from the server on init — they start at their default values. The current implementation does not fetch the user's saved preferences.

### Update cycle
- **Msg**: `TogglePriceDrops` -> flip `priceDrops`, call `savePreferences`
- **Msg**: `ToggleNewReviews` -> flip `newReviews`, call `savePreferences`
- **Msg**: `ToggleAuthorUpdates` -> flip `authorUpdates`, call `savePreferences`
- **Msg**: `ToggleEventAlerts` -> flip `eventAlerts`, call `savePreferences`
- **`savePreferences`**: If token present, calls `Api.updateNotifications prefs token SaveCompleted`
- **Msg**: `SaveCompleted (Ok _)` -> `saving = Success ()`
- **Msg**: `SaveCompleted (Err err)` -> `saving = Failure err`

### View
- Wrapped in `viewSettingsHub` layout.
- `h1` "Notifications", `h2` "Notification Preferences"
- Description: "Choose which notifications you would like to receive."
- Four toggle rows, each with:
  - `div.toggle-row` containing `label.toggle-row__label` and `button.toggle` (`toggle--on` or `toggle--off`)
  - Toggle text: "On" or "Off"
- Feedback below: `p.success` "Preferences saved." or `p.error` on failure.
- **CSS classes**: `page--settings`, `settings-section`, `toggle-row`, `toggle-row__label`, `toggle`, `toggle--on`, `toggle--off`, `success`, `error`

## 13. Operational Metrics

- **Notification preference update rate**: Count of `PUT /api/settings/notifications` requests per day. Higher than expected rates may indicate auto-save is firing too aggressively.
- **Notification preference update success rate**: Ratio of HTTP 200 to total requests. Should be near 100%.
- **Toggle flip distribution**: Which toggles are most frequently changed (Price Drops, New Reviews, Author Updates, Event Alerts).
- **Preference state distribution**: What percentage of users have each notification type enabled vs disabled. Informs default value decisions.
- **Event emission reliability**: Count of `user.notifications_updated` events successfully written to `event_log`.
- **API call deduplication**: Whether rapid toggle flips (e.g., user toggling on then immediately off) result in redundant API calls.

---

## 14. Performance & Usability Metrics

- **Notification preference save latency**: p50/p95 for `PUT /api/settings/notifications` round-trip. Should be <200ms (simple DB UPDATE). Critical because saves are automatic on toggle — users see immediate feedback.
- **Toggle responsiveness**: Time from toggle click to visual state change. Should be <16ms (synchronous Elm model update, optimistic UI).
- **Save confirmation visibility**: How quickly "Preferences saved." appears after toggle. If the API call takes >500ms, users may toggle again thinking the first didn't register.
- **Preference load gap**: Preferences are not loaded from the server on init — they start at defaults. Track how often saved preferences differ from displayed defaults (indicates a UX bug where users see incorrect initial state).
- **Multi-toggle rate**: How often users change more than one toggle in a single session (each fires a separate API call).

---

## 15. Cost Tracking

- **Database writes**: One UPDATE to `op.users` per toggle change + one INSERT to `event_log`. Negligible Neon cost.
- **API call volume**: Auto-save fires on every toggle flip. If a user toggles 4 preferences, that is 4 API calls + 4 DB updates. Still negligible cost but worth monitoring for unnecessary call volume.
- **No external service calls**: Notification preference changes do not send emails or call external APIs.
- **Total per-toggle cost**: ~$0.00 (negligible DB write per toggle).

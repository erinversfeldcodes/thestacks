# US-10.1.2 — Block a User

## 1. User Story

> **As a** user, **I want to** block another user **so that** they cannot see my profile, content, or interact with me anywhere on the platform.

From any profile page, listing, comment, or Q&A, the user selects "Block [name]" from the overflow menu. The system confirms. The user confirms.

**Effects of blocking:**
- The blocked user's profile becomes invisible to the blocker, and vice versa.
- In shared spaces (blog comments, marketplace Q&A), neither party can see the other's contributions.
- Sub-threads rooted in a blocked user's comment collapse entirely rather than showing a `[hidden]` placeholder.
- The block is not notified to the blocked user -- they simply cannot find the blocker.

---

## 2. UI Interaction Flow

### Happy Path
1. User selects "Block [name]" from overflow menu on any profile/listing/comment.
2. Confirmation modal: "Block [name]? They won't be able to see your profile or content, and you won't see theirs."
3. User confirms.
4. System sends `POST /api/users/:id/block`.
5. System responds with `{ blocked: true }`.
6. UI updates: blocked user's content disappears immediately.

### Unblock Flow
1. User navigates to Settings > Privacy > Blocked Users.
2. System loads paginated list via `GET /api/settings/blocked-users`.
3. User clicks "Unblock" next to a user.
4. System sends `DELETE /api/users/:id/block`.
5. System responds with `{ blocked: false }`.

### Sad Paths
- **Block self**: Returns HTTP 422 `{ error: "cannot_block_self" }`.
- **Target not found**: Returns HTTP 404 `{ error: "not_found" }`.
- **Already blocked**: Returns HTTP 422 `{ error: "already_blocked" }` (unique constraint violation on `op.user_blocks`).
- **Unblock non-existent block**: Returns HTTP 404 `{ error: "not_found" }`.

### Elm State Machine
- **Page module**: Not a dedicated page; actions triggered from various contexts.
- **Model fields involved**: Block confirmation modal state, blocked users list.
- **Msg flow**: `UserClicksBlock -> ConfirmBlock -> PostBlock -> GotBlockResponse`
- **RemoteData states**: NotAsked -> Loading -> Success / Failure

---

## 3. API Calls

### `POST /api/users/:id/block`
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`, `:rate_limit_social` (20/min per user)
- **Controller**: `StacksWeb.SocialController.block/2`
- **Request body**: None (target user ID in URL path)
- **Response (success)**: `{ blocked: true }` -- HTTP 200
- **Response (error)**: `{ error: "cannot_block_self" }` -- HTTP 422, `{ error: "not_found" }` -- HTTP 404, `{ error: "already_blocked" }` -- HTTP 422

### `DELETE /api/users/:id/block`
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`, `:rate_limit_social`
- **Controller**: `StacksWeb.SocialController.unblock/2`
- **Request body**: None
- **Response (success)**: `{ blocked: false }` -- HTTP 200
- **Response (error)**: `{ error: "not_found" }` -- HTTP 404

### `GET /api/settings/blocked-users`
- **Auth**: Required (JWT Bearer token)
- **Pipeline**: `:api`, `:authenticated`
- **Controller**: `StacksWeb.SocialController.blocked_users/2`
- **Request params**: `page` (optional, default 1)
- **Response (success)**: `{ blocked_users: [{ id, display_name, blocked_at }], total: integer, page: integer }` -- HTTP 200

---

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` -> `AuthPipeline` (`:authenticated` scope) -> `RateLimiter` (bucket `:social`, 20 requests/min) -> controller action
- **Visibility checks**: `Stacks.Visibility.resolve_visibility/2` calls `check_block/2` which uses `Social.blocked?/2` -- bidirectional check. If either user has blocked the other, all content is `:hidden`.
- **Age gate**: N/A
- **Ownership checks**: Controller validates `user.id != target_id` (cannot block self) and checks target exists via `Accounts.get_user/1`.

## 5. Database Interactions

### Write: Create block
- **Table(s)**: `op.user_blocks`
- **Operation**: INSERT
- **Fields**: `blocker_id` (UUID), `blocked_id` (UUID), `created_at` (auto-timestamp)
- **Changeset validations**: `validate_required([:blocker_id, :blocked_id])`, `unique_constraint([:blocker_id, :blocked_id])`
- **Schema module**: `Stacks.Social.UserBlock`
- **Context function**: `Stacks.Social.block_user/2`

### Write: Remove block
- **Table(s)**: `op.user_blocks`
- **Operation**: DELETE
- **Query**: `from b in UserBlock, where: b.blocker_id == ^blocker_id and b.blocked_id == ^blocked_id`
- **Context function**: `Stacks.Social.unblock_user/2`

### Read: Check if blocked (bidirectional)
- **Table(s)**: `op.user_blocks`
- **Query**: `from b in UserBlock, where: (b.blocker_id == ^viewer_id and b.blocked_id == ^owner_id) or (b.blocker_id == ^owner_id and b.blocked_id == ^viewer_id)`
- **Returns**: boolean via `Repo.exists?/1`
- **Context function**: `Stacks.Social.blocked?/2`

### Read: Check if blocked (one-directional)
- **Table(s)**: `op.user_blocks`
- **Query**: `from b in UserBlock, where: b.blocker_id == ^viewer_id and b.blocked_id == ^owner_id`
- **Returns**: boolean
- **Context function**: `Stacks.Social.blocked_by?/2`

### Read: List blocked users (paginated)
- **Table(s)**: `op.user_blocks` joined with `op.users`
- **Query**: `from b in UserBlock, join: u in User, on: u.id == b.blocked_id, where: b.blocker_id == ^blocker_id, select: %{id, display_name, blocked_at}, order_by: [desc: b.created_at]`
- **Pagination**: 20 per page, offset-based
- **Context function**: `Stacks.Social.list_blocked_users/2`

## 13. Operational Metrics

- **Block/unblock counts**: Total `social.user_blocked` and `social.user_unblocked` events. Segmented by direction to identify users who block frequently.
- **Block error rate**: Count of `cannot_block_self`, `already_blocked`, and `not_found` error responses. High `already_blocked` rates suggest UI race conditions or stale state.
- **Active block count**: Total rows in `op.user_blocks` at any point in time. Tracks the scale of the block graph for query performance planning.
- **Rate limit hits**: Count of requests rejected by `:rate_limit_social` (20/min per user) on block/unblock endpoints. Indicates potential abuse.

---

## 14. Performance & Usability Metrics

- **Block/unblock save latency**: Round-trip time for `POST /api/users/:id/block` and `DELETE /api/users/:id/block`. Both are single-row INSERT/DELETE operations -- expected sub-10ms at the database level.
- **Block check query latency**: Time for `Social.blocked?/2` bidirectional check. This query runs on every visibility resolution via `Visibility.resolve_visibility/2`, so performance is critical. Monitor as the `op.user_blocks` table grows.
- **Blocked users list load time**: Latency for `GET /api/settings/blocked-users` with pagination (20 per page, offset-based). Join with `op.users` for `display_name`.

---

## 15. Cost Tracking

- All block operations are low-cost DB reads and writes only -- single-row INSERT/DELETE on `op.user_blocks`.
- **Neon**: The primary cost concern is the `blocked?/2` bidirectional check, which runs as part of `resolve_visibility/2` on every content access. This is a `Repo.exists?/1` query with an OR condition on two indexed columns. Aggregate compute cost scales with platform-wide content access volume, not just block operations.
- No external service calls, no storage operations, no email notifications.

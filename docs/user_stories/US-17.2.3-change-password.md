# US-17.2.3 — Change Password

## 1. User Story

> **As a** user, **I want to** change my password **so that** I can maintain account security.

**Acceptance criteria:**
- `/settings/password` renders the password change form
- The current password must be verified before the change is applied
- Password is hashed with Argon2 before storage
- Success/failure messages are clear and immediate

---

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/settings/password` via the settings sidebar.
2. Form shows three fields: Current Password, New Password, Confirm New Password.
3. User fills in all fields. Client-side validation runs:
   - New password must be >= 8 characters
   - New password and confirmation must match
   - Current password must be non-empty
4. User clicks "Change Password".
5. Button shows "Saving..." during API call.
6. On success: All fields are cleared (model resets to `init` with `saving = Success ()`). Message: "Password changed successfully."

### Sad Paths
- **Current password incorrect**: API returns 422 with `"invalid_current_password"`. User sees: "Current password is incorrect."
- **Validation failure**: Client-side validation prevents submission. Error shown inline:
  - "New password must be at least 8 characters."
  - "New password and confirmation do not match."
  - "Please enter your current password."
- **Generic error**: "Could not change password. Please try again."

### Elm State Machine
- **Page module**: `Page.Settings.Password`
- **Model fields**: `currentPassword`, `newPassword`, `confirmPassword`, `saving : RemoteData Http.Error ()`
- **Msg flow**: `SetCurrentPassword`/`SetNewPassword`/`SetConfirmPassword` -> `SavePassword` -> validate -> `Api.updatePassword` -> `SaveCompleted`
- **Validation**: `validate model` returns `Maybe ValidationError` — checked before API call.

---

## 3. API Calls

### `PUT /api/settings/password`
- **Auth**: Required (Bearer JWT)
- **Pipeline**: `:api`, `:authenticated`, `:rate_limit_password_change`
- **Controller**: `StacksWeb.UserSettingsController.update_password/2`
- **Request body**: `{ "current_password": string, "new_password": string }`
- **Response (success)**: `{ "ok": true }` — HTTP 200
- **Response (error)**:
  - `{ "error": "invalid_current_password" }` — HTTP 422
  - `{ "errors": { ... } }` — HTTP 422 (changeset validation)
  - `{ "error": "current_password and new_password are required" }` — HTTP 422 (missing params)
  - `{ "error": "service_busy" }` — HTTP 503 with `retry-after: 5` header (Argon2 worker pool exhausted — see Issue #166)
- **Rate limiting**: Stricter rate limit bucket `:password_change` (3/min, per router pipeline `:rate_limit_password_change`)
- **Context function**: `Accounts.change_password/3` — both the current-password verification and the new-password hash run via `ArgonPool.run/1` (Issue #166).

---

## 4. Auth & Middleware Guards

- **Plugs fired**: `SecurityHeaders` -> `AuthPipeline` -> `RateLimiter` (bucket: `:password_change`)
- **Password verification**: `Accounts.change_password/3` calls `verify_password/2` which runs `Argon2.verify_pass` inside `ArgonPool` (Issue #166) to validate the current password before applying the change. If the pool is saturated, the call returns `{:error, :argon2_busy}` and the controller responds with HTTP 503.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.SettingsPassword`
- **URL**: `/settings/password`
- **Public or authenticated**: Authenticated only
- **Browser tab title**: "Password — The Stacks"

### Init
- **`Password.init`**: `{ currentPassword = "", newPassword = "", confirmPassword = "", saving = NotAsked }`

### Update cycle
- **Msg**: `SetCurrentPassword val` / `SetNewPassword val` / `SetConfirmPassword val` — update field, reset `saving` to `NotAsked`
- **Msg**: `SavePassword` — runs `validate model`:
  - If `Just _` (validation error): no-op
  - If `Nothing` (valid): calls `Api.updatePassword { currentPassword, newPassword } token SaveCompleted`, sets `saving = Loading`
- **Msg**: `SaveCompleted (Ok _)` -> resets model to `{ init | saving = Success () }` (clears all password fields)
- **Msg**: `SaveCompleted (Err err)` -> `saving = Failure err`

### View
- Wrapped in `viewSettingsHub` layout.
- `h1` "Password", `h2` "Change Password"
- Three password fields with placeholders: "Enter current password", "At least 8 characters", "Repeat new password"
- Validation error shown inline as `p.error` (only when fields are non-empty and not yet submitted)
- Submit button: "Change Password" (or "Saving..." when loading)
- Success: `p.success` "Password changed successfully."
- Failure: `p.error` — "Current password is incorrect." for 422, "Could not change password." for others.
- **CSS classes**: `page--settings`, `settings-section`, `form-field`, `form-field__label`, `form-field__input`, `btn--primary`, `btn--disabled`, `success`, `error`

## 13. Operational Metrics

- **Password change success rate**: Ratio of HTTP 200 responses to total `PUT /api/settings/password` requests.
- **Password change failure rate by type**: Breakdown — `invalid_current_password` (wrong current password), changeset validation errors (new password too short), missing params (422).
- **Rate limiter trigger count**: Number of times the `:password_change` bucket (3/min) rejects requests. Spikes indicate brute-force attempts against current password.
- **Argon2 hash computation time**: p50/p95/p99 for both `Argon2.verify_pass` (current password verification) and `Argon2.hash_pwd_salt` (new password hashing). Two Argon2 operations per successful password change.
- **Event emission reliability**: Count of `user.password_changed` events successfully written to `event_log`.
- **Wrong current password rate**: Percentage of attempts rejected due to incorrect current password. High rates indicate password recall issues.

---

## 14. Performance & Usability Metrics

- **Password change success rate (vs wrong current password)**: Primary usability metric. Target: >80% first-attempt success rate. Low rates suggest users forget their current password.
- **Password change endpoint latency**: p50/p95 for `PUT /api/settings/password`. Includes two Argon2 operations (~400-800ms total CPU). This is the slowest settings endpoint.
- **Client-side validation catch rate**: Percentage of invalid submissions caught by client-side validation before API call (password too short, mismatch). Higher is better — saves server round-trips.
- **Form completion time**: Time from page load to successful password change. Long times may indicate confusion about field requirements.
- **Post-change session continuity**: Whether the user's session remains valid after password change (current implementation does not invalidate existing tokens).

---

## 15. Cost Tracking

- **Argon2 (Fly.io compute)**: Two Argon2 operations per successful change — one `verify_pass` (current password) and one `hash_pwd_salt` (new password), both gated through `ArgonPool` (Issue #166) to bound concurrency. ~400-800ms combined CPU on shared-cpu-1x. Cost: ~$0.000001-0.000002 per change.
- **Argon2 (failed attempts)**: Each failed attempt still runs `Argon2.verify_pass` for the current password. Same CPU cost as the verification step (~200-400ms).
- **Database writes**: One UPDATE to `op.users` (password hash) + one INSERT to `event_log`. Negligible Neon cost.
- **No external service calls**: Password changes do not involve email delivery, vision, or external APIs.
- **Total per-change cost**: ~$0.000002 (dominated by two Argon2 operations).

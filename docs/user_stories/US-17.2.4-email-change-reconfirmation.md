# US-17.2.4 — Changing your email degrades trust until the new address answers

## 1. User Story

> **As a** reader changing the email address on my account, **I want** the new address to prove itself before it becomes my account's address — and my old address to be told, with a one-click way to undo it — **so that** neither a typo nor someone who got hold of my session can quietly take the account away from me.

Today `PUT /api/settings/profile` with an `email` verifies the current password and
then writes the new address straight onto `op.users`. `email_confirmed` is left
`true` and no token is minted. The account therefore sits **confirmed on an address
nobody has proven they can read**, and `RequireConfirmedEmail` — which sits inside
`AuthPipeline` and therefore guards every authenticated route in the API — honours
that as fully verified. The old address is never told anything at all.

Two readers lose from that. The one who typos their address silently loses every
future password-reset and notification with no signal that anything is wrong. The
one whose session is stolen loses the account outright: the attacker changes the
address, and the only proof of ownership the platform holds now points at the
attacker's inbox.

**Acceptance criteria:**

- An email change does **not** change the account's address. It records a
  **pending** address, and sends **two** emails: a confirmation link to the NEW
  address, and a notice to the CURRENT address carrying a **revert** link and the
  address the change was aimed at.
- The account stays fully usable for a **7-day grace window** while the change is
  pending. `email_confirmed` is not touched at request time.
- Clicking the confirmation link at the new address **swaps** the pending address
  into `email`, clears the pending state, and leaves the account confirmed.
- Clicking the revert link at the old address **cancels** the change: the pending
  state is cleared, the confirmation link stops working, `email_confirmed` is
  restored to `true`, and **every session is revoked** — the hijack path closes
  behind itself.
- If the window lapses with the change still pending, a daily sweep flips
  `email_confirmed` to `false`. `RequireConfirmedEmail` then hard-gates the API,
  and login is refused, exactly as for an unconfirmed signup. The mechanism is the
  flag: the plug's own semantics are untouched.
- The revert link outlives the window (**30 days**), because after the window it is
  the account's only way back.
- Both link endpoints are unauthenticated and answer **uniformly**: every failure —
  malformed token, expired token, token that matches no row, a change already
  resolved — lands on one identical page. Nothing about which addresses exist, or
  which links were ever issued, can be read off them.
- The settings page states the pending situation honestly and in full: which
  address was asked to confirm, which address got the revert link, and when the
  window ends.

## 2. Why a grace window, and not immediate degradation

The obvious implementation is to degrade at request time: null `email_confirmed`
the moment a change is asked for. It is also a way to lock people out of their
accounts with a typo and no warning, because `RequireConfirmedEmail` lives in
`AuthPipeline` and `Accounts.authenticate/2` refuses to mint a token for an
unconfirmed account. A reader who fat-fingers `@gmial.com` and hits Save would be
signed out of everything on the spot, with the only remaining link sitting in an
inbox that does not exist.

So the window is not leniency, it is the difference between a warning and a trap.
For seven days the account works exactly as before, and two emails are racing:
one asking the new address to prove itself, one telling the old address that this
is happening and offering to undo it. Only if **both** go unanswered for a week
does the platform conclude that it no longer knows who reads this account's mail,
and degrades.

Seven days is also the ceiling an unconfirmed signup gets
(`Accounts.unverified_account_max_lifetime_seconds/0`), so "how long may an
address go unproven" has one answer in this system rather than two.

**The consequence must be stated plainly, because it is the sharp edge of this
design:** an account degraded by a lapsed window cannot log in and cannot call any
authenticated route, so it cannot request a *different* change to dig itself out.
The revert link is the way back, and that is why it is signed for 30 days rather
than 7. The notice email says so in as many words.

## 3. UI Interaction Flow

### Happy path — the change is confirmed
1. Reader opens Settings → Profile, edits the Email field. The current-password
   prompt appears (unchanged behaviour).
2. Reader saves. The API answers 200 with the account's **unchanged** email plus
   the pending address.
3. The Email input snaps back to the account's real address, and a pending panel
   appears above it: *"Waiting on new-address@example.com. We sent a confirmation
   link there, and a link to undo this change to old-address@example.com. If
   neither is used by 26 August, you'll be signed out until an address is
   confirmed."*
4. Reader opens the new inbox, clicks **Confirm this address**.
5. The browser lands on `/confirm-email/change-confirmed`: *"Email address
   updated."* The account's address is now the new one; the pending panel is gone
   on the next settings load.

### Happy path — the change is reverted
1–3 as above.
4. Reader (or the real owner, if the change was not theirs) opens the OLD inbox and
   clicks **This wasn't me — undo it**.
5. The browser lands on `/confirm-email/change-reverted`: *"Change undone. Your
   address is unchanged and every signed-in session has been signed out. If this
   wasn't you, change your password now."*
6. The confirmation link at the new address no longer works — it lands on the
   generic failure page like any other dead link.

### Sad paths
- **Address already belongs to an account** — 422 with the ordinary changeset
  error under the field, the same shape and the same disclosure as today's email
  change. (Deliberately unchanged: this is an authenticated caller editing their
  own account, and today's behaviour already answers this question.)
- **Wrong current password** — 422 `invalid_current_password`, unchanged.
- **Email caps reached** (per-user 10/hr or global 100/hr, `Stacks.Email`): the
  change is **refused** with 429 rather than recorded. A pending change whose two
  emails were never sent is a trap with no key in it — better to fail loudly and
  let the reader retry.
- **Dead / already-used / foreign link** on either endpoint: one identical
  `/confirm-email/change-error` page. No distinction, ever.
- **Window lapsed** — the next authenticated request answers 403
  `email not confirmed` and the SPA's existing session-expiry path signs the reader
  out. The revert link still works for the rest of its 30 days.

### Elm state machine
- **Page module**: `Page.Settings.Profile`
- **New model fields**: `pendingEmail : Maybe String`, `pendingEmailSentAt : Maybe String`
- **New Msg**: `GotMe (Result Http.Error Api.MeProfile)` — `init` asks
  `GET /api/auth/me` for server truth, so the panel survives a reload rather than
  existing only in the tab that made the change.
- **Changed Msg**: `SaveProfileCompleted (Result Api.ProfileError Api.ProfileSaved)`,
  where `ProfileSaved = { handle : String, email : String, pendingEmail : Maybe String }`.
  On success the model takes `email`/`initialEmail` from the **server's** value
  (unchanged) and shows `pendingEmail` — the field must not settle on an address
  the account does not have.
- **Landing pages**: `Navigation.Route.ConfirmStatus` gains `EmailChangeConfirmed`,
  `EmailChangeReverted`, `EmailChangeFailed`, reusing the existing `ConfirmEmail`
  route and its card view.

## 4. API Calls

### `PUT /api/settings/profile` *(existing route, changed behaviour)*
- **Auth**: required (`:authenticated` → `AuthPipeline` → `RequireConfirmedEmail`).
- **Controller**: `StacksWeb.UserSettingsController.update_profile/2`.
- **Request body**: unchanged — `{display_name, website_url, handle?, email?, current_password?}`.
- **Response (200)**: `{display_name, website_url, email, handle, syndication_default, pending_email}`.
  `email` is the account's address, which an email change does **not** move;
  `pending_email` is the address awaiting confirmation, or `null`.
- **Response (429)**: `{"error": "email_rate_limited"}` when the change could not
  be recorded because its emails could not be sent.
- Other error shapes unchanged (422 `invalid_current_password`, 422 `{errors}`,
  503 `service_busy`).

### `GET /api/auth/confirm-email-change/:token` *(new)*
- **Auth**: none. Same scope as `GET /api/auth/confirm/:token` — a link clicked in
  an email client that carries no session.
- **Controller**: `StacksWeb.EmailVerificationController.confirm_change/2`.
- **Response**: 302 to `/confirm-email/change-confirmed` on success, 302 to
  `/confirm-email/change-error` for **every** failure.

### `GET /api/auth/revert-email-change/:token` *(new)*
- **Auth**: none, as above.
- **Controller**: `StacksWeb.EmailVerificationController.revert_change/2`.
- **Response**: 302 to `/confirm-email/change-reverted`, or the same single
  `/confirm-email/change-error` page.

### `GET /api/auth/me` *(existing, unchanged route)*
- Now carries `pending_email` and `pending_email_sent_at` in the user object. Both
  are the caller's own data; this serializer is only ever used for the
  authenticated caller's own record (login, refresh, me). The two tokens are
  `skip_fields` in the JSON serializer and never leave the database.

## 5. Auth & Middleware Guards

- `PUT /api/settings/profile`: `SecurityHeaders → AuthPipeline (VerifyHeader →
  EnsureAuthenticated → LoadResource → RequireConfirmedEmail)`. Unchanged.
- Both link endpoints: `SecurityHeaders` only, in the same unauthenticated scope as
  the existing confirm route. The token **is** the credential: signed with its own
  salt, and additionally matched against the value stored on the row, so a
  re-requested change kills the previous link.
- **`RequireConfirmedEmail` is not modified.** Its semantics are the whole point:
  the grace window is implemented by *not degrading `email_confirmed`* while the
  change is pending, and the sweep degrades it at the window's end. The plug keeps
  answering the same question it always did.

## 6. Database Interactions

### Schema (proto-generated — `stacks/common/v1/user.proto` → `proto/persisted.exs` → `mix proto.sync`)

Four new columns on `op.users`, all NULL for an account with no change in flight:

| Column | Type | Meaning |
|---|---|---|
| `pending_email` | text | The address awaiting confirmation. **Personal data.** |
| `pending_email_token` | text | Confirmation link token for the new address. Secret. |
| `pending_email_sent_at` | timestamptz | When the change was requested. The window is **derived** from this — no window-end column exists to drift. |
| `pending_email_revert_token` | text | Revert link token, mailed to the current address. Secret. |

There is deliberately **no unique index on `pending_email`**: two accounts may
name the same pending address, and whoever confirms first wins while the other
gets the uniform failure page. A unique index would turn a rejected change into an
oracle for "does this address already have an account".

### Constraint: `users_pending_email_state_consistent`

```sql
CHECK ( (pending_email IS NULL) = (pending_email_token IS NULL)
    AND (pending_email IS NULL) = (pending_email_sent_at IS NULL)
    AND (pending_email IS NULL) = (pending_email_revert_token IS NULL) )
```

The four columns are one fact. A half-set row is either a pending change nobody
can confirm, a live link pointing at no address, or a change with no clock to age
it out. Added `NOT VALID` and validated in a following migration, matching the
`users_password_reset_pair_consistent` pattern — new columns are all-NULL today,
but the shape of the migration pair is the house's, and copying it costs nothing.

### Write: request a change
`Accounts.update_profile/2` → `update_profile_with_email/2` — one `Ecto.Multi`:
profile changeset → pending-email changeset (validates format, refuses an address
already held by another account) → both `EmailDeliveryJob` inserts →
`user.email_change_requested`. The emails are enqueued **inside** the transaction,
so a pending change and the links that resolve it cannot exist without each other.

### Write: confirm
`Email.confirm_email_change/1` — verify token (salt `"email_change"`, `max_age` =
the grace window) → load by `id` **and** `pending_email_token` → set
`email = pending_email`, `email_confirmed = true`, null all four pending columns.
The unique index on `lower(email)` is the last word: if the address was taken
while the change sat pending, the swap fails and the reader gets the uniform
failure page.

### Write: revert
`Email.revert_email_change/1` — verify token (salt `"email_change_revert"`,
`max_age` 30 days) → load by `id` **and** `pending_email_revert_token` → null all
four pending columns and set `email_confirmed = true`, then
`Accounts.revoke_all_user_sessions/1`.

### Write: sweep
`Accounts.lapsed_email_change_ids/1` selects `pending_email IS NOT NULL AND
email_confirmed = true AND pending_email_sent_at < now - 7 days`; the worker flips
`email_confirmed` to `false` per account and emits `user.email_change_expired`.
The pending columns are **kept**: the row must still say what the account is
waiting on, and the revert link must still resolve.

### Read: the abandoned-signup reaper must not see a degraded account

`Accounts.expired_unverified_ids/1` selects unconfirmed accounts older than the
link TTL and erases them through the full GDPR path. An account degraded by a
lapsed window is `email_confirmed = false` and arbitrarily old — it would have
walked straight into that erasure. The candidate query therefore also requires
`email_confirmation_token IS NOT NULL` (an account that was confirmed once had its
signup token nulled forever, so holding one is the mark of a signup that was never
confirmed) **and** `pending_email IS NULL` (an account mid-change is not an
abandoned signup). A test drives exactly this: sweep, then reap, then assert the
account is still there.

## 7. Event Flow & Lifecycle

| Event | Aggregate | Payload | Emitted by |
|---|---|---|---|
| `user.email_change_requested` | user / user id | `{}` | `Accounts.update_profile_with_email/2` |
| `user.email_change_confirmed` | user / user id | `{}` | `Email.confirm_email_change/1` |
| `user.email_change_reverted` | user / user id | `{}` | `Email.revert_email_change/1` |
| `user.email_change_expired` | user / user id | `{}` | `Workers.ExpiredEmailChangesJob` |

All four carry an **empty payload**. Neither address appears in `op.event_log`,
which is append-only and survives erasure as a UUID-only skeleton; the aggregate id
is the user id and anything more would be personal data written somewhere erasure
only blanks rather than removes. All four are declared in
`Events.PayloadContract` and listed in `Registry.@unsubscribed` — nothing acts on
them; they are the audit trail of an account's identity moving.

## 8. Background Jobs (Oban)

### `Stacks.Workers.EmailDeliveryJob` *(existing worker, two new templates)*
- `email_change_confirmation` — addressed to **`user.pending_email`**, not
  `user.email`. The recipient is read from the row at delivery time, so a change
  reverted between enqueue and delivery discards the job instead of mailing a link
  that no longer resolves.
- `email_change_notice` — addressed to `user.email`, carrying the pending address
  (HTML-escaped: it is reader-supplied text going into a template) and the revert
  link.
- Both bypass notification preferences, like every other transactional email.

### `Stacks.Workers.ExpiredEmailChangesJob` *(new)*
- Queue `:default`, `max_attempts: 3`, daily at 09:45 UTC — beside the other two
  auth sweeps rather than inside them.
- **Why not extend `ExpiredUnverifiedAccountsJob`**, as the cheaper option: that
  worker's whole contract — its name, its `[:stacks, :accounts, :unverified_reaped]`
  telemetry, its partial-failure return — is about *erasing* accounts through
  `GDPR.Deletion.delete_user_data/2`. This sweep flips one boolean on live accounts
  that keep all their data. Putting an irreversible erasure loop and a reversible
  flag flip behind one retry policy buys one crontab line and costs the ability to
  reason about either.

## 9–11. Storage, cache, dbt

No storage or cache interaction. All four columns are `dbt_exclude` in
`proto/persisted.exs`, so `stg_users` never selects them: `pending_email` is
personal data, the two tokens are credentials, and the warehouse has no question
that a change in flight answers.

---

## 12. Observability

`[:stacks, :auth, :email_change]` counts every outcome with an `:outcome` tag —
`:requested`, `:rate_limited`, `:confirmed`, `:revert_confirmed`, `:invalid_confirm`,
`:invalid_revert`, `:window_lapsed` — following the truthful-outcome shape the
password-reset and confirmation-resend counters already use: counting an outcome
and answering the caller are the same act, so a new outcome cannot be added to one
without reaching the other. Metadata carries the outcome only. Two of these
endpoints are unauthenticated, and a counter tagged with an address or a user id
would be a record of who asked.

## 13. GDPR

- **Erasure** — the four columns live on `op.users`, which
  `GDPR.Deletion.delete_user_data/2` hard-deletes (`repo.delete(user)`), so
  `pending_email` goes with the row. No new step, and no free text survives.
- **Export** — `pending_email` and `pending_email_sent_at` are in
  `GDPR.Export.export_user_data/2`'s user map: an address the reader typed is data
  about the reader. The two tokens are excluded as secrets, with the rationale
  recorded beside `email_confirmation_token`'s in the schema-sweep guard's
  exclusion list.
- **Event log** — empty payloads (§7); the addresses never enter `op.event_log`.
- **Warehouse** — `dbt_exclude` on all four (§9).
- **Consent** — no new consent surface: transactional mail about the account's own
  credentials, like registration confirmation and password reset.

# US-14.2.1 — Sign In to an Existing Account

## 1. User Story

> **As a** returning user, **I want to** sign in to my account **so that** I can access my book collection and all authenticated features.

Authenticate with existing credentials and resume using the platform. The system validates credentials against the stored Argon2-hashed password, checks email confirmation status, and issues a JWT on success.

**Acceptance criteria:**
- Login form collects email and password
- Successful login returns a JWT and stores it for subsequent API requests
- The user is redirected to the AntiLibrary (`/antilibrary`) after successful login
- Invalid credentials produce a generic error message (no email enumeration)
- The submit button is disabled during the API request
- Rate limiting is applied to the login endpoint to prevent brute-force attacks
- Unconfirmed email returns a 403 with `"email_unconfirmed"` error

---

## 2. UI Interaction Flow

### Happy Path
1. User navigates to `/login` (or clicks "Sign In" in the nav).
2. The login card renders with "Sign In" tab active. Two fields: Email and Password.
3. User enters credentials. Real-time validation: email must contain `@` and `.`, password must be >= 8 characters.
4. User clicks "Enter the Stacks" (submit button). Button shows spinner during request.
5. API returns `{ token, user: { id, email, display_name, role, ... } }`.
6. Elm receives `GotAuthResponse (Ok authResponse)`, sets `transitionState = Transitioning`, emits `StartTransition`.
7. Main.elm stores `pendingAuthResponse` and calls `playLoginTransition` port (4000ms door animation).
8. After animation, `onLoginTransitionComplete` port fires, Elm dispatches `LoginTransitionCompleted`.
9. Main.elm constructs `Auth` record, stores it via `saveAuth` port (writes to localStorage), and navigates to `/antilibrary`.

### Sad Paths
- **Invalid credentials**: API returns 401. User sees: "The door remains shut. Invalid credentials."
- **Email not confirmed**: API returns 403 with `"email_unconfirmed"`. User sees an error (currently handled as a generic HTTP error).
- **Missing fields**: API returns 422. User sees: "Please ensure all fields are properly filled."
- **Network error**: User sees: "The library is unreachable. Please try again."
- **Rate limited**: API returns 429 via `RateLimiter` plug.

### Elm State Machine
- **Page module**: `Page.Login`
- **Model fields involved**: `email`, `password`, `mode` (set to `LoginMode`), `submitState`, `transitionState`, `emailValidation`, `passwordValidation`
- **Msg flow**: `EmailChanged`/`PasswordChanged` -> validation -> `FormSubmitted` -> `Api.login` -> `GotAuthResponse` -> `StartTransition` OutMsg -> `LoginTransitionCompleted` -> `LoggedIn` OutMsg
- **RemoteData states**: `NotAsked` -> `Loading` -> `Success`/`Failure`
- **OutMsg pattern**: `StartTransition authResponse` -> Main triggers door animation; `LoggedIn authResponse` -> Main stores auth, navigates to `/antilibrary`

## 3. API Calls

### `POST /api/auth/login`
- **Auth**: None
- **Pipeline**: `:api`, `:rate_limit_auth`
- **Controller**: `StacksWeb.AuthController.login/2`
- **Request body**: `{ "email": string, "password": string }`
- **Response (success)**: `{ "token": "jwt...", "user": { "id": uuid, "email": string, "display_name": string, "role": string, "profile_visibility": string, "age_verified": bool, "consent_analytics": bool, "country_code": string, "city": string } }` — HTTP 200
- **Response (error)**:
  - `{ "error": "invalid_credentials" }` — HTTP 401
  - `{ "error": "email_unconfirmed" }` — HTTP 403
  - `{ "error": "email and password are required" }` — HTTP 422

## 4. Auth & Middleware Guards

- **Plugs fired** (in order): `SecurityHeaders` -> `RateLimiter` (bucket: `:auth`)
- **No authentication required** for login endpoint.
- **Timing attack prevention**: `Argon2.no_user_verify()` is called when no user is found, to prevent timing-based email enumeration.
- **Email confirmation check**: After password verification, `check_email_confirmed/1` ensures `email_confirmed == true` before issuing a token.

## 5. Database Interactions

### Read: Look up user by email
- **Table(s)**: `op.users`
- **Query**: `Repo.get_by(User, email: String.downcase(email))`
- **Schema module**: `Stacks.Accounts.User`

### Read: Verify password
- **Operation**: `Argon2.verify_pass(password, user.password_hash)` — compares plaintext against stored hash.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Route variant**: `Route.Login`
- **URL**: `/login`
- **Public or authenticated**: Public

### Init
- **`initPage` branch**: `Route.Login` -> `PageLogin Login.init`
- **API calls on init**: None
- **Initial model state**: `email = ""`, `password = ""`, `displayName = ""`, `mode = LoginMode`, `submitState = NotAsked`, `transitionState = Idle`

### Update cycle
- **Msg**: `EmailChanged email` — updates email, validates format, resets `submitState`
- **Msg**: `PasswordChanged password` — updates password, validates length, resets `submitState`
- **Msg**: `FormSubmitted` — calls `Api.login { email, password }`, sets `submitState = Loading`
- **Msg**: `GotAuthResponse (Ok authResponse)` — sets `submitState = Success`, `transitionState = Transitioning`, OutMsg `StartTransition authResponse`
- **Msg**: `GotAuthResponse (Err err)` — sets `submitState = Failure err`
- **Msg**: `TransitionCompleted authResponse` — sets `transitionState = Complete`, OutMsg `LoggedIn authResponse`
- **Main.elm on StartTransition**: Stores `pendingAuthResponse`, calls `playLoginTransition` port with `{ duration: 4000 }`
- **Main.elm on LoggedIn**: Constructs `Auth` from response, sets `model.auth = Just auth`, calls `saveAuth` port (encodes `{ token, userId, email, displayName, role }` to JSON, stored in localStorage), calls `Nav.pushUrl` to `/antilibrary`
- **Port**: `saveAuth : Json.Encode.Value -> Cmd msg` — stores auth data in localStorage for session persistence across page reloads

### View
- **Key elements**: Multi-layer login animation (`layer-arrival`, `layer-passage`, `layer-bookshelf`, etc.), login card overlay with form. Submit button text: "Enter the Stacks".
- **ARIA attributes**: `role="tablist"`, `role="tab"`, `aria-selected`, `aria-required="true"` on inputs, `aria-live="polite"` on error container.
- **CSS classes**: `page--login`, `login-overlay`, `login-card`, `login-card__title`, `login-card__subtitle`, `login-card__tab`, `login-card__submit`

## 13. Operational Metrics

- **Login success rate**: Ratio of HTTP 200 responses to total `POST /api/auth/login` requests.
- **Login failure rate by type**: Breakdown of failures — HTTP 401 (invalid credentials), HTTP 403 (email unconfirmed), HTTP 422 (missing fields), HTTP 429 (rate limited).
- **Rate limiter trigger count**: Number of times the `:auth` bucket (5/min per IP) rejects login attempts. Spikes indicate brute-force attempts.
- **JWT issuance count**: Number of tokens issued via `Guardian.encode_and_sign/2` on successful login.
- **Argon2 verification time**: p50/p95/p99 latency for `Argon2.verify_pass/2` and `Argon2.no_user_verify/0`. Directly impacts login response time.
- **Audit log write rate**: Count of `user.login` audit entries written per hour/day.
- **Unconfirmed email rejection rate**: Percentage of login attempts rejected due to `email_confirmed == false`. High rate indicates email confirmation UX issues.

---

## 14. Performance & Usability Metrics

- **Login time (form submit to redirect)**: Client-side measurement from `FormSubmitted` to `LoginTransitionCompleted`. Includes API round-trip + 4000ms door animation.
- **Login API latency**: p50/p95 for `POST /api/auth/login` server-side (Argon2 verification + DB lookup + JWT issuance).
- **Incorrect password retry rate**: Average number of failed attempts before a successful login. High values indicate password recall issues.
- **Time-on-login-page**: Duration from page load to successful form submission. Long durations may indicate UX confusion.
- **Tab preference**: Ratio of users who stay on Sign In tab vs switch to Register tab.
- **Door animation completion rate**: Percentage of logins where the 4000ms transition animation completes vs is interrupted (e.g., by navigation).
- **Mobile vs desktop login success rate**: Breakdown by device type to identify platform-specific UX issues.

## 15. Cost Tracking

- **Argon2 (Fly.io compute)**: Each login attempt triggers `Argon2.verify_pass` (~200-400ms CPU on shared-cpu-1x). Failed logins with non-existent users still invoke `Argon2.no_user_verify` (same CPU cost, by design for timing attack prevention). Cost: ~$0.0000005-0.000001 per login attempt.
- **Guardian JWT**: Token encoding is HMAC-SHA512 — negligible CPU (<1ms).
- **Database reads**: One `Repo.get_by` query per login attempt. Negligible Neon cost.
- **Audit log writes**: One INSERT to audit log per successful login. Negligible cost.
- **No external service calls**: Login does not involve Resend, vision, or any external APIs.
- **Total per-login cost**: ~$0.000001 (dominated by Argon2 CPU time).

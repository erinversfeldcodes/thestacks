# US-15.2.2 — Swipe Navigation Between Bookshelves (Mobile)

## 1. User Story

> **As a** mobile user, **I want to** swipe left or right to move between adjacent bookshelves **so that** browsing my collection feels fluid and tactile on a touch device.

**Acceptance criteria:**
- Swipe left on a bookshelf navigates to the next shelf in sequence
- Swipe right navigates to the previous shelf in sequence
- Swiping at the boundaries (first or last shelf) wraps around (current implementation uses modular arithmetic)
- Swipe navigation triggers the same transition animations as click navigation
- Swipe gestures are detected via JavaScript ports and communicated to the Elm runtime

---

## 2. UI Interaction Flow

### Happy Path
1. User is on a bookshelf page (Library, AntiLibrary, WishList, ReadingPile, or LookingForHome).
2. User performs a swipe gesture (detected by JavaScript).
3. JavaScript sends the swipe direction ("left" or "right") to Elm via the `onSwipe` port.
4. Main.elm receives `SwipeReceived direction`.
5. `SwipeNavigation.swipeLeft` or `SwipeNavigation.swipeRight` is called with the current route.
6. If a valid next route exists, `Nav.pushUrl` navigates to it.
7. `UrlChanged` fires, loading the new bookshelf page with its transition animation.

### Bookshelf Order
The `bookshelfRoutes` list in `SwipeNavigation.elm` defines the order:
1. `Library`
2. `AntiLibrary`
3. `WishList`
4. `ReadingPile`
5. `LookingForHome`

### Wraparound Behaviour
**Note:** The current implementation uses `modBy len (idx + 1)` and `modBy len (idx - 1 + len)`, which means swiping wraps around — swiping left on LookingForHome goes to Library, and swiping right on Library goes to LookingForHome. The spec says "swiping past the first or last shelf does nothing," but the implementation wraps.

### Non-Bookshelf Pages
If the user is on a non-bookshelf page (Search, Upload, Settings, etc.), `findIndex` returns `Nothing`, and `swipeRoute` returns `Nothing`. The swipe is ignored.

### Elm State Machine
- **Module**: `Navigation.SwipeNavigation`
- **Port**: `port onSwipe : (Decode.Value -> msg) -> Sub msg` — receives swipe direction from JS.
- **Msg flow**: JS swipe detected -> `onSwipe` port -> `decodeSwipe` -> `SwipeReceived direction` -> `SwipeNavigation.swipeLeft/swipeRight` -> `Nav.pushUrl` (or nothing).

## 12. Elm Frontend State Machine (Detail)

### Route
- **Applicable routes**: `Library`, `AntiLibrary`, `WishList`, `ReadingPile`, `LookingForHome`
- **Non-applicable routes**: All others — swipe is silently ignored.

### Subscriptions
- `onSwipe decodeSwipe` — active globally, decodes incoming port values.
- `decodeSwipe : Decode.Value -> Msg` — decodes string ("left"/"right") -> `SwipeReceived direction`; decode failure -> `SwipeIgnored`.

### Update cycle
- **Msg**: `SwipeReceived direction`
  - If `direction == "left"`: `SwipeNavigation.swipeLeft model.route`
  - If `direction == "right"`: `SwipeNavigation.swipeRight model.route`
  - If `Just nextRoute`: `Nav.pushUrl model.key (Route.toPath nextRoute)`
  - If `Nothing`: `Cmd.none` (not on a bookshelf page)
- **Msg**: `SwipeIgnored` — `( model, Cmd.none )`

### SwipeNavigation module
- `bookshelfRoutes : List Route` — `[Library, AntiLibrary, WishList, ReadingPile, LookingForHome]`
- `swipeLeft : Route -> Maybe Route` — finds current index, returns route at `(idx + 1) % len`
- `swipeRight : Route -> Maybe Route` — finds current index, returns route at `(idx - 1 + len) % len`
- `findIndex : Route -> List Route -> Int -> Maybe Int` — linear scan for route in list
- `getAt : Int -> List Route -> Maybe Route` — index into list

### View
- No visible swipe UI elements. The swipe is a gesture-only interaction.
- Transition animations are applied by `UrlChanged` handler via `transitionClass`.

## 13. Operational Metrics

- **Swipe event rate**: Count of `onSwipe` port events received per session, split by direction ("left" vs "right").
- **Swipe-to-navigation success rate**: Percentage of swipe events that result in a `Nav.pushUrl` call (vs being ignored because the user is on a non-bookshelf page).
- **Swipe decode failure rate**: Count of `SwipeIgnored` messages (port decode failures). Should be zero under normal operation.
- **Swipe vs click navigation ratio**: Proportion of bookshelf-to-bookshelf navigations initiated by swipe vs top nav click.
- **Wraparound swipe rate**: How often users swipe past the boundary (LookingForHome -> Library, Library -> LookingForHome).

---

## 14. Performance & Usability Metrics

- **Swipe detection latency**: Time from physical swipe gesture to `SwipeReceived` Msg in Elm. Depends on JavaScript swipe detection implementation.
- **Swipe-to-page-load time**: Time from swipe gesture to target bookshelf page fully rendered (includes API call for bookshelf data).
- **Swipe discoverability**: Percentage of mobile users who ever use swipe navigation. Low rates indicate the gesture is not discoverable.
- **Swipe direction accuracy**: Whether users swipe in the expected direction for their intended destination.
- **Non-bookshelf swipe attempt rate**: How often users attempt to swipe on non-bookshelf pages (ignored swipes). High rates indicate confusion about where swipe works.

---

## 15. Cost Tracking

- **No server-side costs**: Swipe navigation is purely client-side. The resulting `Nav.pushUrl` triggers a route change, and the target bookshelf page makes its own API calls (accounted for in those stories).
- **Compute**: Zero. JavaScript swipe detection + Elm routing logic.
- **Total cost**: $0.00 (client-side only).

# US-16.3.1 — Handle Unauthenticated Access to Protected Pages

## 1. User Story

> **As a** user who is not signed in, **I want** protected pages to redirect me to the sign-in page **so that** I can authenticate and then access the content I was trying to reach.

**Acceptance criteria:**
- Unauthenticated API requests to protected endpoints return 401
- The frontend handles unauthenticated access by redirecting to the sign-in page
- The sign-in page loads cleanly after the redirect
- After authentication, the user is redirected to `/antilibrary`

---

## 2. UI Interaction Flow

### Happy Path
1. Unauthenticated user navigates directly to a protected URL (e.g., `/library`, `/upload`, `/settings/consent`).
2. The Elm router parses the URL to the appropriate route (e.g., `Route.Library`).
3. `initPage` calls `requiresAuth route`. For all protected routes, this returns `True`.
4. `requiresAuth` returns `True` AND `maybeAuth == Nothing`.
5. `initPage` returns `( PageLogin Login.init, Cmd.none )` — the login page renders instead of the protected page.
6. No API call is made. No 401 is received. The redirect is entirely client-side.
7. After successful login, user is redirected to `/antilibrary` (not back to the originally requested page).

### Routes That Require Auth
All routes return `True` from `requiresAuth` except:
- `Home`
- `Login`
- `CostTransparency`
- `Catalogue`
- `BookDetail _`
- `MarketplaceBrowse`
- `MarketplaceDetail _`
- `BlogArchive`
- `BlogPost _`
- `ConfirmEmail _`
- `NotFound`

### Server-Side 401 (Defence in Depth)
If an API request somehow reaches a protected endpoint without a valid token:
1. `StacksWeb.Plugs.AuthPipeline` -> `Guardian.Plug.EnsureAuthenticated` fails.
2. `StacksWeb.Plugs.AuthErrorHandler` returns `{ "error": "unauthenticated" }` with HTTP 401.
3. The Elm page's `RemoteData` field transitions to `Failure (Http.BadStatus 401)`.
4. A page that wires the expiry path emits a `SessionExpired` OutMsg, which the **global
   session-expiry interceptor** (#173/#178, `Main.elm:857-920` — `handleSessionExpiry` /
   `forceSessionExpiry`) turns into a hard sign-out: it clears stored auth and redirects to
   `/login` with a `data-testid="session-expired-notice"` banner ("The library closed your session
   for safekeeping — sign in again to return."). This is distinct from the client-side
   `requiresAuth` guard above, which renders Login **in place** at the protected URL for a user who
   was never authenticated.

> **Doc reconciliation (2026-07-25, Issue #125 Phase 1):** the previous note here — "there is
> currently no global 401 handler; each page handles the error independently" — is obsolete. The
> #173/#178 interceptor now exists. **Live-drive evidence (local stack):** navigating an
> authenticated bookshelf with a server-revoked token (revoked via a password change, #178/#179)
> redirects to `/login` and shows the `session-expired-notice` banner. **Important nuance also
> observed:** the interceptor fires on **page-load fetch** 401s (bookshelf load → redirect), but a
> settings **save** 401 (e.g. `PUT /api/settings/profile` with a revoked token) is NOT routed
> through it — `Page.Settings.Profile` surfaces the 401 as an inline "Could not save profile."
> message and stays on the page. Coverage of the interceptor's `SessionExpired` OutMsg is per-page,
> not universal.

### Elm State Machine
- **Guard function**: `requiresAuth : Route -> Bool` in Main.elm.
- **Redirect logic**: In `initPage`, if `requiresAuth route && maybeAuth == Nothing`, returns `( PageLogin Login.init, Cmd.none )`.
- **No return-to-original-page**: After login, user always goes to `/antilibrary`. The originally requested route is not stored.

## 3. API Calls

### `AuthErrorHandler` (server-side fallback)
- **401 Unauthenticated**: `{ "error": "unauthenticated" }` — missing or invalid token
- **403 Forbidden**: `{ "error": "unauthorized" }` — valid token but insufficient permissions (e.g., unconfirmed email)

---

## 4. Auth & Middleware Guards

### Client-Side Guard
- `requiresAuth` function checks route type. Protected routes are caught before any API call.

### Server-Side Guard
- **`AuthPipeline`**: `Guardian.Plug.VerifyHeader` (scheme: "Bearer") -> `Guardian.Plug.EnsureAuthenticated` -> `Guardian.Plug.LoadResource` (allow_blank: false) -> `RequireConfirmedEmail`
- **`AuthErrorHandler`**: Returns JSON error responses for auth failures.
- **`RequireConfirmedEmail`**: Returns 403 if user exists but `email_confirmed == false`.

## 12. Elm Frontend State Machine (Detail)

### Route
- **Applicable routes**: All routes where `requiresAuth` returns `True`.
- **Redirect target**: `Route.Login` (`/login`)

### Init
- **Guard in `initPage`**:
  ```elm
  initPage route maybeAuth maybePreviousRoute =
      if requiresAuth route && maybeAuth == Nothing then
          ( PageLogin Login.init, Cmd.none )
      else
          initPageAuthenticated route maybeAuth maybePreviousRoute
  ```
- This runs on both initial page load (from URL) and on subsequent `UrlChanged` events.
- The URL in the browser bar does NOT change to `/login` — the login page renders at the protected URL. This means the user cannot share the URL to the protected page.

### Update cycle
- After successful login (`LoggedIn` OutMsg), Main.elm calls `Nav.pushUrl model.key (Route.toPath AntiLibrary)`, navigating to `/antilibrary` regardless of the originally requested route.
- **Missing feature**: Store the requested route and redirect there after authentication.

### View
- When the guard triggers, `PageLogin Login.init` renders the standard login form.
- No error banner or message — the login page appears as if the user navigated there directly.

## 13. Operational Metrics

- **Client-side redirect rate**: Count of `requiresAuth` guard triggers per day (unauthenticated user attempts to access a protected route).
- **Server-side 401 rate**: Count of HTTP 401 responses from `AuthErrorHandler`. Should be near zero if client-side guards work correctly — non-zero indicates direct API access attempts or stale tokens.
- **Server-side 403 rate**: Count of HTTP 403 responses (valid token but unconfirmed email). Indicates users who registered but did not confirm.
- **Protected route attempt distribution**: Which protected routes unauthenticated users most frequently attempt to access.
- **Post-redirect login success rate**: Percentage of users who successfully log in after being redirected from a protected route.

---

## 14. Performance & Usability Metrics

- **Redirect latency**: Time from protected URL navigation to login page render. Should be <50ms (client-side guard, no API call, synchronous `requiresAuth` check).
- **Return-to-intent rate**: Currently users always go to `/antilibrary` after login, not their originally requested page. Track how many users immediately navigate to a different page after post-redirect login (indicates need for return-to-original-page feature).
- **Confusion indicator**: Rate of users who attempt the same protected URL multiple times without logging in (may not understand why they see the login page).
- **URL bar mismatch awareness**: The login page renders at the protected URL (e.g., `/library` shows the login form). Track if users share these URLs expecting the protected content.

---

## 15. Cost Tracking

- **No server-side costs**: The client-side `requiresAuth` guard prevents API calls entirely. No database reads, no external services.
- **Server-side 401/403 fallback**: If an API call does reach the server without auth, `AuthErrorHandler` returns a JSON error. Cost: one request handler invocation — negligible.
- **Total cost**: $0.00 (client-side guard prevents any server-side work).

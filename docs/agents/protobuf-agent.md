# The Stacks — Protobuf Agent

## Role
Develop and maintain the Protobuf schema contracts: `.proto` files, buf configuration, the `proto/persisted.exs` manifest, code generation to all 4 languages, breaking change detection, and event upcasting patterns. Protobuf is the **single source of truth** for all structured data (ADR 007, ADR 009, ADR 010, ADR 014) — Ecto schemas, dbt staging models, migrations, ProtoJSON serializer, schema.yml, and Elm decoders are all generated from `.proto` files via `mix proto.sync` (Issue #131, complete).

## Technology Stack
- **Schema language:** Protocol Buffers v3
- **Toolchain:** buf (lint, breaking change detection only — `buf generate` is **not** used)
- **Wire format:** JSON (not binary — for debuggability and Elm compatibility)
- **Code generation:** Custom generators (`scripts/gen_python_proto.py` + wrappers) that read the buf JSON descriptor and emit idiomatic output per language. `mix proto.sync` drives Elixir Ecto + dbt + ProtoJSON + migration drift detection. See `buf.gen.yaml` for the rationale (avoids Modal protobuf<7 conflict; integrates with each service's conventions).

## Owned Domains

### Proto Files (in `proto/`)
All `.proto` files live under `proto/stacks/{domain}/v1/` (versioned packages).
```
proto/
├── buf.yaml                    # Module config, lint rules
├── buf.gen.yaml                # Retained for `buf lint`/`buf breaking`; plugin entries are commented out — see Code Generation below
├── persisted.exs               # Manifest mapping proto messages → persisted DB tables (ADR 009)
├── gen/                        # Buf JSON descriptor output (consumed by custom generators)
└── stacks/
    ├── api/v1/                 # Public API request/response envelopes (admin, auth, blog, book, bookshelf, listing, source, requests)
    ├── common/v1/              # Domain types shared across services (book, blog, costs, enrichment, listing, location, marketplace, placement, social, upload, user)
    ├── infra/v1/               # Infrastructure-owned caches (book_cache)
    ├── internal/v1/            # Service-to-service contracts (event_bus, audit, partner, scraper, vision)
    └── monitoring/v1/          # Operational telemetry (source_health_check)
```

### Generated Code
- **Elixir Ecto schemas:** `apps/core/lib/stacks/gen/` — generated by `mix proto.sync` (committed; CI runs `mix proto.sync --check` to detect drift)
- **dbt staging models + schema.yml:** `dbt/models/staging/` — generated by `mix proto.sync` (committed)
- **ProtoJSON.Gen base serializer:** `apps/core/lib/stacks/gen/proto_json.ex` — generated by `mix proto.sync` (gitignored)
- **Elm decoders/encoders:** `proto/gen/elm/` — regenerated at build time via `scripts/gen-elm-proto.sh` (gitignored). JSON decoders, not binary Protobuf.
- **Python (Pydantic v2):** generated via `scripts/gen-python-proto.sh`
- **Rust (serde):** generated via `scripts/gen-rust-proto.sh`
- **Elixir defstructs (non-Ecto):** generated via `scripts/gen-elixir-proto.sh`

### buf Configuration
```yaml
# buf.yaml
version: v2
lint:
  use:
    - STANDARD
    - COMMENTS
  enum_zero_value_suffix: _UNSPECIFIED
  disallow_comment_ignores: true
breaking:
  use:
    - FILE
```

### Persisted Manifest (`proto/persisted.exs`)
Maps proto messages → DB tables with `field_overrides` for type coercion (`api_only`, `dbt_exclude`, `ecto_name`, `belongs_to`, `assoc_name`, ecto_type, defaults, nullability) and explicit `indexes`. This file is the source of truth for which proto messages are persisted and how. Adding a new persisted message = add an entry here, then run `mix proto.sync`.

## Key Patterns

### Field numbers are forever
Never reuse a field number. Never change a field's type. Additive changes only. `buf breaking` enforces this in CI.

### Enum zero value
Every enum must have an `_UNSPECIFIED = 0` value. This is buf's DEFAULT lint rule and prevents ambiguous defaults.

### JSON on the wire
All Protobuf messages are serialised as JSON (not binary). This means:
- Human-readable in logs and event_log JSONB columns
- Elm can consume them with standard JSON decoders
- Binary Protobuf is reserved for future optimisation if needed

### Elm decoder generation
Since Elm has no Protobuf runtime, we generate Elm `Json.Decode` / `Json.Encode` modules from `.proto` files via `scripts/gen-elm-proto.sh`. These are gitignored and regenerated at build time (`just setup`, `just dev`, `scripts/deploy-stack.sh`). CI runs `--check` mode to verify the generator output matches.

### `mix proto.sync` (single source of truth)
A single proto message determines the Ecto schema, dbt staging model, dbt schema.yml column definitions, ProtoJSON base serializer, and surfaces migration drift. Changing a field in the proto automatically propagates across all derived layers. Run `mix proto.sync` after any `.proto` edit; CI runs `mix proto.sync --check` and fails on drift. See ADR 009 and ADR 010.

### Event upcasting
Old events in `event_log` may have older schema versions. The `Stacks.Events.Upcaster` module (Elixir) transforms old event shapes to current on read:

```elixir
def upcast(%{"event_type" => "inventory.updated", "schema_version" => 1} = event) do
  event
  |> update_in(["payload"], &Map.put_new(&1, "currency", "ZAR"))
  |> Map.put("schema_version", 2)
  |> upcast()  # chain to next version
end
```

Each version bump is an explicit, testable function clause. Same pattern as Commanded (Elixir CQRS).

## Schema Evolution Rules

| Change | Allowed? | Notes |
|--------|----------|-------|
| Add a new field | Yes | Use next available field number |
| Add a new enum value | Yes | Never at position 0 |
| Remove a field | No | Mark as `reserved` instead |
| Change field type | No | Add a new field with new type |
| Rename a field | JSON only | JSON name can differ from proto name |
| Change field number | Never | |
| Reuse a field number | Never | |

## Integration Handoffs
- **All agents:** Proto changes affect all services. Coordinate via Orchestrator.
- **elixir-agent:** Run `mix proto.sync` after proto edits — regenerates Ecto schemas (`apps/core/lib/stacks/gen/`), dbt staging models, ProtoJSON serializer, and surfaces migration drift. Upcaster functions must be updated together with event schema changes.
- **elm-agent:** Elm decoders are regenerated at build time; verify with `scripts/gen-elm-proto.sh --check` after any proto change
- **rust-agent:** Run `scripts/gen-rust-proto.sh` to regenerate serde types
- **python-agent:** Run `scripts/gen-python-proto.sh` to regenerate Pydantic v2 models
- **database-agent:** Migration files are derived from proto + `persisted.exs`; coordinate any schema change there
- **platform-agent:** `buf lint`, `buf breaking`, and `mix proto.sync --check` run in CI

### Challenge the Brief

Before making any schema changes, read the phase plan carefully and identify anything that seems:
- **Underspecified:** field types, enum values, or message nesting that are ambiguous or would require a breaking change to correct later
- **Risky:** field additions that may conflict with existing reserved numbers, or changes that would silently break JSON serialisation for the Elm frontend
- **Suboptimal:** a better message structure, naming convention, or enum design would serve this contract better long-term
- **Inconsistent:** the plan conflicts with existing field number sequences, the `_UNSPECIFIED = 0` enum rule, or the additive-only evolution constraint

Raise each finding explicitly in your completion report under "Pre-implementation Flags". Field numbers are forever — flag any ambiguity before committing. If no flags, state "None". Do not block on flags — implement as planned, but flag first.

### Self-Verification

Before submitting your completion report:
1. Run `buf lint proto/` and confirm no lint errors.
2. Run `buf breaking proto/ --against '.git#branch=main'` and confirm no unintended breaking changes.
3. If the change touches a persisted message, run `mix proto.sync` and commit any regenerated Ecto schemas / dbt staging models / schema.yml updates; then run `mix proto.sync --check` and confirm clean.
4. Run `scripts/gen-elm-proto.sh --check` and confirm the generated Elm decoders match the current schema. Run the other language generators (`scripts/gen-python-proto.sh`, `scripts/gen-rust-proto.sh`, `scripts/gen-elixir-proto.sh`) if the change affects those services.
5. If upcaster functions were added, trace through the upcast chain with a representative old event payload and confirm the output matches the current schema.
6. If any step fails, fix it before submitting.

Do not submit a completion report with buf lint failures, breaking changes without justification, a `mix proto.sync --check` drift, or a failing `scripts/gen-elm-proto.sh --check`.

### Test-First Protocol

When the Orchestrator delegates a test-writing step (2A-i), follow this protocol:

1. **Read the phase DoD items** and translate each into one or more test cases
2. **Write tests only** — no production code, no stubs, no mock implementations
3. **Run the test suite** and confirm tests fail with meaningful assertion failures:
   - Assertion failures (e.g., "expected X, got Y" or "function not found")
   - Compile errors or missing module errors do not count
4. **Return failing test output** verbatim in your completion report under "Failing Test Evidence"

Do not write any production code until the Orchestrator confirms the failing tests and delegates the implementation step (2A-iii).

**Test command:** `buf lint proto/ && buf breaking proto/ --against '.git#branch=main'`

### Self-Review

Before submitting your completion report, load `docs/agents/reviewers/protobuf-reviewer.md` (and `docs/agents/reviewers/contract-reviewer.md` for cross-service API contract changes) and self-check the following mechanical axes:

| Check | How to verify |
|-------|---------------|
| `buf lint` | Run and confirm zero errors |
| `buf breaking` | Run against main branch and confirm no breaking changes |

# The Stacks — Database Agent

## Role
Develop and maintain the PostgreSQL database: Ecto schemas, migrations, query optimisation, dbt models, and data integrity. You own the data model across all four schemas (op, wh, audit, cache).

## Technology Stack
- **Database:** PostgreSQL (Neon serverless)
- **ORM:** Ecto 3.x
- **Migrations:** Ecto migrations (in `apps/core/priv/repo/migrations/`)
- **Data transforms:** dbt (in `dbt/`)
- **Schema contracts:** Protobuf-generated types drive table structure (ADR-009, ADR-010). Most Ecto schemas under `apps/core/lib/stacks/gen/` are generated by `mix proto.sync` from `.proto` files — do not hand-edit.

## Owned Domains

### Schemas
- **`op` (operational):** All application tables — books, authors, bookshelves, bookshelf_placements, partners, partner_inventory, event_log, marketplace, social, blog, monitoring, etc.
- **`wh` (warehouse):** dbt-managed read models — staging, intermediate, marts
- **`audit`:** Immutable audit_log table with INSERT-only grants and an append-only trigger
- **`cache`:** Short-lived lookup caches (e.g. ISBN resolver, title search)

### Tables
See `docs/technical-architecture.md` section 7 (Database Schema) for full definitions. The op schema covers core (`users`, `books`, `book_editions`, `authors`, `bookshelves`, `bookshelf_placements`, `bookshelf_placement_history`, `shelves`), enrichment (`review_snapshots`, `price_snapshots`, `bookstores`, `bookstore_events`), content (`uploaded_images`), discovery (`third_spaces`, `third_space_events`, `discovered_sources`), partner (`partners`, `partner_inventory`), marketplace (`listings`, `offer_threads`, `offer_messages`, `transactions`), social (`groups`, `group_members`, `group_invitations`, `visibility_grants`, `user_blocks`), blog (`post_comments`, `post_book_associations`), costs/monitoring (`platform_costs`, `source_health_checks`), and the system tables (`event_log`, `oban_jobs`). `audit.audit_log` and the `cache` lookup tables live in their own schemas.

**Domain terminology (critical):** *bookshelf* is the user-facing virtual collection (`op.bookshelves`, five named categories); *shelf* is a physical row within a bookshelf (`op.shelves`). Never conflate the two.

### dbt Models (in `dbt/models/`)
- **Staging (stg_*):** One-to-one with op tables, light cleaning
- **Intermediate (int_*):** Business logic joins and aggregations
- **Marts (mart_*):** Final read models for the API and dashboards

See `docs/implementation-mapping.md` Quick Reference: dbt Model Inventory for the full list.

### Database Roles
- `stacks_app` — Full CRUD on op schema, SELECT on wh, INSERT-only on audit
- `stacks_dbt` — SELECT on op, full CRUD on wh
- `stacks_readonly` — SELECT on op and wh (for debugging)

## Key Patterns

### UUID primary keys everywhere
All tables use `UUID` PKs generated by Ecto. No serial integers.

### TIMESTAMPTZ for all temporal columns
Never use `TIMESTAMP` without timezone.

### Soft deletes via removed_at
Bookshelf placements use `removed_at` (NULL = active). Never hard delete placement data — a partial unique index on `(book_id, bookshelf_id) WHERE removed_at IS NULL` enforces one active placement per book per bookshelf.

### event_log is append-only
No UPDATE or DELETE on event_log (except GDPR erasure of PII in payloads). Partition by month for performance.

### Adaptive staleness
`review_snapshots.stale_after` and similar columns drive re-scrape scheduling. Not a fixed interval.

### JSONB for flexible data
`event_log.payload`, `event_log.metadata`, `partner_spaces.opening_hours`, `audit_log.metadata` — all JSONB. Validated at the application layer (Protobuf schemas), not with CHECK constraints.

## Migration Conventions
- One migration per logical change
- Always reversible (define both `up` and `down`, or use reversible `change` operations)
- Index creation on large tables uses `CREATE INDEX CONCURRENTLY` (via `@disable_ddl_transaction true`)
- Name format: `YYYYMMDDHHMMSS_descriptive_name.exs`

See `docs/agents/standards/migrations.md` for the full migration standard (column types, FK conventions, role grants, lock-safety rules).

## Orchestrator Integration

DO NOT: Write plan files, commit messages, or proceed to next phase.
DO: Write migrations, Ecto schemas, dbt models, and return a completion report. Call `mcp__project-tools__update_progress(number, note)` to append progress notes — do not edit the issue file directly.

### Challenge the Brief

Before writing any code, read the phase plan carefully and identify anything that seems:
- **Underspecified:** column types, nullability constraints, index strategies, or dbt model grain that are ambiguous or missing detail
- **Risky:** irreversible migrations, missing `down/0` implementations, assumptions about existing data volume or distribution that may be wrong
- **Suboptimal:** a better index type, JSONB query pattern, or dbt materialisation strategy exists for this specific use case
- **Inconsistent:** the plan conflicts with existing table conventions (UUID PKs, TIMESTAMPTZ, soft deletes), the schema separation (op/wh/audit/cache), Protobuf-defined field types, or the proto-to-schema codegen boundary (hand-editing a generated schema under `apps/core/lib/stacks/gen/` instead of updating the `.proto` and re-running `mix proto.sync`)

Raise each finding explicitly in your completion report under "Pre-implementation Flags". If no flags, state "None". Do not block on flags — implement as planned, but flag first.

### Self-Verification

Before submitting your completion report:
1. Run `mix ecto.migrate` and confirm it succeeds without errors.
2. Run `mix test` (scoped to repo/schema tests if applicable) and confirm it passes. Record the exact output.
3. Run `dbt test` for any new or changed dbt models and confirm all tests pass.
4. If a new table was created, insert a representative row and query it back to confirm column types and constraints behave as expected.
5. If any step fails, fix it before submitting.

Do not submit a completion report with migration failures, failing tests, or untested schema changes.

### Test-First Protocol

When the Orchestrator delegates a test-writing step (2A-i), follow this protocol:

1. **Read the phase DoD items** and translate each into one or more test cases
2. **Write tests only** — no production code, no stubs, no mock implementations
3. **Run the test suite** and confirm tests fail with meaningful assertion failures:
   - ✅ Assertion failures (e.g., "expected X, got Y" or "function not found")
   - ❌ Compile errors or missing module errors do not count
4. **Return failing test output** verbatim in your completion report under "Failing Test Evidence"

Do not write any production code until the Orchestrator confirms the failing tests and delegates the implementation step (2A-iii).

**Test command:** `mix test` (Ecto tests run through ExUnit)

### Self-Review

Before submitting your completion report, load `docs/agents/reviewers/database-reviewer.md` and self-check the following mechanical axes:

| Check | How to verify |
|-------|---------------|
| Reversible migrations | Every migration has `up`/`down` or uses reversible `change` operations |
| One concern per migration | Each migration file handles one logical change |
| Lock-safe DDL | Large-table alterations use `disable_ddl_transaction!` + `CONCURRENTLY` |
| Timestamps | `timestamps(type: :utc_datetime_usec)` on all tables |
| UUID primary keys | All tables use `binary_id` |
| SQL naming | Lowercase, snake_case, tables plural, columns singular |
| Changesets validate | Required fields, format validations, unique constraints |
| No Repo in schemas | Schemas are data-only; Repo calls live in contexts |
| Tests passing | `mix test` passes with zero failures |

Fix any failures before submitting. Include a **Self-Review** section in your completion report (see Completion Report Format below).

A missing or empty Self-Review section is a reviewer blocker.

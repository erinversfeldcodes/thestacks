# ADR 014: Proto-First Context Interfaces

**Status:** Accepted
**Date:** 2026-03-27
**Deciders:** Platform owner
**Technical area:** Schema contracts, API design, developer experience

---

## Context

ADR 007 established Protobuf as the single source of truth for structured data contracts.
ADR 009 extended that principle to storage, generating Ecto schemas, dbt models, and
migrations from `.proto` messages via `mix proto.sync`.

After completing #131 (proto as single source of truth across all 30 persisted tables),
one significant asymmetry remains:

**Outbound** (response) is fully proto-governed:
- `mix proto.sync` generates `ProtoJSON.Gen` — one serializer function per proto message.
- Controllers call `ProtoJSON.book/1`, `ProtoJSON.placement/1`, etc.
- Responses are guaranteed to match the proto contract; drift is caught in CI.

**Inbound** (request) is proto-decorative:
- `proto/stacks/api/v1/requests.proto` defines 12+ request message types.
- These message definitions are never parsed or validated at runtime.
- Controllers pattern-match on raw `params` maps (`%{"book_id" => ..., "bookshelf_name" => ...}`).
- Validation is manual (`if bookshelf_name in @valid_bookshelves`) or deferred to Ecto
  changesets deep in the context layer.

The result is that the proto contract governs the wire format for responses but provides
no enforcement for requests. A required field could be removed from a request message in
proto with no compile-time or CI consequence. The single source of truth is only half-applied.

**Comparison with Google's approach:**

Google's internal philosophy treats proto messages as the primary data type throughout a
service — not just at the wire boundary. Business logic accepts proto request messages and
returns proto response messages. The service definition (`service ShelvingService { rpc
PlaceBook(...) returns (...); }`) is the authoritative contract, from which routing,
validation, and serialization are derived.

The Stacks currently sits closer to Clean Architecture: domain objects (Ecto structs) live
in the business logic layer; proto is only a wire contract at the edges. This is principled
but creates the inbound gap above, and distributes serialization logic into controllers
rather than owning it in the layer that understands the data.

**Decision driver:**

The goal is not to adopt gRPC or binary serialization — JSON on the wire remains correct
for this stack. The goal is to make the proto contract symmetric (inbound and outbound),
move serialization ownership into context modules where the data lives, and make context
function signatures the machine-readable expression of the API contract.

---

## Decision

**Move toward proto-typed context interfaces in three phases.** Each phase is independently
deployable and valuable. Phase 3 (service definitions) is the long-term goal; Phases 1 and
2 close the inbound gap and are higher priority.

### Phase 1: Inbound request decoding and validation

Extend `mix proto.sync` to generate a `ProtoJSON.Decode` module — a mirror of
`ProtoJSON.Gen` for inbound requests rather than outbound responses.

**New codegen module:** `apps/core/lib/mix/tasks/proto_sync/decode_generator.ex`
**Generated output:** `apps/core/lib/stacks/gen/proto_json_decode.ex`

```elixir
# Generated by mix proto.sync — DO NOT EDIT MANUALLY.
defmodule StacksWeb.ProtoJSON.Decode do
  def place_book_request(params) do
    with {:ok, book_id}        <- require_string(params, "book_id"),
         {:ok, bookshelf_name} <- require_string(params, "bookshelf_name") do
      {:ok, %PlaceBookRequest{book_id: book_id, bookshelf_name: bookshelf_name}}
    end
  end
end
```

Validation rules are derived from proto field definitions:
- Non-optional string/int fields → `require_string/require_integer`
- `optional` fields → `optional_string/optional_integer` (nil on missing)
- Enum fields → validated against the enum value set from the descriptor
- `repeated` fields → validated as lists

A `StacksWeb.Plugs.DecodeRequest` plug runs before controller actions, calls the
appropriate decoder, stores the typed struct in `conn.assigns.request`, and returns
`422 Unprocessable Entity` on validation failure:

```elixir
# Router pipeline
plug StacksWeb.Plugs.DecodeRequest, decoder: &ProtoJSON.Decode.place_book_request/1

# Controller — no more pattern matching on params
def create(conn, _params) do
  %PlaceBookRequest{book_id: book_id, bookshelf_name: bookshelf_name} = conn.assigns.request
  ...
end
```

**What this eliminates:** all manual `%{"key" => val}` pattern matching, `if val in
@valid_enum` guards, and duplicated required-field checks across every controller action.

**CI impact:** `mix proto.sync --check` already catches outbound drift; it will also catch
inbound drift once decode functions are generated. Adding a required field to a request
message in proto automatically updates the decoder and fails CI if the controller doesn't
handle it.

### Phase 2: Proto-typed context function signatures

Context functions accept proto request structs as input and return proto response structs
(or tagged tuples wrapping them) as output. ProtoJSON serialization moves from controllers
into contexts.

**Before:**
```elixir
# Controller owns serialization
def create(conn, _params) do
  %PlaceBookRequest{...} = conn.assigns.request
  case Shelving.place_book(user.id, book_id, bookshelf_name) do
    {:ok, placement} -> json(conn, %{placement: ProtoJSON.placement(placement)})
  end
end

# Context returns Ecto struct
def place_book(user_id, book_id, bookshelf_name) do
  # ... Ecto operations ...
  {:ok, %Placement{}}
end
```

**After:**
```elixir
# Controller is a thin dispatcher
def create(conn, _params) do
  case Shelving.place_book(conn.assigns.request, current_user(conn)) do
    {:ok, response} -> json(conn, response)
    {:error, reason} -> json_error(conn, reason)
  end
end

# Context owns its output shape; internal Ecto work is unchanged
def place_book(%PlaceBookRequest{book_id: book_id, bookshelf_name: bookshelf_name}, user) do
  with {:ok, placement} <- Repo.insert(placement_changeset(...)) do
    {:ok, ProtoJSON.placement(placement)}
  end
end
```

Ecto internals (changesets, queries, associations) remain unchanged. Only the public
interface of each context module changes: it becomes the proto contract expressed as
Elixir function signatures. Callers — controllers, Oban workers, other contexts — are all
typed against the same contract.

**What this eliminates:** `ProtoJSON` calls scattered across controllers; the need for
controllers to know which projection of a resource to use (e.g., `ProtoJSON.catalogue_book`
vs `ProtoJSON.bookshelf_book` — this knowledge lives in the context, which knows the
call site).

### Phase 3: Service definitions in proto (long-term)

Add `service` blocks to the API proto files and extend `mix proto.sync` to generate
controller stubs and router entries from them.

```proto
// proto/stacks/api/v1/shelving_service.proto
service ShelvingService {
  rpc PlaceBook(PlaceBookRequest)   returns (PlacementResponse);
  rpc MoveBook(MoveBookRequest)     returns (PlacementResponse);
  rpc RemoveBook(RemoveBookRequest) returns (google.protobuf.Empty);
}
```

**Generated:** router scope block with HTTP verb mapping, controller module with typed
action stubs and `@spec` annotations.

**Breaking change enforcement:** removing or renaming an RPC method fails `buf breaking` in
CI — the same protection that already applies to field changes in persisted schemas.

**What this achieves:** the proto file becomes the authoritative definition of what
endpoints exist, what they accept, and what they return. Controllers are implementations of
a known contract rather than ad-hoc handlers. New contributors can read the service
definition and know the complete API surface.

This phase is explicitly deferred until Phases 1 and 2 are stable. The HTTP verb mapping
convention (whether to adopt `google.api.http` annotations or define a project-local
approach) requires a separate decision.

---

## Consequences

**Positive:**
- Proto contract is symmetric: inbound and outbound are both validated against proto
  definitions. The current half-applied single source of truth becomes fully applied.
- Controller code is dramatically simpler — no parameter extraction, no manual validation,
  no serialization. Each action is ~5 lines: extract request, call context, return response.
- Context function signatures are the machine-readable API contract. Dialyzer covers them.
  Adding a required request field to proto automatically fails CI if the context doesn't
  handle it.
- `buf breaking` gains coverage over request schemas — today it only catches field changes
  in persisted messages, because request messages are never connected to the runtime.
- Serialization logic (which projection to use, which computed fields to include) lives in
  the context that understands the data, not in controllers that don't.

**Negative:**
- Phase 2 is a large migration — every context function signature changes. The Ecto
  internals are untouched but the public API of every context module is rewritten. This
  should be done context-by-context over multiple PRs, not in one changeset.
- Context functions that currently return `{:ok, %EctoStruct{}}` will return `{:ok, map}`
  (proto-shaped). Any internal callers that pattern-match on Ecto struct fields will need
  updating. Audit required per context before migration.
- The distinction between "domain tables hand-written" and "raw/ingestion tables codegen"
  from ADR 009 applies here too — not every context function maps cleanly to a proto
  request/response pair. Pure domain operations (e.g., internal state machines, GDPR
  erasure) may stay as Elixir-native signatures.
- Phase 3's service definitions require a decision on HTTP verb mapping that isn't yet made.

**Relationship to prior ADRs:**
- Extends ADR 007 (proto as contract) to cover inbound requests, not just wire responses.
- Builds on ADR 009's codegen infrastructure (`mix proto.sync`, `persisted.exs`,
  `buf build` descriptor parsing) — Phase 1 adds a new generator module to an existing
  pipeline rather than introducing new tooling.
- Does not change the JSON-on-the-wire decision from ADR 007. Binary proto encoding is
  not being introduced.

## Implementation notes

**Phase 1 scope** (`mix proto.sync` extension):
- New module: `apps/core/lib/mix/tasks/proto_sync/decode_generator.ex`
- New manifest section: `requests` in `proto/persisted.exs`, mapping request message names
  to the API endpoint(s) that use them (for Plug wiring codegen)
- New plug: `apps/core/lib/stacks_web/plugs/decode_request.ex`
- New generated file: `apps/core/lib/stacks/gen/proto_json_decode.ex`
- Controller migration: replace `%{"key" => val}` pattern matches with
  `conn.assigns.request` access — one controller at a time

**Phase 2 scope** (per-context migration):
- Audit each context for internal callers that pattern-match on Ecto struct return values
- Migrate context function signatures one module at a time (Shelving, Books, Accounts, ...)
- Move `ProtoJSON.*` calls from controllers into context functions
- Update controller tests to use request struct fixtures instead of params maps

**Phase 3 scope** (deferred):
- Decide HTTP verb mapping convention
- Add `service` block codegen to `mix proto.sync`
- Migrate one service as a proof of concept before full rollout
